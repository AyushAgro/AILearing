What an FDE Is

A Forward Deployed Engineer sits between a platform and a paying customer. The job is not "write more demos". It is to turn platform capabilities into measured outcomes under customer constraints — then leave an operable system behind.

The Engineering Problem

Product engineering ships a platform. Sales promises "AI for support in six weeks". Support leadership wants ticket deflection. Security wants no data leaving the VPC. Nobody owns the engagement brief. Three months later there is a dazzling demo, no golden set, no SLO, and an angry renewals call. The missing role was not another model specialist — it was an FDE with contracts.

Possible approaches

  • Solutions consulting only. Slide decks and reference architectures. Fast relationship; weak implementation truth.
  • Product engineering on-site. Builds features the roadmap already planned. Under-weights customer-specific constraints and kill criteria.
  • FDE with an engagement lifecycle. Discovery → brief → PoC → pilot → handoff, each with explicit exit and kill criteria. This volume's default.

Discovery and Problem Framing

Discovery is not a listening tour. It produces an engagement brief: jobs-to-be-done, decision owners, data reality and hard constraints that later chapters cannot invent.

The Engineering Problem

A discovery workshop ends with sticky notes saying "AI assistant for agents". Latency target: "fast". Data: "we'll get you a dump". SSO: "probably Okta". Six weeks later the PoC dies on residency and missing ticket fields. Sticky notes are not a brief.

Jobs-to-Be-Done and Decision Owners

  • Job. Who is trying to accomplish what, in what context, measured how? "Deflect tier-1 password resets" is a job. "Add generative AI" is not.
  • Decision owner. Name the person who can kill or extend the engagement. If that person is "the AI committee", you do not have an owner.
  • Anti-job. What must never happen (cross-tenant leak, unsupervised refund, PII in prompts to a public API).

Scoping and ADRs for Customers

Scope is a decision about build versus buy versus configure, plus PoC exit criteria sharp enough to kill a bad engagement early. ADRs make those decisions survivable after the FDE leaves.

The Engineering Problem

The customer asks for "a full agent that can do everything Zendesk does". The FDE agrees to explore. Eight weeks later the PoC still has no exit criteria, the golden set is the FDE's laptop screenshots, and nobody can say whether the engagement succeeded. Scope without kill criteria is infinite work with finite goodwill.

PoC Exit Criteria and Kill Criteria

  • Exit criteria (go to pilot): numbered, measurable, owned. Example: offline helpful ≥ 80% on co-owned golden set N≥ 100; zero cross-tenant hits; TTFT p95 under brief; cost ≤ budget line on scripted mix.
  • Kill criteria (stop spending): missing decision owner, unreachable SSO, no data sample and no synthetic plan, security theatre that blocks measurement, scope that expands faster than exit criteria.

Risk
  • Exit criteria written only by the vendor are theatre. Require a customer co-signer on the golden-set definition (Chapter 6).
  • "Executive loved the demo" is not an exit criterion. It is a sales note.

ADR stubs every customer engagement needs

  • Workflow versus agent for the first journey (Volume 21).
  • Data plane: customer VPC index versus vendor-hosted with residency tags.
  • Model plane: platform registry only; no laptop API keys in production paths.
  • Degraded mode when the frontier route or connector is down.

Writing the Kill Note

Killing early is a professional outcome. The note to the decision owner should include: what was attempted, which kill criterion triggered, evidence (dates, missing owners, failed gates), what assets remain usable, and an explicit recommendation (stop / defer / re-scope). Avoid blame language; preserve the relationship for a better-scoped return.

Environment Reality

Customer VPCs, identity, networking, secrets and data samples are the terrain. Synthetic substitutes are honest when labelled; pretending a laptop tunnel is production is not.

The Engineering Problem

The PoC runs on an FDE laptop with a personal API key and a CSV emailed by a champion. Security review starts the week before "go-live". Identity is a shared password. The system that worked in the demo cannot be deployed without rewriting networking, secrets and data handling — which is to say the PoC never tested the real environment.

Putting the Checklists on a Calendar

Environment work is often the critical path, not model quality. Schedule SSO and VPC proofs in parallel with discovery labelling. A brief that says vpc_required: true with no networking owner named is incomplete — treat that as a discovery defect, not a week-four surprise.

  • Day 1–3. Confirm landing zone, region, and IdP app registration started.
  • Day 4–7. Private path health check to one read-only customer API.
  • Day 7–10. Secrets in vault; FDE laptop keys revoked from any shared channel.
  • Before any production-like data. Log redaction and retention ADRs signed.
Risk
  • "Temporary" public endpoints for the PoC have a habit of becoming permanent. Prefer private link from day one, even if the model is still scripted.

PoC Engineering

A PoC is a thin vertical slice on Forge with real constraints simulated by fakes where needed — not a second product. Demo hygiene and reproducibility packs decide whether the pilot can restart without the original FDE.

The Engineering Problem

The demo uses a hard-coded answer for the three tickets the champion cares about, a public chat UI, and a live frontier key. When the security team asks to reproduce the run in the VPC, nothing is scriptable. The PoC was a performance, not an engineering artefact.

Thin vertical slice (minimum)

  • One primary job from the brief (e.g. where_is_order).
  • Gateway → forge.guard → forge.router → forge.rag (or workflow) → model adapter → post-guard.
  • Fake connector for the order API with a contract test; real connector behind a flag.
  • Offline eval on the golden set (even if still growing).
  • Reproducibility pack: brief version, prompts, index build script, eval command, seed.

  • Record the exact build SHA, brief version and eval command in the demo notes.

Evaluation with the Customer

Golden sets co-owned with the customer are the only credible PoC exit gate. Offline gates, human review loops and a ban on vanity leaderboards keep the engagement honest.

The Engineering Problem

The vendor reports 92% "accuracy" on an internal set the customer has never seen. Champions disagree with half the answers in a live session. Leadership still wants to pilot because the number was large. Without co-ownership, evaluation is marketing.

Golden-Set Co-Ownership

  • Co-owners. At least one customer labeler (or team) and one FDE; both named in the brief.
  • Rubric. Helpful / unhelpful / harmful / abstain — aligned with Volume 10 and forge.eval.
  • Slice plan. By intent, language, tenant, and "must_never" probes.
  • Change control. Adding cases is encouraged; silently dropping hard cases is a kill criterion.

Pilot Design

A pilot is production traffic with training wheels: SLOs, traffic shape, shadow or canary in the customer context, and human-in-the-loop escalation that actually pages someone.

The Engineering Problem

Leadership declares "we're in pilot" because fifty champions have UI access. There is no error budget, no shadow comparison, no escalation rota, and cost is someone's personal card. When quality dips, nobody knows whether to roll back the prompt, the index or the model.

Integration Patterns

Customer delivery is ACL-aware RAG, tool calls into customer APIs, routing with cost caps, and guardrails mapped to written policy — all on the Volume 24 platform path, not a side stack.

The Engineering Problem

The FDE wires a notebook to the customer's SharePoint, pastes chunks into a prompt, and calls a public model. It "works" until an ACL miss, a surprise bill, or a policy violation. Integration without forge.rag filters, forge.guard and forge.router is a liability transfer dressed as progress.

RAG over Customer Corpora with ACLs

  • Index build runs in the customer VPC with group claims on each chunk.
  • Filter-before-rank: foreign scopes never enter the prompt (Volume 14 / 24).
  • Freshness: policy documents carry effective_at; stale chunks drop.

Tool Calling, Routing and Guardrails

  • Tools. Order, refund, user-lookup APIs behind forge.harness allow/ask/deny — same as Platform 1.0 agents.
  • Router. Prefer small / cached routes when forge.eval says quality holds; residency tags exclude non-compliant providers.
  • Guards. Map written customer policy IDs to guard rule packs; fail closed on must-never.
Key Idea
  • The FDE's job is to bind customer policy to existing Forge seams, not to invent a parallel middleware for each account.
  • Cost caps belong in the router and ledger, not in a spreadsheet updated weekly.

Change Management

Champions, runbooks and deflection metrics move organisations. Productivity and case claims must carry Documented versus Inferred labels — especially in customer settings where optimism is a sales hazard.

The Engineering Problem

A deck claims "40% productivity lift" citing a famous paper and a two-week champion pilot with no control group. Training was a lunch-and-learn. When results fade, trust dies. The failure was not the model — it was unlabelled inference sold as evidence.

Training Champions and Runbooks

  • Name champions per queue; give them escalation authority and a feedback form that files golden-set candidates.
  • Ship a one-page runbook: when to trust, when to escalate, how to report bad answers.
  • Deflection metrics for support: define in-scope intents; exclude out-of-scope before celebrating.

Documented versus Inferred Claims

Documented (cite primary artefacts)

  • Documented Brynjolfsson et al., 2023 report productivity effects of generative AI in a customer-support setting with measured handling-time changes — cite the paper's population and design, not a slogan.
  • Documented Peng et al., 2023 provide a controlled experiment on Copilot task time — relevant analogy for coding assistants, not automatic proof for ticket deflection.
  • Documented Amershi et al., 2019 publish human–AI interaction guidelines usable in champion training checklists.
  • Documented Your pilot dashboard numbers, when logged with methodology (denominator, intent filter, period).

Inferred (label explicitly)

  • Inferred "We will see the same lift as Brynjolfsson et al. because we also do support" — different tooling, workforce and ticket mix.
  • Inferred Champion smiles in a demo as evidence of production deflection.
  • Inferred Vendor case studies without methodology sections.
Risk
  • Mixing Documented citations with Inferred forecasts in one bullet is how customer trust erodes. Split them visually in every deck.
  • Parnin et al., 2023 (Documented interview study) surface how hard product copilots are to evaluate — use that humility in change management, not as a reason to skip metrics.

Deflection Metrics without Self-Deception

  • Define in-scope intents in the brief; report deflection only on that denominator.
  • Separate "customer abandoned" from "AI resolved" — abandonment is not success.
  • Track reopen rate within 72 h; a silent wrong answer is not deflection.
  • Publish Documented pilot numbers beside any Inferred extrapolation in the same slide — never blended into one big percentage.

Failure Modes of FDE Work

This chapter is deliberately frank. Most failed AI engagements die from process and honesty failures, not from missing a newer model.

The Engineering Problem

After enough customer sites, the same corpses reappear: dazzling demos, vague scope, nobody owning data quality, shadow IT models on personal keys, and security questionnaires answered with screenshots. Naming these modes is how you refuse to repeat them.

Demo-Driven Development

  • Optimising the three champion tickets instead of the golden-set distribution.
  • Hot-fixing prompts in the meeting; never checking them into version control.
  • Hiding guard refusals because they "look bad" in the room.
  • Success criterion = applause. Exit criterion never written.

Countermeasure. Reproducibility pack required before any external demo. Show one deliberate refusal. Tie the next meeting to an exit-criteria diff, not a new feature.

Unbounded Scope

  • "While you're here, also do search, also do agents, also do the mobile app."
  • Exit criteria that grow every week without a kill discussion.
  • Custom one-offs that never become platform ADRs — shadow product engineering.

Countermeasure. K4 in the PoC checklist. Written declines. Configure before build; build only with a path back into platform/ or forge.*.

Unowned Data Quality

  • CSV in email as the system of record.
  • No steward for labels; FDE labels alone; customer disputes later.
  • Indexes rebuilt from memory; stale policy chunks serving as truth.

Countermeasure. Data reality section of the brief; co-owned golden set; freshness metadata; delete paths.

Shadow IT Models

  • Personal API keys in champion browsers.
  • Unregistered models "just for the PoC" that somehow reach production traffic.
  • Copying customer text into public consumer chat tools for "debugging".

Countermeasure. Registry allow-list only; secrets in customer vault; treat consumer-tool paste as a security incident.

Security Theatre

  • Hundred-row questionnaires answered without a threat model.
  • Guards disabled to hit a latency slide.
  • "We'll turn on SSO after the pilot" with production data already flowing.

Countermeasure. Chapter 4 checklists as gates, not appendix. Fail closed. Kill criteria when security blocks measurement indefinitely or when teams demand measurement without controls — both are failure modes.

Frank list — stop the engagement if
  • Decision owner will not name kill criteria.
  • You are asked to bypass ACL "for the demo tenants".
  • Cost is unbounded and nobody will set a router cap.
  • Productivity claims must be presented without Documented/Inferred labels.
  • Handoff is refused because "we'll keep the FDE forever".
  • Demo-driven development without a reproducibility pack.
  • Unbounded scope; exit criteria that only expand.
  • Unowned data quality and solo-labelled golden sets.
  • Shadow IT models and personal API keys.
  • Security theatre; guards off; SSO deferred with real data.
  • Vanity leaderboards replacing customer tasks.
  • Pilot declared without SLOs or on-call.
  • Handoff email without a packet.
  • Inferred productivity lifts sold as documented fact.
  • Building a parallel stack beside platform/.

How These Modes Interact

Demo-driven development invites unbounded scope ("just one more wow"). Unbounded scope starves data ownership. Missing data ownership makes evaluation theatrical, which tempts shadow IT models to "unblock the demo". Shadow IT then collides with security questionnaires answered as theatre. The cure is not a pep talk — it is the brief, kill criteria, co-owned golden set and handoff packet enforced as gates.

Problem

Previous limitation
Anecdotes and lab tasks without large-scale workplace data.
Approach
