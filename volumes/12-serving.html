Serving Requirements

An LLM endpoint looks like any other RPC service until you measure it. A single request lasts seconds, its cost varies by three orders of magnitude with its token counts, and the replica serving it holds per-request state in accelerator memory. This chapter turns product requirements into service-level objectives and a first capacity number.

The Engineering Problem

A product team asks for "a chat API with good latency and high availability". The model team says one H100 does "about 2,400 tokens per second". Neither statement is enough to decide how many GPUs to buy, what the queue limit should be, when to autoscale, or when to page someone. You need SLOs expressed in the units the system actually consumes: tokens, time to first token and time between tokens.

Latency SLOs for Streaming Responses

End-to-end latency is the wrong single metric for a streamed response. Decompose it:

T_{\text{e2e}} = \underbrace{T_{\text{queue}} + T_{\text{prefill}}}_{\text{TTFT}} + (n_{\text{out}} - 1)\cdot \text{TPOT}
  • TTFT (time to first token): queueing plus prefill. Dominated by queue depth and prompt length. This is what users perceive as "responsiveness".
  • TPOT (time per output token, also inter-token latency): one decode step. Dominated by batch size and memory bandwidth. Humans read at roughly 5–10 tokens/s, so a TPOT below ~50 ms is "fast enough" for chat but not for agents that consume the output programmatically.
  • E2E matters for non-streaming callers: agents, tool calls, batch jobs.
  • Goodput: requests per second that meet all latency SLOs. Throughput that violates SLOs is not capacity.
Key Idea
  • Batching trades TPOT for throughput: a bigger batch raises tokens/s per GPU and slows every sequence in it. Capacity is therefore "tokens/s at a TPOT target", measured, never quoted.
  • TTFT is mostly a queueing problem; TPOT is mostly an engine problem. Different teams, different fixes.

From SLOs to a Capacity Plan

Little's law gives the number of requests in flight, which sizes concurrency and therefore KV memory per replica:

L = \lambda W \qquad \text{replicas} = \left\lceil \frac{\lambda \cdot \bar{n}_{\text{out}}}{\text{tok/s per replica at SLO} \cdot (1 - h)} \right\rceil
  • \lambda is the peak arrival rate, W the time in system, and h the headroom you keep for bursts and failover.
  • The error budget is 1 - \text{availability} of requests or minutes per window; it funds releases and experiments (Beyer et al., 2016).
error budget: 43.2 min/month or 15,000 failed requests/month
worst-case in-SLO latency 12.5s -> 250 requests in flight at peak
decode demand 6,000 tok/s -> 4 replicas at 2,400 tok/s, 30% headroom
per-replica concurrency needed: 62 sequences (sizes the KV cache)
  • The replica count is only valid if 2,400 tok/s was measured at 62 concurrent sequences and the TPOT target. At lower concurrency a replica produces fewer tokens/s; at higher concurrency it breaks the TPOT SLO.
  • 62 sequences × (1,500 + 300) tokens is ~110k tokens of KV cache per replica. Check it fits with the Volume 1 formula before trusting the plan.
  • The plan ignores prefill: 20 req/s × 1,500 input tokens is 30k prefill tokens/s, which competes with decode for compute. Measure with the real prompt-length distribution (Chapter 3 load generator).
Common Mistake
  • Publishing an SLO on mean latency. LLM latency is heavy-tailed because output length is heavy-tailed. Use p95/p99 of TTFT and TPOT, and normalise E2E by output tokens when comparing versions.
  • Counting a 200 with a truncated or empty answer as "available". Include finish_reason and a cheap validity check in the success definition.

Rework the plan for a RAG workload with 12,000-token prompts and 150-token answers at the same request rate. Which constraint binds first: decode throughput, prefill throughput or KV memory? What does that imply for the TTFT SLO you can offer?

API Design for LLMs

The API contract outlives every model and engine behind it. The industry has converged on the OpenAI chat-completions shape, so clients, SDKs, gateways and evaluation harnesses work unchanged across providers. This chapter implements that contract precisely, including the parts most teams get wrong: streaming framing, error semantics and idempotency.

The Engineering Problem

Three internal teams call your model. One retries every non-200, including 400s. One cannot tell a rate limit from an outage. One re-sends a "create ticket" agent request after a network timeout and files the ticket twice. None of this is a model problem; all of it is contract.

Possible solutions and what each does not solve

  • Bespoke JSON API: full control, but every SDK, gateway and eval tool needs an adapter.
  • OpenAI-compatible surface: free ecosystem compatibility; does not define idempotency, and its error shapes are under-specified for internal SLOs. You must add both. Documented vLLM, SGLang, TGI, Ollama and llama.cpp each document an OpenAI-compatible HTTP server in their official docs.
  • gRPC: good for internal engine-to-router hops (Documented Triton Inference Server documents both HTTP/REST and gRPC endpoints, and TensorRT-LLM is commonly served through it); poor for browsers and third-party tools. Common pattern: gRPC inside, HTTP+SSE at the edge.

Streaming with Server-Sent Events

  • Why SSE, not WebSockets: the stream is one-way, SSE is plain HTTP (works through proxies, gateways and HTTP/2 multiplexing), and it is what OpenAI-compatible clients expect. WebSockets are justified only for bidirectional sessions (voice, interruptible agents).
  • Framing: each event is data: {json}\n\n. The first chunk carries the role, content chunks carry delta.content, the final chunk carries finish_reason, then data: [DONE]. Documented This is the framing in OpenAI's Chat Completions API reference; Anthropic's Messages API instead documents named events (message_start, content_block_delta, message_stop, periodic ping), so a gateway that fronts both must normalise framing.
  • Errors mid-stream: the status line (200) is already sent. Emit an error event (data: {"error": ...}) and close; clients must check for it. Documented Anthropic's streaming docs state that errors such as overloaded_error can arrive as an error event after a 200. This is why a 200 on a stream is not success.
  • Usage on streams: token counts are only known at the end. Send a final usage chunk (Documented OpenAI's stream_options.include_usage, per its API reference) or bill from server-side logs, never from the client.
  • Proxies: disable response buffering (X-Accel-Buffering: no on nginx), raise idle timeouts above your longest generation, and send comment heartbeats (: ping\n\n) on long reasoning pauses.

Idempotency Keys

A generation is not a side effect, but what an agent does with it often is. Once the network fails after the server has started work, the client cannot know whether it ran.

  • The client generates a UUID per logical operation and reuses it across retries.
  • The server stores key → (request fingerprint, response). A replay with the same body returns the stored response; a different body is a 409; a concurrent duplicate while the first is running is a 409 (or waits on it).
  • Failed attempts are removed so a retry can execute; successful ones are kept for a TTL (24 h is common: Documented Stripe's API docs say idempotency keys may be pruned once they are at least 24 hours old).
  • Streaming requests are not replayed in forge.serve. Replaying a stream needs the whole event log stored; Inferred to our knowledge no major chat API documents idempotent stream replay (check current docs), so agents that need exactly-once semantics should use non-streaming calls for side-effecting steps.
Risk
  • Scope idempotency keys to the authenticated tenant. A global key space lets one tenant read another's stored response by guessing or reusing a key.
  • The idempotency store holds full responses, often with personal data: apply the same retention and encryption rules as conversation logs.

Structured Outputs and Tool Calls in the Contract

  • response_format: {"type": "json_schema", ...} and tools are part of the request contract. The server either enforces them (constrained decoding, Volume 13) or rejects them with a 400. Silently ignoring an unsupported field is the worst option.
  • Tool-call arguments stream as partial JSON fragments in delta.tool_calls. Clients must accumulate and parse at the end; gateways must not attempt to validate partial fragments.
  • Version the contract (/v1) and add fields, never change meanings. Engines differ in which OpenAI fields they honour; your gateway is where you normalise that.

Building a Model Server

Before deploying vLLM or TGI, build the thing they are. A model server is a small amount of HTTP code wrapped around a scheduler, and nearly every production incident lives in the scheduler: unbounded queues, work for clients who have gone, a blocked event loop, a replica that reports healthy while wedged. This chapter builds forge.serve with all four handled, runs it against a real model, and load-tests it.

The Engineering Problem

The obvious server calls model.generate() inside the request handler. It serves one request at a time per worker, blocks the event loop for the whole generation, never batches, keeps generating after the user closes the tab, and under a traffic spike queues requests until every one of them times out. Adding workers multiplies GPU memory, not throughput.

Simple Version Versus Production Version

@app.post("/generate")
def generate(prompt: str):
    return {"text": tok.decode(model.generate(**tok(prompt, return_tensors="pt"))[0])}

Correct for a demo with one user.

  • Handlers only validate, enqueue and stream; one scheduler task owns the model.
  • The scheduler runs a step loop: each iteration admits waiting sequences into free batch slots, runs one batched decode step, and routes each new token to its request's queue (continuous batching, Yu et al., 2022; Volume 11).
  • Bounded admission: a full queue returns 429 with Retry-After immediately.
  • Cancellation: a disconnected stream marks its sequence cancelled; the next step drops it and frees the slot.
  • Deadlines: a sequence whose deadline passed while queued is dropped before it costs a GPU step.
  • Health: liveness checks the scheduler heartbeat; readiness is false during load and drain.
  • The GPU is a single, shared, stateful resource; HTTP concurrency must be decoupled from model concurrency.
  • Asyncio makes it easy to block the event loop by accident: one synchronous forward pass freezes health checks, streaming and admission for every request.
  • Disconnect detection depends on the ASGI server, the proxy chain and whether the response is streaming.

Architecture

The Engine Interface

The scheduler needs one operation: given a batch of token sequences, return the next token for each. Any engine that can do this can join continuous batching at step granularity.

  • HFEngine deliberately has no KV cache so that the scheduler logic stays visible. A production engine keeps a paged KV cache per sequence (Kwon et al., 2023) and the step costs O(1) in sequence length instead of O(T).
  • The fake's cost model (20 ms per step + 1 ms per sequence) captures the fact that matters for scheduling: decode is memory-bound, so adding a sequence to a batch is nearly free until the batch is large.

The Scheduler and the HTTP Layer

Design decisions in this code

  • asyncio.to_thread(engine.step, ...) keeps the event loop free during the forward pass, so health checks, admission and streaming keep working. PyTorch releases the GIL inside kernels. A production engine runs the model in a separate process (vLLM's engine core) and talks to the API process over IPC.
  • Admission counts waiting + running. The limit should come from the SLO: with measured throughput \mu requests/s and a TTFT budget B, a queue longer than about \mu B guarantees that newcomers miss the SLO, so reject them now rather than time them out later.
  • Cancellation via finally: when the client disconnects, Starlette cancels the streaming generator; finally marks the sequence and the scheduler drops it before the next step. Non-streaming requests in this server are not cancelled on disconnect; add a watcher on request.is_disconnected() for that.
  • Deadline from a header (X-Request-Timeout): the caller's remaining budget travels with the request, so the server never spends GPU time on an answer nobody will read (Chapter 9).
  • Incremental detokenisation decodes the full sequence and emits the new suffix. Decoding token by token breaks multi-byte UTF-8 characters and some tokenisers' whitespace rules.
  • Warm-up in lifespan before readiness flips: lazy initialisation (CUDA context, kernel autotuning, graph capture) is paid by the platform, not the first user.

A Load Generator

Most home-grown load tests are closed-loop: N workers each send a request and wait. When the server slows, the workers send less, and the test hides exactly the queueing it was meant to find (coordinated omission). Use open-loop Poisson arrivals at a fixed rate instead.

  • Batch 16 at the same 8 req/s: TTFT p95 72 ms. The same "hardware" serves the load comfortably because each step now produces up to 16 tokens.
  • The knee is between 24 and 40 req/s: throughput grows only 24% while TTFT p95 grows 12×. That is the queueing hockey stick; operate on the left of it.

Implementation Notes
  • Report goodput (requests meeting both TTFT and TPOT SLOs per second), not raw throughput, when comparing configurations.
  • Replay a production prompt- and output-length distribution. A fixed 16-token output hides the head-of-line effects of long generations.
  • Run the generator on a different machine from the server in real tests; here both share one laptop.

Failure Modes

  • Blocking the event loop: a synchronous forward pass or tokeniser call in a handler freezes all streams and makes liveness fail, so Kubernetes restarts a healthy but busy pod.
  • Unbounded queue: every request eventually times out; the replica does 100% work for 0% goodput.
  • Orphaned generations: disconnects not propagated, often because a proxy buffers the stream or keeps the upstream connection open.
  • Readiness tied to load: failing readiness when busy removes capacity exactly when it is needed and can cascade across replicas. Shed with 429 instead.
  • Liveness that loads the model: a probe that runs inference times out under load and triggers restart loops.
  • Multiple uvicorn workers per GPU: each worker loads its own weights; memory doubles and batching halves.

Add a priority field (interactive or batch) and make admission into the running batch prefer interactive sequences. Then add chunked prefill to the fake engine (prefill costs 1 ms per 64 prompt tokens, in chunks of at most 512) and measure the TPOT of running sequences when a 16k-token prompt arrives, with and without chunking.

Production Serving Engines

forge.serve has the right shape and the wrong engine. Production engines keep the same outer loop (admit, step, stream) and replace the inside with paged KV memory, prefix caching, fused kernels, CUDA graphs, quantised weights, speculative decoding and multi-GPU parallelism. This chapter says what each engine abstracts, so you can choose one and know what you still own.

The Engineering Problem

The hand-built server re-runs the whole sequence at each step and holds no KV cache. On a GPU, the gap between it and a tuned engine is one to two orders of magnitude in tokens per GPU-second. Writing that engine yourself is a multi-year project; choosing the wrong one costs months of migration.

Containers for GPU Workloads

A GPU container is an ordinary OCI image with three unusual properties: it depends on a kernel driver it cannot ship, it is often 10–20 GB, and the most important artefact (the weights) is usually too large to belong in it. Those three facts decide your cold-start time, and cold-start time decides your autoscaling and your bill.

The Engineering Problem

Traffic doubles at 09:00. The autoscaler asks for four more replicas. Each needs a GPU node (minutes), a 12 GB image pull, 140 GB of weights, and a warm-up. The replicas are ready at 09:11, after the spike has already burned the error budget.

The CUDA Stack in a Container

  • The driver is on the host; the NVIDIA Container Toolkit injects its user-space libraries and device nodes at run time. The image's CUDA runtime must be supported by that driver (NVIDIA publishes the compatibility matrix).
  • Use -runtime base images for serving; -devel images carry compilers and headers you need only to build kernels. Multi-stage builds keep them out of the final image.
  • PyTorch wheels bundle their own CUDA libraries, so a slim Python base plus the CUDA wheels often works; the nvidia/cuda base is still the safer default for engines with native extensions.

A Dockerfile for GPU Serving

  • One uvicorn worker: the engine owns the GPU; scale with replicas, not workers.
  • Pinned, hashed dependencies: engine versions change numerics and defaults. The image digest plus the weights digest is the deployable unit (Chapter 8).
  • HF_HUB_OFFLINE=1: production pods must never download from the internet at start-up; it is slow, rate-limited and a supply-chain risk.
  • Graceful shutdown longer than your longest generation, so in-flight streams finish during a rollout.

Kubernetes for Model Serving

Kubernetes descends from Borg and Omega (Burns et al., 2016) and was built for fungible CPU containers that start in seconds. Model servers are the opposite: scarce accelerators, minute-long starts, and a load signal that CPU utilisation does not capture. This chapter adapts the standard primitives (scheduling, probes, rollouts, autoscaling) to those facts.

The Engineering Problem

The default HPA scales on CPU. An LLM pod's CPU sits at 30% whether its queue is empty or holds 500 requests, because the work happens on the GPU. The HPA never scales out, and when a node fails, the replacement pod is killed by its liveness probe while it is still loading weights.

GPU Scheduling Primitives

  • Device plugin: the NVIDIA device plugin (usually installed by the GPU Operator, which also manages drivers and the container toolkit) advertises nvidia.com/gpu as an extended resource. GPUs are requested as integers in limits; they are not overcommitted.
  • Node pools, taints and tolerations: GPU nodes are tainted so only GPU workloads land on them; serving pods tolerate the taint and select the GPU type with a node label.
  • Sharing: MIG partitions an A100/H100 into isolated slices; time-slicing and MPS share without isolation. Use MIG for small models with isolation needs; avoid time-slicing for latency SLOs.
  • Multi-GPU and multi-node: tensor parallel within a node needs all GPUs of one pod on one node (and NVLink); multi-node serving uses a leader/worker group (for example the LeaderWorkerSet API) scheduled as a unit.
  • Dynamic Resource Allocation (DRA) is the newer Kubernetes API for describing devices with attributes rather than counts; check your cluster version and vendor support.

Deployment, Probes and Drain

  • startupProbe holds off liveness until the model has loaded. Without it, a liveness probe with a normal timeout kills every replica mid-load, forever.
  • preStop sleep gives kube-proxy and the load balancer time to remove the endpoint before the server stops accepting; the lifespan drain then finishes in-flight streams.
  • maxUnavailable: 0 with maxSurge: 1 needs a spare GPU during rollouts. If GPUs are fully booked, rollouts stall; budget one spare or roll by node pool.

Load Balancing and Gateways

Round-robin is the wrong default for LLMs. The expensive state is the prefix cache on a particular GPU, and the scarce resource is free KV memory, not open TCP connections. This chapter builds LLM-aware routing, then puts rate limits and an API gateway in front of it.

The Engineering Problem

Tenants share long system prompts. Round-robin scatters the same 2,000-token prefix across every replica, so each GPU recomputes it. Least-connections ignores KV headroom: a replica with two long RAG jobs looks "light" on connection count and then OOMs. A multi-region outage needs a policy that fails over without doubling every in-flight stream.

Possible solutions and what each does not solve

  • L4 / connection round-robin: cheap and opaque to HTTP; blind to prefixes and KV.
  • Least outstanding requests: better than round-robin for heterogeneous latency; still ignores prefix locality and KV bytes.
  • Prefix-cache affinity: sticky hash on a prefix fingerprint; needs an overload escape hatch or one hot tenant pins a replica.
  • Least-KV / least-load from engine metrics: balances memory and queue depth; without affinity, cache hit rate collapses.

Why Affinity Matters

A shared system prompt of P tokens that hits the prefix cache costs roughly nothing in prefill; a miss costs a full prefill of P. With T tenants and R replicas, random routing yields a per-replica hit probability that falls as T / R grows past the cache capacity. Affinity maps each prefix to one primary replica so the working set per GPU shrinks by about R.

{'policy': 'least', 'hit_rate': '18.1%', 'prefill_tokens': 906851}
{'policy': 'prefix', 'hit_rate': '58.6%', 'prefill_tokens': 518051}
  • Prefix affinity nearly triples the hit rate and cuts prefill tokens by ~42% versus round-robin on the same tenant mix.
  • Least-in-flight alone is slightly worse for hits: it spreads a tenant across replicas to balance load, which is the opposite of what the cache wants.
  • The escape hatch matters: without it, one chatty tenant pins a replica while others idle; with a threshold of +3 in-flight, affinity yields under overload.
Key Idea
  • Route on a fingerprint of the cacheable prefix (system prompt, tool schemas, RAG template), not the whole prompt and not the TCP connection.
  • Publish per-replica kv_cache_usage and num_requests_waiting; the router’s secondary key is least-KV / least-waiting, not CPU.

Model Registry and Release Management

A model weight file is not a release. Production needs an immutable artefact identity, a promotion path through environments, and traffic controls that can reverse a bad model as quickly as a bad binary. This chapter wires a registry to shadow, canary, blue-green and multi-LoRA serving.

The Engineering Problem

The training job writes checkpoint-48000/ to object storage. Someone copies it to the production mount as llama-8b-latest. Two days later quality drops on one tenant; nobody can say which digest was live, whether the tokenizer matched, or how to put yesterday back without a heroic filesystem revert. Meanwhile three LoRA adapters want to share one base GPU.

Possible solutions and what each does not solve

  • Mutable “latest” pointers: convenient; forbids audit, rollback and digests.
  • MLflow / custom registry with content digests: immutable versions; still need a traffic plane to promote them safely.
  • Shadow only: measures the candidate on live inputs without user impact; does not prove the serving path under real load split.
  • Canary / blue-green: expose users gradually or cut over by environment; need automated rollback gates or you are doing hope-driven ops.

Reliability

LLM calls are long, non-idempotent by default, and expensive to retry. Timeouts, retries, circuit breakers, fallbacks and load shedding are not optional middleware — they are how you keep a few bad GPUs from taking down the product. This chapter finishes the resilience story Volume 1 started with ResilientClient.

The Engineering Problem

One replica’s GPU driver wedges. Clients time out at 60 s, retry immediately, and pile onto the remaining replicas. TTFT blows the SLO, the autoscaler adds cold pods that are not ready for three minutes, and the on-call discovers that “retry on any error” also retried a successful side-effecting tool call twice. Availability is now worse than if the first replica had simply been removed.

Possible solutions and what each does not solve

  • Longer timeouts: fewer false timeouts; worse queueing under load (holds capacity).
  • Retries with backoff: survive blips; amplify outages unless bounded, jittered and idempotent.
  • Circuit breakers: stop sending to a sick dependency; need half-open probes and a fallback path.
  • Load shedding / admission control: protect goodput for what you can serve; users see fast 503s instead of slow death.
  • Graceful degradation: smaller model, shorter max_tokens, cached answer, or “try again”; product must define what “degraded” means.

Deadlines, Retries and Idempotency

  • Propagate a single deadline (budget) from gateway → router → engine; each hop checks remaining time. A 60 s client timeout with three 60 s server attempts is a 3-minute outage amplifier.
  • Retry only retryable failures: 408/429/502/503/504, connection errors. Never retry 400 validation errors.
  • Require Idempotency-Key (Chapter 2) for any retry that could have reached the server; replays must return the cached completion, not a second generation.
  • Use exponential backoff with full jitter; cap attempts (typically 2–3 for interactive chat).
Key Idea
  • Goodput under overload beats raw availability: a fast refusal preserves the replicas that are still healthy.
  • The circuit breaker protects the caller and the rest of the fleet; load shedding protects a single server’s queue.

Cloud Architecture Patterns

The same model can be a metered API call, a always-on GPU Deployment, or a scale-to-zero serverless worker. The right shape depends on traffic, latency SLO, data residency and how much operational load you will own. This chapter compares the patterns and finds the cost crossover with honest utilisation assumptions.

The Engineering Problem

Finance asks whether to “just use the hosted API” or “buy H100s”. Engineering quotes peak tokens per second; finance multiplies by the list GPU price and 720 hours. Both numbers are wrong: hosted bills tokens you actually use, self-hosted bills GPUs you keep warm, and serverless bills a chilly middle that still pays cold starts on every diurnal trough.

Possible solutions and what each does not solve

  • Managed model API (OpenAI-compatible hosted): minimal ops, strong peak elasticity; data leaves your boundary, unit economics worsen at steady high volume, limited runtime control.
  • Self-hosted on GPUs (GKE/EKS/AKS, bare metal): full control, better $/token at high utilisation; you own drivers, pages, and cold starts.
  • Serverless GPUs (scale-to-zero containers): pay for use; cold starts of tens of seconds break interactive TTFT unless you keep a warm floor.
  • Hybrid: self-host the fat steady workload; burst to managed or another region; route with the Chapter 7/9 machinery.

Review and Next Steps

What You Learned

  • LLM endpoints are token- and KV-shaped systems: SLOs split into TTFT and TPOT, capacity follows Little’s law, and goodput under SLO is the only throughput that counts.
  • The OpenAI-compatible chat contract (SSE, error taxonomy, idempotency) outlives any engine; backpressure and cancellation belong in the server, not only in the client.
  • Production engines (vLLM, SGLang, TGI, TensorRT-LLM, Triton, Ollama, llama.cpp) package continuous batching and paged KV; you still own the API, probes and rollout.
  • GPU containers and Kubernetes need startup probes, weight caching, queue-depth autoscaling and disruption budgets — CPU utilisation is the wrong signal.
  • Load balancing for LLMs is prefix-cache affinity plus least-KV, with token-aware rate limits and careful multi-region failover.
  • Releases are immutable artefacts promoted through shadow, sticky canary and blue-green with automated non-inferiority rollback; multi-LoRA shares one base.
  • Reliability is deadlines, idempotent retries, circuit breakers, priority shedding and an explicit degradation ladder.
  • Managed, self-hosted and serverless GPUs cross over on utilisation and cold-start tax; reserved versus spot is a reliability choice as much as a price choice.

Important Architecture

Failure Modes

  • SLOs stated as average latency; no separate TTFT and TPOT targets; throughput reported without an SLO.
  • Closed-loop load tests that hide queueing collapse (coordinated omission).
  • No backpressure: an unbounded queue turns overload into timeouts for everyone instead of fast 429s for some.
  • Client disconnects not propagated, so cancelled streams keep consuming KV and decode slots.
  • Retries without idempotency keys or jitter; retry storms amplifying a partial outage.
  • Autoscaling on CPU or GPU utilisation instead of queue depth and KV pressure; scale-up slower than the traffic ramp because of cold starts.
  • Readiness probes that pass before weights are loaded and warmed; liveness probes that kill replicas during long prefills.
  • Round-robin load balancing that destroys prefix-cache hit rate.
  • Mutable model tags ("latest") in production; canaries without stickiness or without a quality guardrail; no tested rollback.
  • Spot capacity for latency-critical traffic without a fallback pool.

Evaluation

  • Evaluate the service against its SLO, not the model in isolation: open-loop load tests at 50%, 100% and 150% of forecast peak, reporting TTFT and TPOT percentiles, goodput, error rate by class and cost per million tokens.
  • Every release candidate passes the Volume 10 offline gate first, then shadow traffic comparison, then a sticky canary with pre-registered non-inferiority thresholds on task success, TTFT p95 and error rate. Rollback must be automatic when a guardrail fires.
  • Test the failure paths explicitly: kill a replica mid-stream, exhaust KV, drop the network to a provider, cancel 20% of streams, and assert that the observed behaviour matches the degradation ladder (shed, degrade, fail over) rather than timing out.
  • Contract tests for the API: schema validation, SSE framing, error codes and idempotent replay are checked against both forge.serve and any external engine you put behind the same contract.
  • Track operational metrics over time: cold-start duration, time to scale, prefix-cache hit rate and cost per successful request. Regressions in any of them are release blockers, like quality regressions.
