The Modern AI Landscape

Modern AI engineering is not "machine learning with bigger models". The unit of work changed: instead of training one model per task, engineers adapt one general model and build systems around it. This chapter explains how that happened and what it changes for you.

The Engineering Problem

Until roughly 2018, every language task needed its own labelled dataset, its own model and its own training pipeline. A company with 40 text problems ran 40 ML projects. Each was expensive to label, brittle outside its training distribution, and impossible to extend without retraining.

What changed

  • Self-supervised pretraining on raw text removed the labelling bottleneck: the label is simply the next token.
  • The Transformer made that pretraining parallelisable on GPUs at enormous scale.
  • Scale (parameters, data, compute) produced models that perform many tasks from instructions alone.
  • Post-training (instruction tuning, preference optimisation) turned raw text predictors into usable assistants.
  • Tool use and agents let models act: call APIs, run code, retrieve documents.

A Short Technical History

The path to foundation models is a sequence of engineering shifts, not a single invention:

  1. Statistical NLP (pre-2013): n-grams, HMMs, feature-engineered classifiers. Strong on narrow tasks; brittle outside their feature set.
  2. Deep learning: end-to-end neural models replace hand-crafted features.
  3. Pretraining: learn representations (then full models) from raw text once; adapt per task.
  4. Foundation models → assistants → agents: one general model, then instruction-following, then tool-using loops.

Key Idea
  • The paradigm shifted from one model per task to one foundation model, many systems.
  • Most engineering effort moved from model architecture to data, evaluation, inference cost and the system around the model.
  • Model capability keeps moving; the engineering disciplines in this book (evaluation, serving, retrieval, guardrails, routing) stay.
  • The Bitter Lesson (Sutton, 2019): methods that leverage computation and general learning consistently beat hand-crafted specialisation, given enough scale. Modern AI engineering is that lesson applied to systems around foundation models.

The Capability Frontier and How It Is Measured

  • Benchmarks measure narrow skills: knowledge (MMLU), graduate science (GPQA), code (HumanEval, SWE-bench), maths, instruction following.
  • Saturation: a benchmark stops discriminating once top models reach its noise ceiling. The field then creates harder ones.
  • Contamination: benchmark questions leak into web-scale training data, inflating scores (Volume 5).
  • Human preference arenas rank models by pairwise votes; they measure what users prefer, which is not the same as correctness.
  • "Emergent" abilities: some tasks appear to jump suddenly with scale. Part of this effect comes from discontinuous metrics such as exact match; smooth metrics often show gradual improvement (Wei et al., 2022; Schaeffer et al., 2023).
Engineering Rule
  • Public benchmark scores tell you which models to try. Only your own evaluation set tells you which model to ship.

Open-Weight Versus Closed Models

Open-weight (Llama, Qwen, Mistral, DeepSeek, Gemma …)

  • Run anywhere: laptop, on-premises, any cloud.
  • Full control: fine-tuning, quantisation, inspection of logits.
  • Data never leaves your infrastructure.
  • Predictable cost at high volume.

Closed / hosted API (GPT, Claude, Gemini …)

  • Usually the strongest capability at any given time.
  • Zero infrastructure; pay per token.
  • Provider handles safety layers, scaling and upgrades.
  • Less control: model versions change or are retired; limited customisation.
Practical Default
  • Prototype with the strongest hosted model to find out whether the task is solvable at all.
  • Build the evaluation set during the prototype.
  • Then use the evaluation set to test whether a cheaper or self-hosted model is good enough (Volume 18, routing).

  • Each arrow is a trust boundary: licences, data provenance, safety behaviour and known weaknesses propagate downwards.

Precise Terminology

Teams waste weeks because "agent", "model" and "platform" mean different things to different people. This book uses each term exactly as defined here.

Why Precision Matters

A product manager asks for "an AI agent". One engineer builds a fixed three-step pipeline, another builds an autonomous loop with tool access. The first is cheap and predictable; the second needs permissions, budgets, sandboxing and trajectory evaluation. Same words, different system, different risk.

Workflow Versus Agent in Code

The clearest way to separate the two terms is to look at who owns the loop. Both examples use a ScriptedModel, a deterministic fake that returns pre-written replies. Fakes like this let us test system logic without network access or API keys (Chapter 8).

agent:    Order 42 was double-charged; refund issued.

What the code shows

  • In the workflow the number of model calls is fixed (two). Cost and latency are predictable.
  • In the agent the number of calls depends on the model's choices. You need a step budget (max_steps), and in production also token, cost and time budgets.
  • The agent executes whatever tool name the model emits. A production system needs a tool runtime that validates arguments and a permission policy. That is the job of the harness (Volume 16).
Decision Rule
  • Use a workflow when you can write the steps down in advance. This covers most production use cases.
  • Use an agent only when the steps depend on information discovered during execution and cannot be enumerated.
  • Agency costs you predictability, latency, money and safety surface. Spend it deliberately.

How an LLM Works: an Engineer's Overview

An LLM is a function from a sequence of token IDs to a probability distribution over the next token, applied repeatedly. Everything else (chat, tools, reasoning) is built on that loop. This chapter walks through the loop on a real model and implements sampling from scratch.

The End-to-End Pipeline

  1. Tokeniser splits text into sub-word units and maps each to an integer ID (Volume 3).
  2. Embedding turns each ID into a vector of size d_{\text{model}}.
  3. Transformer blocks mix information across positions (attention) and transform each position (MLP), L times (Volume 2).
  4. LM head projects the last position's vector to V scores, one per vocabulary entry (the logits).
  5. Sampling converts logits to a probability distribution and picks one token.
  6. The token is appended to the input and the loop repeats until a stop token or a length limit.

The Mathematics in Four Equations

1. Language modelling factorises the probability of a sequence

p(x_1, \dots, x_T) = \prod_{t=1}^{T} p_\theta(x_t \mid x_{<t})
  • The model p_\theta only ever predicts the next token given all previous ones. A "causal" or "autoregressive" model is one that factorises this way.

2. Softmax turns logits into probabilities

p_\theta(x_t = i \mid x_{<t}) = \frac{\exp(z_i / \tau)}{\sum_{j=1}^{V} \exp(z_j / \tau)}
  • z \in \mathbb{R}^V are the logits and \tau is the sampling temperature (\tau = 1 in training).

3. Training minimises cross-entropy (negative log-likelihood)

\mathcal{L}(\theta) = -\frac{1}{T} \sum_{t=1}^{T} \log p_\theta(x_t \mid x_{<t})
  • Measured in nats per token. Every position in every training sequence is a training example, which is why pretraining needs no labels.

4. Perplexity is the exponentiated loss

\text{PPL} = \exp(\mathcal{L})
  • Intuition: a perplexity of 10 means the model is, on average, as uncertain as a uniform choice among 10 tokens.
  • Perplexity is only comparable between models that use the same tokeniser. Different tokenisers split text differently, so loss per token is not comparable. Use bits per byte instead (Volume 3).

What the output teaches

  • Tokens are not words. Ġ marks a leading space in byte-level BPE, so " France" and "France" are different tokens.
  • The model outputs logits for every position (shape (1, 5, 49152)). Training uses all 5 positions; generation uses only the last.
  • The most likely continuation is " the", not " Paris". A base model predicts plausible text ("…is the city of Paris"), not the answer to a question. Answering questions directly is taught by post-training (Volume 8).
  • " Paris" gets only 9.4%. Small models spread probability widely; that is why sampling settings matter.
Key Idea
  • An LLM is a conditional probability distribution over the next token. It is not a database lookup, not a program interpreter and not a reasoning engine with guaranteed correctness.
  • Facts, reasoning and style all emerge from next-token prediction, and so do hallucinations, when the most plausible text is not the true text.

Sampling from Scratch

The model gives a distribution; the decoding strategy picks a token from it. Decoding has no learned parameters, yet it changes output quality dramatically.

  • At \tau = 0.5 the top token takes 83% of samples; at \tau = 2 the distribution flattens and the worst token rises from 3% to 8%.
  • Top-p = 0.8 keeps three tokens because 0.559 + 0.205 = 0.764 < 0.8, so a third token is needed to cross the threshold.
Trade-off
  • Greedy decoding is deterministic but can loop and repeat itself on long outputs.
  • High temperature increases diversity and error rate. For factual tasks, lower temperature is usually better; for brainstorming or sampling many candidates (Volume 9), higher is better.
  • \tau = 0 on a hosted API is usually not perfectly deterministic: batched GPU arithmetic and serving changes introduce small differences.

Chat Is a Text Format

An assistant has no separate "chat mode". A chat template serialises roles into a single token sequence using special tokens, and the model continues it.

  • The model generates until it emits <|im_end|>, the stop token.
  • System prompts, tool definitions, tool results and retrieved documents are all just text inside this sequence. That is why prompt injection is possible: data and instructions share one channel (Volume 17).
  • Using the wrong template for a model silently degrades quality. Always use the tokenizer's own apply_chat_template.

Prefill and Decode: Why Output Tokens Cost More

  • Prefill: the whole prompt is processed in one parallel forward pass. This phase is compute-bound and fast per token.
  • Decode: output tokens are generated one at a time, and each step reads all model weights from GPU memory. This phase is memory-bandwidth-bound and slow per token.
  • The KV cache stores each layer's keys and values for previous tokens so decode does not recompute them (Chapter 4, Volume 11).
  • This is why hosted APIs price output tokens several times higher than input tokens, and why latency is reported as time to first token (prefill) plus time per output token (decode).

What an LLM Is Not

  • Not a database: knowledge is compressed and lossy, frozen at the training cut-off, and cannot be updated by editing a row. Use retrieval (Volume 14).
  • Not a calculator: arithmetic is pattern-matched over tokens. Use tools (Volume 15).
  • Not deterministic by default: sampling is stochastic, and serving introduces numeric noise.
  • Not self-aware of its errors: confidence in the text is not calibrated probability of correctness (Volume 18).
  • Not a security boundary: instructions in the prompt can be overridden by other text in the prompt.

Compute, Memory and Cost Arithmetic

Almost every AI engineering decision reduces to four numbers: parameters, FLOPs, bytes and bandwidth. An engineer who can estimate them on paper can check vendor claims, size hardware, predict latency and price a feature before writing any serving code.

The Engineering Problem

Your team wants to self-host an 8B-parameter model for a chat feature with 8k-token conversations. Questions arrive immediately. Will it fit on one GPU? How many users can it serve at once? What is the latency per token? Is it cheaper than a hosted API? Could we fine-tune it on the same GPU? All of these can be answered in five minutes with the formulas in this chapter.

Counting Parameters

A modern decoder-only Transformer (Llama-style: RMSNorm, grouped-query attention, SwiGLU MLP) with vocabulary V, width d, L layers, h_{kv} key/value heads of size d_h and MLP width d_{ff} has:

N \approx \underbrace{V d}_{\text{embedding}} + L\Big(\underbrace{2d^2 + 2\,d\,h_{kv} d_h}_{\text{attention}} + \underbrace{3\,d\,d_{ff}}_{\text{SwiGLU MLP}}\Big) + \underbrace{V d}_{\text{LM head (if untied)}}
  • Attention: W_Q, W_O are d \times d; W_K, W_V are d \times h_{kv} d_h, which is smaller than d \times d under GQA.
  • SwiGLU has three matrices (gate, up, down) instead of two.
  • Norm weights and biases are negligible (< 0.01% of parameters).
  • For large models, the MLP holds roughly two-thirds of the non-embedding parameters.

Counting FLOPs

  • A matrix–vector product with an m \times n matrix costs 2mn FLOPs (one multiply and one add per weight).
  • Therefore a forward pass costs about 2N FLOPs per token, plus attention over the context, which is small unless the context is very long.
  • The backward pass costs about twice the forward pass, so training costs about 6N FLOPs per token.
C_{\text{train}} \approx 6 N D \qquad C_{\text{infer}} \approx 2 N \text{ per generated token}

Here D is the number of training tokens. This one formula underpins the scaling laws in Volume 6.

Inference memory

M_{\text{infer}} \approx \underbrace{N \cdot b_w}_{\text{weights}} + \underbrace{B \cdot S \cdot 2 L\, h_{kv}\, d_h\, b_{kv}}_{\text{KV cache}} + \text{activations and overhead}
  • B is the number of concurrent sequences, S the tokens per sequence, and b the bytes per value.
  • The factor 2 counts keys and values. The KV cache grows linearly with both batch size and context length, and it is what limits concurrency on a GPU.

Training memory

Mixed-precision training with Adam keeps, per parameter (Rajbhandari et al., 2019):

  • BF16 weights (2 bytes) and BF16 gradients (2 bytes).
  • An FP32 master copy of the weights (4 bytes).
  • Adam first and second moments in FP32 (4 + 4 bytes).
  • That totals 16 bytes per parameter before activations. Activations depend on batch size and sequence length and are reduced by activation checkpointing (Volume 6).

Bandwidth and the Roofline

A GPU can be limited either by arithmetic (FLOP/s) or by moving data from memory (bytes/s). The arithmetic intensity of a workload decides which:

I = \frac{\text{FLOPs performed}}{\text{bytes moved}} \qquad \text{attainable FLOP/s} = \min\big(\text{peak FLOP/s},\; I \times \text{bandwidth}\big)
  • An H100 SXM offers about 989 TFLOP/s of dense BF16 compute and 3.35 TB/s of HBM bandwidth Documented (NVIDIA datasheet). The ridge point is therefore 989e12 / 3.35e12 ≈ 295 FLOPs per byte.
  • Decode at batch size 1: each 2-byte weight is read once to do 2 FLOPs, so I \approx 1. This is far below 295, which makes decode memory-bound: the GPU's compute sits mostly idle.
  • Batching B sequences reuses each weight read B times, so I \approx B. That is why batching raises throughput almost for free until the workload becomes compute-bound or the KV cache fills memory.
  • Prefill processes many tokens per weight read and is usually compute-bound.

Reading the Numbers: The 8B Model Problem Answered

  • Correctness check. The calculator gives 8.03B parameters, matching Meta's published size for Llama 3 8B Documented. Always validate an estimator against a known model before trusting it.
  • Does it fit? Weights take 16 GB. On an 80 GB GPU that leaves about 60 GB for KV cache, which is about 60 sequences of 8k tokens at 1 GiB each. That KV budget is the real concurrency limit.
  • Can we fully fine-tune it on one GPU? No: the 128 GB of training state exceeds 80 GB before activations are counted. Options are sharding across GPUs (Volume 6) or LoRA and QLoRA (Volume 8).
  • Latency. Decode is capped at about 209 tokens/s per sequence even at batch 1. Real systems reach perhaps 60–80% of that bound.
  • Cost. The same GPU costs $4.00 or $0.33 per million tokens depending on batching. Utilisation is the cost lever (Volumes 11–12).
  • Training estimate versus reality. Meta's model card reports about 1.3M H100 GPU-hours for Llama 3 8B Documented, 2.6× our 40%-MFU estimate. The gap plausibly comes from lower sustained utilisation, failures and restarts, evaluation runs and experiments Inferred. Treat 6ND as a lower bound.
Assumptions to State Every Time
  • GPU price ($3/hour here) varies by several times across providers, commitment levels and regions.
  • Utilisation (MFU) for large training runs is typically 30–50%; for naive code it can be under 10%.
  • Throughput under batching depends on prompt and output lengths. Always measure (Volume 11).
Beyond This Chapter
  • Attention FLOPs grow as O(S^2), so for very long contexts the 2N rule underestimates prefill cost.
  • Mixture-of-experts models activate only part of N per token. Compute follows the active parameters, but memory must hold all of them (Volume 7).

The AI Model Lifecycle

A model is not a file. It is the output of a pipeline of data, code, configuration and compute, and it must be reproducible, comparable, auditable and replaceable. This chapter defines the lifecycle and the artefacts each stage must produce.

The Engineering Problem

Six months after release, users report that the model has become worse at invoices. Nobody can say which dataset version trained the production model, which evaluation it passed, or what changed since. Rolling back is impossible because the previous checkpoint was overwritten. Every one of these failures is a missing lifecycle artefact.

Lineage in Practice: An Artefact Manifest

The smallest useful unit of model governance is a manifest written next to every checkpoint. It links the weights to the exact data, code and configuration that produced them.

{'train.jsonl': '7cda9ec1f0842184c2f10f1b056ef625e75a4749c94b594d0a70c9eda7553262'}
  • Content hashes, not file names. train_final_v2.jsonl says nothing; a SHA-256 hash changes whenever a single byte changes.
  • Parent pointer. Fine-tuned models form a tree. When a base model is found to have a problem, you can find every descendant.
  • Production version. Registries such as MLflow and Weights & Biases store the same information with UI, permissions and APIs (Volumes 12 and 23). Understand the manifest first; the tool is just storage.

Model Cards

  • Intended use and out-of-scope use. For example: "English invoice fields, not legal advice".
  • Training data summary and known gaps (languages, domains).
  • Evaluation results with dataset versions, confidence intervals, and slices by segment.
  • Known failure modes and safety evaluation.
  • Operational characteristics: size, memory, latency, cost per 1k requests.

Risk
  • A hosted model alias such as "latest" can change behaviour under you. Pin explicit model versions in production and re-run your evaluation suite before upgrading.
  • Training data is a security asset. Poisoned or leaked data propagates into every descendant model (Volumes 5 and 17).

Retraining Triggers

  • Scheduled: knowledge freshness, for example a monthly continued-pretraining or re-indexing job.
  • Metric-triggered: quality on a monitored slice drops below a threshold.
  • Data-triggered: enough new labelled production failures have accumulated.
  • Upstream-triggered: a better or cheaper base model is released and passes your evaluation.
  • Evaluation data leaks into training data, so offline scores rise while production quality does not.
  • Checkpoints are overwritten, so rollback is impossible.
  • The serving stack uses a different tokeniser version or chat template than training, a silent quality drop.

The AI Product Lifecycle

The model lifecycle asks "is the model good?". The product lifecycle asks "does this solve the user's problem at an acceptable cost and risk?". Most failed AI projects failed on the second question.

The Engineering Problem

A team spends three months building an LLM-based document router. It reaches 81% accuracy. Then someone notices that a keyword rules engine written in an afternoon reaches 71%, and the business needed 95% to remove the human reviewer. The project never had a baseline, a target or an evaluation set, so nobody could say whether it was succeeding.

Defining Success

  • Task metric: accuracy, exact match, task completion, pass rate.
  • Quality metric: faithfulness, helpfulness rubric, human preference.
  • Operational: p50/p95 latency, time to first token, availability.
  • Cost: dollars per request and per successful task. A cheap model that fails often is expensive per success.
  • Safety: policy violation rate, PII leakage, unauthorised actions.
  • Business: deflection rate, time saved, conversion. This is what the product is for.

Implementation: Comparing Against a Baseline Properly

Two systems evaluated on the same 200 examples. The question is not "which number is higher" but "is the difference larger than the noise from our limited sample?". The bootstrap resamples the evaluation set to estimate that noise.

baseline  accuracy 0.710  95% CI [0.645, 0.770]
candidate accuracy 0.815  95% CI [0.760, 0.870]
p(candidate not better) = 0.0000
  • The two confidence intervals overlap, yet the paired test is decisive. Pairing removes per-example difficulty, which is the dominant source of variance. Always compare systems on the same examples with a paired test.
  • With 200 examples, a 95% interval is about ±6 points wide. To detect a 2-point improvement you need thousands of examples, or a paired design (Volume 10).
  • The candidate is 10 points better, but still 13 points short of a 95% business target. The decision is "rescope or keep human review", not "ship".
Trade-off
  • A small, carefully labelled evaluation set is worth more than a large noisy one, but it has wide confidence intervals. Grow it continuously from production failures.
  • Demo-driven development: five impressive examples, no evaluation set.
  • Measuring model quality but not cost per successful task.
  • Evaluating on synthetic examples that do not resemble real traffic.
  • No human fallback for the error rate that remains.

Pick a real task from your work. Write the problem frame (user, task, success metric, target, cost ceiling, worst-case failure). Build a deterministic baseline in under two hours and label 50 examples. You now have the start of every AI project in this book.

Anatomy of a Production AI System

The model is typically a small part of the code in a production AI system. This chapter presents the reference architecture used throughout the book, first as a high-level design (HLD), then as a low-level design (LLD) with runnable code.

Simple Version Versus Production Version

answer = client.chat(model="some-model", messages=[{"role": "user", "content": question}])

One call to a model API. Correct for a prototype.

The same question passes through authentication, rate limiting, input guardrails, context assembly (conversation history, retrieved documents, tool definitions), a router, a model adapter with retries and timeouts, tool execution, output guardrails, logging, tracing, cost accounting and evaluation sampling.

  • Models fail: rate limits, timeouts and overloads are routine, not exceptional.
  • Models are wrong: outputs need validation, and some need human approval.
  • Models are attackable: every piece of text in the context is a potential instruction.
  • Models are expensive: every token must be attributed, budgeted and optimised.
  • Models are opaque: without traces you cannot debug why an answer was produced.

Low-Level Design: The Model Boundary

The most important LLD decision is a single, narrow interface between your system and any model. Everything above it (routing, caching, retries, evaluation) works for local, open-weight and hosted models alike, and tests can substitute a deterministic fake. In Forge this lives as forge.models.

Design decisions in this code

  • Frozen request and response types are hashable and loggable, and they give you an exact record of what was sent.
  • Only transient errors are retried. Retrying a 400 (bad request) or a content-policy refusal wastes money and time.
  • Exponential backoff with jitter prevents thousands of clients retrying in lock-step after an outage.
  • Only deterministic requests are cached. Caching a sampled answer would silently remove diversity the caller asked for.
  • Token counts in the response feed cost accounting from day one.
What Production Adds
  • Idempotency keys for requests that trigger actions, so a retry never double-charges a customer.
  • An overall deadline across all attempts, not only a per-attempt timeout.
  • Circuit breakers and fallback models when a provider is down (Volume 18).
  • Streaming responses, and cancellation when the user disconnects (Volume 12).
Risk
  • Cache keys must include the tenant and user permissions whenever the context contains private data. Otherwise one user's answer can be served to another.

Systematic Improvement: Classify Before You Fix

When an output is wrong, "use a bigger model" is the most expensive and least informative fix. First classify the failure.

Diagnostic questions for classifying a failure.
QuestionIf yes
Was the information needed for the answer present in the context?No → retrieval or context problem
Would a careful human give the right answer from this exact context?No → instructions or context are ambiguous
Does a stronger model answer correctly with the same context?Yes → capability problem: route, fine-tune or distil
Did the model call the wrong tool or wrong arguments?Tool description, schema or examples problem
Is the answer right but in the wrong format?Structured output or schema-validation problem

Add a deadline_s to ResilientClient so that the sum of all attempts and back-off sleeps never exceeds it. Write a test with a ScriptedModel that fails five times, and assert that the call raises within the deadline.

Engineering Environment and the Forge Repository

AI code fails in ways ordinary code does not: results change between runs, bugs show up as slightly worse numbers rather than exceptions, and generated code looks right while being subtly wrong. This chapter sets the habits—and the Forge package layout—the rest of the book relies on.

The Engineering Problem

A training change improves validation loss from 2.31 to 2.28. Is the change real, or noise from a different random seed? The run cannot be repeated because the environment drifted: a library upgraded and a data file was edited in place. Without reproducibility, every experiment result is an anecdote.

Project Layout: the Forge Repository

  • Configuration is data: hyperparameters live in versioned config files, not in code edits.
  • Scripts are thin: logic lives in the importable forge package, so tests can reach it.
  • Lock files: uv lock (or pip-tools) pins every transitive dependency. Numerical results can change between library versions.

Seeds, Typed Config and Structured Logging (forge.core)

same seed, same tensor: True
4 log lines
Why Typed Config
  • A plain dict silently accepts typos ("lrr"). A frozen dataclass rejects unknown fields at the boundary and documents every knob the run used.
  • Load YAML/TOML into a mapping, then TrainConfig.from_mapping. The file is versioned; the type is enforced in code.
Limits of Determinism
  • Seeds make runs repeatable on the same hardware, software and batch composition, not across GPU models or library versions.
  • Hosted model APIs are generally not bit-reproducible even at temperature 0.
  • The right response is statistical: run several seeds and report the mean and spread. A 0.03 improvement in loss is meaningless if the seed-to-seed spread is 0.05.

AI-Assisted Development: First Principles

You will use AI coding assistants throughout this book. The goal is to become a better engineer with them, not to accept code you have not verified. Volume 23 covers this in depth; these are the rules from day one.

What an agent instructions file (AGENTS.md / CLAUDE.md) should contain

  • How to install, run, test and lint the project: exact commands.
  • Architecture overview and where things live.
  • Conventions: naming, typing, shape comments, error handling.
  • Hard rules: never commit secrets, never disable tests, never add dependencies without asking.
Verify Generated Code
  • Dependencies: assistants can suggest packages that do not exist. Attackers register such names ("slopsquatting"). Check every new dependency on the package index before installing it.
  • Numerics: a plausible-looking attention function with a wrong transpose still runs. Only a reference comparison test catches it.
  • Security: check for injection, unsafe deserialisation (pickle, torch.load on untrusted files), hard-coded secrets and overly broad permissions.
  • Results that cannot be reproduced because data was edited in place.
  • Comparing two runs with different seeds and calling the difference an improvement.
  • Tests that call a live model API: slow, flaky, costly and non-deterministic.
  • Accepting generated code that passes the tests it wrote for itself.

Train any small model (for example logistic regression on synthetic data) with five seeds. Report the mean and standard deviation of the final metric. Then change one hyperparameter and decide, with a paired comparison across seeds, whether the change is real.

Volume Review

What You Learned

  • Modern AI engineering adapts one foundation model and builds a system around it, instead of training one model per task.
  • Precise meanings of AI, ML, DL, generative AI, foundation model, LLM, SLM, multimodal model, workflow, agent, agentic system, framework, harness, orchestrator, tool runtime, guardrail, evaluation system and platform.
  • An LLM is a next-token probability distribution: tokens → embeddings → Transformer → logits → sampling, repeated autoregressively.
  • Training minimises cross-entropy; perplexity is exp(loss) and is comparable only with the same tokeniser.
  • Decoding controls (temperature, top-k, top-p) trade diversity against error rate.
  • Prefill is compute-bound; decode is memory-bandwidth-bound; batching is the main cost lever.
  • Estimation formulas: parameters, 2N/6N FLOPs, 16 bytes per parameter for Adam training, KV cache per token, the roofline and cost per million tokens.
  • The model lifecycle is a loop that needs versioned artefacts; the product lifecycle starts from a problem frame, a baseline and an evaluation set.
  • Build versus buy (hosted vs self-host) is separate from how you adapt (prompt, RAG, tools, fine-tune, route).
  • Failures must be classified as model problems or system problems before they are fixed.
  • Forge starts here: forge.compute, forge.core and forge.models seed the continuous package.

Important Architecture

Failure Modes

  • Treating the model as a database, a calculator or a security boundary.
  • Choosing a model from public benchmarks instead of your own evaluation set.
  • Building an agent where a workflow would do.
  • Ignoring the KV cache when sizing hardware; ignoring utilisation when estimating cost.
  • Unpinned model versions, overwritten checkpoints, unversioned prompts.
  • Comparing systems without paired tests or confidence intervals.
  • Fixing system failures by upgrading the model.

Evaluation

  • Define success before building: task, quality, latency, cost, safety and business metrics.
  • Start with a deterministic baseline and 50–500 labelled real examples.
  • Report confidence intervals; compare systems with paired tests on identical examples.
  • Measure cost per successful task, not cost per request.
  • Grow the evaluation set continuously from production failures.

Practical Project

Choose a real feature, for example "answer questions over our internal documentation" with 2,000 daily users. Deliver:

  1. A problem frame with success metrics and targets.
  2. Capacity estimates with the calculator for two candidate open-weight models: memory, concurrency, tokens per second.
  3. A cost comparison of self-hosting versus a hosted API at your expected token volume, with every assumption stated.
  4. An HLD diagram marking which components you need on day one and which can wait.
  5. An evaluation plan: dataset, metrics, baseline, and the paired test you will use.

Exercises

  1. Prove that softmax is invariant to adding a constant to all logits, and explain why implementations subtract the maximum.
  2. Show that \tau \to 0 recovers greedy decoding and \tau \to \infty gives a uniform distribution.
  3. Derive the KV-cache size for MHA versus GQA with 8 KV heads for the Llama 3 8B shape. What concurrency does GQA buy on an 80 GB GPU at 8k tokens?
  4. Compute the arithmetic intensity of batched decode at batch sizes 1, 16 and 256. At which batch size does an H100 become compute-bound, ignoring KV-cache reads?
  5. Decide build versus buy for a documentation Q&A feature at 2,000 daily users. State residency, cost and ops constraints that flip the choice.
  6. Extend ResilientClient with a circuit breaker that stops calling a model after 5 consecutive failures for 30 seconds.
  7. Using paired_bootstrap_p, find the smallest evaluation-set size at which a true 3-point improvement is detected 80% of the time.
