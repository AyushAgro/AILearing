The Routing Problem

No single model is optimal on every request. A frontier API wins hard reasoning and multimodal work; a small local model wins chat latency and cost. Routing is the system that picks a point on that frontier for each request — or refuses to pretend one model can cover all three axes at once.

The Engineering Problem

Product wants "GPT-4 quality at GPT-3.5 cost". Ops wants p95 under a second. Finance wants the bill to stop growing linearly with traffic. Pinning every call to the strongest model solves the first sentence and fails the other two. Pinning everything to the cheapest model does the reverse. You need a policy that is allowed to be different for different requests.

The Quality–Cost–Latency Frontier

For a fixed workload mix, each always-route-to-M policy is a point (c_M, q_M, \ell_M). The interesting set is the Pareto front: policies where you cannot improve one axis without hurting another.

tiny-local     quality=0.62  $/req≈0.000  p95=80ms  ctx=8192
mid-open       quality=0.78  $/req≈0.195  p95=900ms  ctx=32768
frontier-api   quality=0.92  $/req≈4.500  p95=2200ms  ctx=200000
Pareto frontier (cost, quality):
  tiny-local    cost=0.000 quality=0.62
  mid-open      cost=0.195 quality=0.78
  frontier-api  cost=4.500 quality=0.92
Key Idea
  • A router is valuable only if it lands above the always-route segment joining two tiers: same quality at lower expected cost, or higher quality at the same budget.
  • Latency is a third axis. A cascade that eventually hits the frontier can still miss a TTFT SLO even when average dollars look good.

What a Router Needs to See

A router that only sees the model string in the client SDK cannot help. It needs request features: estimated tokens, task class, modality, tenant budget and latency SLO. Chapter 2 extracts them; later chapters consume the same RequestFeatures object.

Real Products: Routing in Chat Assistants

Routing is no longer an internal cost trick; at least one major chat assistant describes it as part of the product.

  • Documented OpenAI describes GPT-5 in ChatGPT as a unified system: a fast model for most questions, a deeper reasoning model for harder ones, and a real-time router that chooses between them based on conversation type, complexity, tool needs and explicit user intent (for example, asking it to "think hard"). When usage limits are reached, a mini version of each model handles remaining queries (OpenAI, Introducing GPT-5, August 2025; GPT-5 System Card, 2025).
  • Documented The same sources state that the router is continuously trained on real signals, including when users switch models, preference rates for responses and measured correctness. Chapter 10 returns to this as online learning from implicit feedback.
  • Inferred The usage-limit behaviour is a budget constraint in the sense of Chapter 4: when a tenant's allowance is exhausted, the feasible set shrinks to cheaper tiers. The exact features, thresholds and model of the router are not public, and nothing in this volume should be read as a description of them.
  • Inferred A visible "auto" mode shifts the frontier choice from the user to the system, which makes the router's misroutes user-visible. That is why products that route also tend to expose a manual override: explicit intent is the cheapest, highest-precision feature available.

Rule-Based Routing

Most production routers start as three if statements and a policy table. That is not embarrassing — it is the right baseline. The failure modes of rules are what later chapters fix, not an argument to skip the table.

The Engineering Problem

Every team begins with MODEL = os.getenv("MODEL"). Then code paths hard-code a second model for "hard" tickets, a third for images, and nobody can answer which policy produced yesterday's bill. You need features, an explicit table, and a single route function.

Request Features

task=chat   tok≈2     modality=text
task=code   tok≈5     modality=text
task=math   tok≈6     modality=text
task=vision tok≈6     modality=image

The vision example gets modality=image only because the keyword screenshot made the task vision and the extractor derives modality from the task when the caller passes none. Keyword hints are a weak signal: an attached image with the text “what is this?” would be classed as chat. The client contract should carry modality explicitly (see the feature contract below).

The Three-Line Router

task=chat   tok≈2     -> tiny-local
task=code   tok≈5     -> mid-open
task=math   tok≈6     -> frontier-api
task=vision tok≈6     -> frontier-api
chat   -> tiny-local  (policy_table)
code   -> mid-open  (policy_table)
math   -> frontier-api  (policy_table)
Key Idea
  • Put the policy in data (table), not in scattered conditionals. The three-line function is for teaching; the table is for changing without redeploying every caller.
  • Always log reason. Without it you cannot debug a misroute.

Feature Contract

A rule router is only as good as its features, and features drift when several teams compute them. Fix ownership: each feature has exactly one producer, and some features must never be set by the model or by the router itself.

Ordering, Specificity and Golden Routes

  • Order rules by specificity. Put rare, high-stakes overrides first (VIP tenant, legal hold, multimodal), then task rules, then length heuristics, then the default. Never put the default in the middle of the list.
  • Make the default loud. Emit reason=default and log the raw task label distribution of default hits every week; a growing default share is the earliest signal of a stale table.
  • Freeze golden routes. A small set of (prompt, expected model) pairs runs in CI so a table edit cannot silently move a slice of traffic.

Capability Routing

Before optimising dollars, eliminate illegal assignments. A model without vision must not receive an image. A 8k-context local model must not receive a 50k-token prompt. Capability routing is a hard filter; quality ranking happens among the survivors.

The Engineering Problem

The cost-optimal router picks tiny-local for a screenshot OCR ticket because chat keywords look cheap. The API returns 400. The user sees a failure. Capability constraints are not preferences — they are admissibility.

Capability Profiles

Each model publishes a profile: modalities, context limit, and capability tags (chat, code, math, vision, tools). The router returns only models that accepts the request, then picks maximum quality.

task=chat   tok≈5      mod=text  -> frontier-api  elig=['frontier-api', 'mid-open', 'tiny-local']
task=vision tok≈7      mod=image -> frontier-api  elig=['frontier-api']
task=chat   tok≈12500  mod=text  -> frontier-api  elig=['frontier-api', 'mid-open']
  • Plain chat: all three are eligible; max quality picks the frontier. Cost routing (next chapter) will re-rank under budget.
  • Image OCR: only frontier-api lists the image modality.
  • Long context: tiny-local drops out at 8 192 tokens; mid survives at 32 k.
Failure Mode

Soft “prefer vision models” in a prompt to the router model is not a capability gate. Gates belong in code that cannot be talked out of a 400.

Add a tools-only mid-tier model to the catalogue. Route a needs_tools=True request and show that tiny-local is excluded even when it is the cheapest.

Cost- and Latency-Aware Routing

Among capable models, pick by budget. An SLO is a constraint; preference among feasible models is an objective — minimise cost, maximise quality, or minimise predicted latency including the queue you can see.

The Engineering Problem

Capability routing always selects the frontier when it is eligible. That maximises quality and the invoice. Product has a $0.05 per-request cap and a 1 s p95 ceiling. You need the subset of models that satisfy both, then a rule for ties.

Budgets and SLO-Constrained Selection

\mathcal{F}(x) = \{ m : \widehat{c}(m,x) \le B,\; \widehat{\ell}_{p95}(m,x) \le L \} \qquad m^\star = \arg\operatorname{opt}_{m \in \mathcal{F}(x)} \; \mathrm{obj}(m) 
route -> tiny-local (slo_quality) candidates=['tiny-local']
feasible: tiny-local cost=0.0000 lat=80
queue-aware -> tiny-local
  tiny-local    pred_p95=80ms
  mid-open      pred_p95=1900ms
  frontier-api  pred_p95=2200ms

Under a tight $0.05 / 1 s budget, only the local tier is feasible — mid’s token price alone exceeds the cap on this estimate. With a 5-deep mid queue, predicted p95 jumps to 1 900 ms and mid falls out of a 1.5 s latency SLO even if dollars allow it.

Key Idea
  • Separate feasibility from preference. Mixing them into one score hides why a model was dropped.
  • Queue-aware latency is load balancing meeting model routing. Volume 12’s least-load ideas belong in \widehat{\ell}.

When the feasible set is empty, CostLatencyRouter degrades to the cheapest catalogue member. Add an explicit reason=budget_infeasible_degraded metric and a page if that reason exceeds 1% of traffic.

Quality-Based and Learned Routing

Rules and SLOs do not know that this particular paraphrased maths question is hard. Learned routers estimate which model will win from features or from preference data — matrix factorisation over clusters, or a small classifier over \phi(x).

The Engineering Problem

Benchmark-driven routing (Shnitzer et al., 2023; Hu et al., 2024) and preference routers (Ong et al., 2024 RouteLLM; Ding et al., 2024 Hybrid LLM) exist because keyword task labels are coarse. You need training signals: pairwise preferences, or per-model correctness on logged prompts — and an offline eval that does not leak the test week into training.

Confidence Estimation

Cascades and abstention need a number in [0,1] that correlates with correctness. Log-probabilities, self-consistency, semantic entropy, verbalised scores, calibration and conformal thresholds are the toolbox — none is magic; all must be measured.

The Engineering Problem

You want to run the cheap model first and escalate only when it is unsure. "Unsure" is not a vibe. If your confidence score is miscalibrated, you either escalate constantly (bill looks like frontier-only) or you ship wrong answers with high confidence.

Semantic entropy here clusters bag-of-words near-paraphrases: three France/Paris answers versus one Berlin outlier → two clusters, confidence 1 - H / \log n \approx 0.59. Identical answers yield confidence 1. Guo et al. (2017) ECE on deliberately overconfident scores is about 0.15 — large enough to wreck a cascade threshold. Angelopoulos & Bates (2021) conformal gives a threshold with finite-sample coverage guarantees when exchangeability holds; LLM prompts often violate that, so treat the number as a calibrated deferral knob you still monitor online.

Key Idea
  • Pick one primary signal for deferral and measure ECE on a frozen calibration set weekly.
  • Conformal thresholds buy coverage assumptions, not immunity to distribution shift.

Cascades

A cascade tries models in order and stops when confidence clears a threshold. FrugalGPT (Chen et al., 2023) made the LLM version mainstream; Viola & Jones (2001) had the same control flow for faces. The engineering problem is choosing \tau so expected cost falls without giving up the quality floor.

The Engineering Problem

Always-frontier costs $1.80 per request on the toy mix and scores 1.00 quality. Mid alone scores 0.75. You want mid’s quality at a fraction of frontier’s bill. A cascade with a deferral threshold is the lever — if you set \tau wrong, you either never escalate or always do.

Sequential Escalation

A cascade runs stage 0; if its confidence falls below \tau it defers to stage 1, and so on. With p_j = \Pr(\mathrm{defer}_j) and the empty product equal to 1, expected cost and latency are:

\mathbb{E}[C] = \sum_{i=0}^{K-1} c_i \prod_{j=0}^{i-1} p_j \qquad \mathbb{E}[L] = \sum_{i=0}^{K-1} \ell_i \prod_{j=0}^{i-1} p_j

For three stages this is c_0 + p_0 c_1 + p_0 p_1 c_2. Stages on the critical path add latency; hedging stage 1 while stage 0 is still streaming buys latency with dollars spent on cancelled work — rarely worth it on GPUs you pay for.

tau*=0.25 quality=0.750 E[cost]=0.0390 solo_mid=0.750
cascade mean_cost=0.0390 quality=0.750 mean_steps=1.50
always_frontier mean_cost=1.8000 quality=1.000
E[cost] formula (p=[0.4,0.25], c=[0,0.12,1.5]) = 0.1980

On this stub workload the search finds \tau^\star = 0.25: quality matches solo mid (0.75) while expected cost is about 2% of always-frontier. Mean steps 1.5 means half the requests stop at the first model. The closed-form line shows how deferral probabilities compound cost — useful for back-of-envelope design before you have a calibrated conf_fn.

Failure Mode

Optimising \tau on the same prompts you report quality on overfits the threshold. Hold out a week. Hybrid LLM (Ding et al., 2024) and FrugalGPT both stress evaluation under budget, not only average accuracy.

Checking the Formula

Before trusting the closed form in a design review, check it against simulation. The formula assumes deferral events are independent across stages given the request; correlated difficulty (hard prompts defer at every stage) breaks that, which is why the empirical cascade in the listing above, not the formula, is what you tune on.

formula=0.1980 monte_carlo=0.1953 err=0.0027

Tuning under Dual Constraints

The grid search above optimises cost subject to a quality floor. Production has two floors: quality \ge Q^\star and latency \le L^\star. Sweep \tau, keep candidates that satisfy both, and minimise cost among survivors. If the set is empty you must raise the budget, lower Q^\star, add a faster middle tier, or refuse traffic — not quietly relax the latency SLO in a spreadsheet.

Fallbacks and Resilience

Routing assumes the chosen provider answers. Rate limits, regional outages and 503 storms say otherwise. A fallback chain with per-provider circuit breakers — and an explicit degraded mode — is routing’s reliability twin from Volume 12.

The Engineering Problem

Your learned router picks provider A. A returns HTTP 429 for three consecutive calls. Without a breaker, every request still hammers A, burns retry budget, and never tries B. Users see timeouts; dashboards show “router healthy” because the policy function did not throw.

Breakers across Providers

breaker A: open
call1: provider=C ok=True degraded=False text='ok from C'
call2: provider=C ok=True degraded=False text='ok from C'
call3: provider=B ok=True degraded=False text='ok from B'

A is open, so the chain never calls it. B fails closed twice (503), so early calls land on C. After B’s failures clear the half-open path, call 3 succeeds on B. If every provider fails, the chain returns degraded=True with a cached short answer — a product decision you must design, not a silent empty 200.

Resilience modes for model providers.

Key Idea
  • Breakers are per provider (or per model endpoint), not one global switch.
  • Degraded mode must be detectable in metrics and in the API contract.

Real Products: Provider Failover

  • Documented OpenRouter's provider-routing documentation describes load balancing across providers of the same model that prefers providers without recent significant outages and weights by price, a provider.allow_fallbacks switch for same-model failover, and a models array for falling back to a different model when every provider of the first one fails (OpenRouter docs, Provider Routing and Model Fallbacks).
  • Documented The open-source LiteLLM Router supports retries, fallbacks to other deployments or models, and cooldowns that take a deployment out of rotation after repeated failures — a circuit breaker by another name (LiteLLM docs, Router: Load Balancing, Fallbacks).
  • Documented Hosted model APIs signal pressure with distinct errors; Anthropic's API, for example, documents HTTP 429 rate_limit_error and 529 overloaded_error (Anthropic API docs, Errors). Treat them differently: 429 is your quota, 529 is the provider's capacity.
  • Inferred First-party chat assistants run equivalent failover internally across regions and serving clusters. Their mechanisms are not public; the shared lesson is that same-model failover (another provider) and cross-model fallback (a different quality point) are distinct decisions with distinct quality consequences.

Incidents and the Operator Runbook

Breakers make the failure bounded; the runbook makes it diagnosable. Every routing incident starts from the decision log (Chapter 12) and asks the same questions in the same order.

  1. Quality drop: pull router_decision_total by reason and slice; diff the active policy table and τ against the last known-good digests.
  2. Cost spike: check escalation rate, τ, and whether open breakers forced traffic onto a more expensive peer.
  3. Latency spike: compare QueueState predictions with measured TTFT; a queue-blind latency model routes into the busiest tier.
  4. ECE alert: freeze τ changes and collect a fresh calibration set before retuning.
  5. Provider 5xx: confirm breaker transitions (closed → open → half-open); never disable fallbacks “to help recovery” — that converts a partial outage into a full one.
symptom: p95 quality drop 4pp on code slice
window: 2026-09-28 14:00–16:00 UTC

top_reasons: [('default', 0.41), ('task_code', 0.33)]
model_mix_delta: {'mid-open': -0.18, 'tiny-local': 0.18}

The record above reads as a story: a table edit raised the default share to 41%, the default is tiny-local, and code traffic moved 18 points onto a model that cannot do code. The fix is a revert plus the golden test from Chapter 2 that would have caught it.

Add a half-open probe: after recovery_timeout_s, allow one request to A. If it succeeds, close the breaker; if it fails, reopen. Show the state transitions in a unit test with a fake clock. Then run a game day: inject a mid-tier 503 rate of 20% for fifteen minutes and confirm breakers open, the degraded rate rises, and quality on the answered set stays within 2 pp.

Ensembles

Sometimes one forward pass is not enough. Voting, rank fusion, generate-then-rank and mixture-of-agents spend extra compute for diversity. They pay when the error modes of members are uncorrelated — and they hurt when you only needed a cascade.

The Engineering Problem

A single mid-tier sample fails a hard coding interview question 30% of the time. Three independent samples majority-vote down to roughly 3% if errors are independent — at 3× cost and latency of the slowest member. Ensembles are a bet that error diversity is worth that multiplier.

Mixture-of-Agents and Generate-then-Rank

Wang et al. (2024) Mixture-of-Agents stacks proposers and aggregators: several models draft, another model synthesises. LLM-Blender (Jiang et al., 2023) is the generate-then-rank cousin — propose many, score with a pairwise or pointwise ranker, return the top. Both are ensembles with an explicit fusion stage rather than exact-string voting.

Dynamic and Adaptive Routing

Static tables rot. Traffic shifts, models change, and last month’s classifier drifts. Contextual bandits update arm values from feedback while exploration safety stops the bandit from sending medical queries to a random new endpoint.

The Engineering Problem

You shipped a classifier router. Two weeks later the mid-tier model improved on code and the frontier got slower. Offline labels are stale. You need online learning from rewards (thumbs, unit-test pass, escalation rate) without exploring arms that violate policy.

LinUCB

Disjoint LinUCB (Li et al., 2010) keeps a linear model per arm. For context x and arm a:

\mathrm{score}_a(x) = \hat\theta_a^\top x + \alpha \sqrt{x^\top A_a^{-1} x} 
pulls={'tiny-local': 23, 'mid-open': 1, 'frontier-api': 36}
mean_reward=0.777 cumulative_regret=4.35
  'hello'            -> frontier-api
  'prove theorem'    -> frontier-api
  'def f():'         -> frontier-api

With \alpha=0.6 and unbounded exploration, the bandit over-pulls the frontier (highest mean reward on every task in this synthetic table). Cumulative regret 4.35 on 60 rounds is the price of learning. In production you would put cost into the reward (r - \lambda c) and constrain arms.

Exploration Safety

  • Allowlist / denylist — LinUCBRouter.allowlist and denylist remove illegal arms before scoring.
  • Capability ∩ bandit — intersect eligible models from Chapter 3 with bandit arms on every request.
  • Cold-start caps — min_pulls_before_explore forces a minimum sample before trusting UCB bonuses on sensitive tenants.
  • Shadow exploration — log what the bandit would have picked while the serving path still uses the certified policy (Volume 12 shadow).
RouteDecision(model='tiny-local', reason='linucb:0.400', candidates=('tiny-local', 'mid-open', 'frontier-api'))
RouteDecision(model='frontier-api', reason='linucb:0.566', candidates=('frontier-api',))

For the image request the allowlist collapses to a singleton — exploration cannot invent a text-only arm. That is the correct failure mode: capability wins over curiosity.

Reward Shaping

The bandit optimises whatever reward you give it. Pure quality reward converges on the most expensive arm whenever it is even slightly better. Shape the reward with a price on dollars:

r = q - \lambda\, c_{\mathrm{usd}} 
lambda=0.0  pulls={'tiny-local': 2, 'mid-open': 36, 'frontier-api': 82}
            final picks={'hello': 'frontier-api', 'prove theorem': 'frontier-api', 'def f():': 'frontier-api'}
lambda=0.05 pulls={'tiny-local': 2, 'mid-open': 82, 'frontier-api': 36}
            final picks={'hello': 'mid-open', 'prove theorem': 'frontier-api', 'def f():': 'mid-open'}
lambda=0.2  pulls={'tiny-local': 3, 'mid-open': 116, 'frontier-api': 1}
            final picks={'hello': 'mid-open', 'prove theorem': 'mid-open', 'def f():': 'mid-open'}
  • \lambda=0 reproduces the collapse: every task goes to the frontier.
  • \lambda=0.05 is the useful regime: maths keeps the frontier (0.9 quality is worth $4.50 at this price), chat and code move to mid.
  • \lambda=0.2 over-shapes: maths moves to mid and loses 0.4 quality. λ is a product decision — dollars per quality point — and belongs in reviewed config.
  • tiny-local is barely pulled at any λ: its chat quality (0.70) is below mid's (0.75) and it is free either way. The bandit is right; if you want chat on tiny, that is a latency or capacity objective, not a quality one, and must appear in the reward or the feasible set.

Real Products: Learning from Implicit Feedback

  • Documented OpenAI states that the GPT-5 router in ChatGPT is continuously trained on real signals, including when users switch models, preference rates for responses and measured correctness (OpenAI, Introducing GPT-5, 2025).
  • Inferred These are the same reward sources as this chapter — explicit preference, correction by switching, and graded correctness — and carry the same risks: users who switch models are not a random sample, and a router trained on its own traffic sees only outcomes for arms it chose. Whether OpenAI uses a bandit, periodic supervised retraining or something else is not public.
Failure Mode

Optimising only task reward makes the bandit converge to the most expensive arm whenever that arm is slightly better. Put dollars in the reward or in the feasible set, and document the λ sweep in release notes rather than leaving it as a magic number in a pull request.

Add a latency term to the reward (r = q - \lambda c - \mu \ell) and find a (λ, μ) pair that sends chat to tiny-local while maths stays on the frontier. Report pulls and cumulative regret after 120 steps, and compare against the capability-intersected bandit.

Decision Systems Beyond Models

Sometimes the right model decision is not to answer. Selective prediction, abstention and human escalation turn the router into a decision system: maximise expected utility under the cost of being wrong, silent or escalating.

The Engineering Problem

A support bot is 70% confident about a refund eligibility answer. Wrong answers create chargebacks; abstaining creates tickets; escalating costs agent time. “Always call the LLM” is not a policy — it is an abdication of the utility function.

Utility Framing

U_{\mathrm{answer}}(p) = u_+ p - u_-(1-p) - c_{\mathrm{model}},\quad U_{\mathrm{abstain}} = u_0,\quad U_{\mathrm{escalate}} = u_h - c_h

Geifman & El-Yaniv (2017) selective classification is the ML ancestor: answer only when confidence clears a coverage constraint. Here we compare three actions explicitly.

p=0.95 -> answer   U=0.850
p=0.70 -> escalate U=0.550
p=0.50 -> escalate U=0.550
p=0.30 -> escalate U=0.550
no_escalate:
p=0.95 -> answer   U=0.850
p=0.70 -> answer   U=0.100
p=0.50 -> abstain  U=0.000
p=0.30 -> abstain  U=0.000

With human escalation available, medium confidence prefers a person (U=0.55) over answering at p=0.7 (U=0.1) because wrongs are costly (u_-=2). Without escalation, the policy abstains below the min_confidence floor instead of guessing.

ActionWhenSystems consequence
AnswerHigh calibrated confidenceNormal route / cascade path
AbstainLow confidence, no human pathReturn structured “cannot answer”

Key Idea
  • Routing chooses which model; decision systems also choose whether to act.
  • Utility parameters are product choices. Encode them in config next to the policy table, and review them when chargeback or CSAT moves.

Real Products: Support-Bot Escalation

  • Documented Klarna reported that its OpenAI-powered customer-service assistant handled 2.3 million conversations — two-thirds of its customer-service chats — in its first month, with resolution time falling from 11 minutes to under 2 (Klarna press release, 27 February 2024).
  • Documented In 2025 Klarna publicly said it was again recruiting human customer-service agents after its AI-first push (reported by CX Dive and others, May 2025).
  • Inferred Read through this chapter, that is a change in the utility parameters rather than in the model: when the perceived cost of a wrong or frustrating automated answer (u_-) rises relative to handle cost (c_h), the escalate region widens. Klarna's actual escalation logic is not public.
  • Inferred Support platforms that advertise AI agents with human hand-off implement some version of answer / clarify / escalate. The load-bearing design choices are the confidence signal, the thresholds and whether the hand-off carries the conversation state so the human does not start from zero.

Composing the Full Pipeline

Every chapter so far contributed one stage. Composed, the router is a decision pipeline in which hard gates run before soft scores and the final action is chosen by utility, not by the model.

('mid-open', 1.0, 'answer')
('mid-open', 0.25, 'escalate')

Self-consistency 1.0 on identical samples answers via mid for code. The maths prompt's classifier pick (frontier) exceeds the $1 budget, so the budget router substitutes mid; its diverse samples score 0.25 and the decision layer escalates under default utilities — even though the model pick cleared every gate.

Fit (u_+, u_-, c_h) from last quarter’s chargeback rate and mean handle time. Recompute the confidence thresholds where decide switches action. Then wire handle to FallbackChain so provider failures flip action to degraded without raising to the client.

Evaluating Routers

A router without an eval is a config file with opinions. Cost–quality curves, area under the budget curve, cumulative regret and offline replay are how you prove that routing beats always-frontier and always-mid — with significance, not anecdotes.

The Engineering Problem

The classifier routes 40% of traffic to tiny-local. Finance celebrates. Quality on the golden set drops two points and nobody can say whether the router, the model update or the traffic mix caused it. You need counterfactual-aware offline metrics and an online holdout.

Cost–Quality Curves and AUC over Budgets

For each policy \pi (always-m, rules, cascade, learned), plot mean cost against mean quality on a fixed eval mix. The cascade should dominate the line segments between always-route points. Integrating quality over a cost budget axis gives a single scalar akin to AUC — useful for RouterBench-style comparisons (Hu et al., 2024).

always-route frontier:
  tiny-local    cost=0.000 quality=0.62
  mid-open      cost=0.195 quality=0.78
  frontier-api  cost=4.500 quality=0.92
replay always-mid: mean_cost=0.1203 mean_quality=0.250 (no oracle — IPS-naive)

Without an oracle or inverse-propensity scoring, replaying a different model on logged data underestimates quality whenever the log’s chosen model differs from the candidate — the 0.25 figure is a warning, not a mid-tier score. Collect oracle labels on a sample, or run a shadow parallel call, before you trust counterfactual curves.

Regret and Online Gates

  • Cumulative regret — \sum_t (r^\star_t - r_t) against the best arm in hindsight or an oracle model (Chapter 10).
  • Online A/B — sticky assignment by session; primary metric task success; guardrails on p95 latency and $/request.
  • Slice metrics — report curves per task class; a router can win on average and fail on vision.
Key Idea
  • Publish the always-route frontier every release. A new router that does not beat it on at least one budget is not a promotion candidate.
  • Naive offline replay without propensity weights is exploratory only.

Operating the Router in Production

The cascade saved 40% in a notebook. Two months later the bill is back. Nobody changed the threshold file — traffic shifted toward tool-calling agents, ECE drifted, and the mid-tier model was silently swapped by the provider. Evaluation that runs once is a one-off optimisation; a router needs continuous telemetry and a change process.

Change management

  • Policy as data. Tables, τ, λ, utilities and allowlists live in versioned config with review, not only in Python.
  • Shadow then canary. Log disagreements for 24–72 h; canary 5% sticky by session; auto-rollback on quality or cost guardrails (Volume 12).
  • Model card sync. When a provider changes context limits or modalities, update ModelSpec in the same change as the traffic shift.
  • Weekly ECE job. Fail the release train if deferral ECE doubles.
  • Log propensities. Record the probability with which the serving policy chose each arm; without it, later inverse-propensity replay is impossible.

Review and Next Steps

What You Learned

  • No single model owns the quality–cost–latency frontier. Routing, cascading and ensembling are different control flows over the same catalogue (Chapter 1).
  • Rule routers need explicit features, policy tables and logged reasons; keyword miss and silent defaults are the main failure modes (Chapter 2).
  • Capability profiles are hard gates on modality, context and tools before any soft score (Chapter 3).
  • Budgets define a feasible set; preference among survivors is a separate objective; queues belong in latency predictions (Chapter 4).
  • Learned routers (classifiers, preference / MF scores) need preference or correctness labels and still sit behind gates (Chapter 5).
  • Confidence for deferral must be calibrated: logprob, self-consistency, semantic entropy, verbalised scores, ECE and conformal thresholds (Chapter 6).
  • Cascades minimise expected cost subject to a quality floor by searching deferral thresholds (Chapter 7).
  • Fallbacks use per-provider breakers and an explicit degraded mode (Chapter 8).
  • Ensembles (vote, RRF, MoA, generate-then-rank) buy diversity at multiplied cost — compare to cascades on the same budget (Chapter 9).
  • LinUCB adapts online; exploration safety and cost-aware rewards stop it from collapsing to frontier-only (Chapter 10).
  • Abstention and escalation are first-class actions under a utility function (Chapter 11).
  • Evaluate with cost–quality curves, regret, paired bootstrap intervals and careful offline replay; operate with decision logs, telemetry and versioned policy config (Chapter 12).
  • Real products route too: ChatGPT's GPT-5 router, RouteLLM, OpenRouter and LiteLLM failover and support-bot escalation are documented at the level of behaviour; their internals are inferred at best (Chapters 1, 5, 8, 10, 11).
