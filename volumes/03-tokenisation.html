The Tokenisation Problem

A Transformer consumes integers, not text. The tokeniser is the function that turns a string into those integers, and it fixes three things before a single weight is trained: the sequence length of every input, the size of the embedding and output layers, and what the model can and cannot see. It is the one component that is never retrained and rarely re-examined.

The Engineering Problem

We need a mapping \text{encode}: \Sigma^* \to \{0,\dots,V-1\}^* and its inverse \text{decode} such that (a) every possible string can be encoded (open vocabulary), (b) \text{decode}(\text{encode}(x)) = x exactly, (c) sequences are short, because attention cost grows with length, and (d) V is small enough that the embedding table and softmax are affordable. These four goals conflict.

Key Idea
  • Tokenisation is lossless compression with a fixed, learned codebook. The model's cost is paid per token, so compression rate is a direct cost multiplier.
  • Every choice moves cost between two places: the sequence axis (attention, KV cache, latency) and the vocabulary axis (embedding memory, softmax FLOPs, rare-token under-training).

The Sequence Length Trade-off

Let a text have B UTF-8 bytes and let the tokeniser compress at c bytes per token. Then T = B / c, and per layer:

\text{FLOPs}_{\text{attn}} \propto T^2 d = \frac{B^2}{c^2} d, \qquad \text{KV bytes} = 2 L T d_{kv} \cdot \text{bytes}_{\text{dtype}} \propto \frac{B}{c}
  • Doubling c quarters attention FLOPs and halves the KV cache and the number of decode steps.
  • The price is a larger V: the embedding and LM head are both V \times d, and the output softmax costs 2 V d FLOPs per token.
  • A fixed context window of T_{\max} tokens holds c \cdot T_{\max} bytes. A language at half the compression gets half the effective context and pays double per character.

Unicode, UTF-8 and Normalisation

Code points and bytes

  • Unicode assigns code points (U+0000 to U+10FFFF). UTF-8 encodes each as 1–4 bytes: ASCII is 1 byte, most European accents 2, Devanagari and CJK 3, emoji 4.
  • This is why byte-level tokenisers start with a "tax" on non-Latin scripts: a Hindi character is three bytes before any merging.
  • Not every byte sequence is valid UTF-8. A byte-level decoder that splits a multi-byte character across tokens must re-join before decoding, or use errors="replace" at the very end only.

Normalisation (NFC, NFKC)

  • NFC composes: e + combining acute (U+0301) becomes é (U+00E9). Canonically equivalent strings become byte-identical. Safe for almost all text.
  • NFKC also applies compatibility mappings: full-width Ａ becomes A, the ligature ﬁ becomes fi, superscript ² becomes 2. It is lossy: x² and x2 collapse.
  • Byte-level BPE (GPT-2, tiktoken) applies no normalisation, so it is exactly reversible. SentencePiece defaults to NFKC-like normalisation (nmt_nfkc), so decode(encode(x)) may differ from x.

Grapheme clusters

  • What a user perceives as one character may be several code points: 👩‍👩‍👧 is 5 code points (joined by U+200D zero-width joiners) and 18 bytes; a Devanagari syllable is a consonant plus vowel sign.
  • Tokenisers do not respect grapheme boundaries. Truncating a token sequence can split a grapheme, yielding invalid UTF-8 or a visibly broken character in streamed output.
  • Streaming mojibake: decoding each token independently while streaming prints � when a character spans two tokens. Buffer incomplete UTF-8 sequences before emitting.
  • Normalisation mismatch: normalising at training but not at serving (or vice versa) changes token IDs for accented text and silently degrades quality.
  • Length limits in characters: enforcing limits with len(str) rather than token counts under- or over-fills context by a factor of up to 4 for non-Latin text.

Byte Pair Encoding from Scratch

BPE began as a 1994 compression algorithm and was adapted to neural machine translation by Sennrich et al. (2015). GPT-2 made it byte-level and added a pre-tokenisation regex. That combination, unchanged in essence, tokenises most text processed by LLMs today. We build it in about 70 lines as the start of forge.tokenizers.bpe, then prove it matches tiktoken exactly.

The Algorithm

Simple Version

  1. Start with a vocabulary of the 256 byte values. Represent the corpus as byte sequences.
  2. Count every adjacent pair of symbols. Merge the most frequent pair into a new symbol and record the merge.
  3. Repeat until the vocabulary reaches the target size V.
  4. To encode new text, replay the merges in the order they were learned.

Training is greedy: at step k it picks

(a, b)^{*} = \arg\max_{(a,b)} \sum_{w \in \mathcal{W}} f(w) \cdot \text{count}_{w}(a, b)
  • \mathcal{W} is the set of distinct pre-tokens (chunks), f(w) its corpus frequency.
  • The merge list is ordered: its index is the rank. Encoding must apply lower-ranked merges first, or it produces different tokens than training saw.
  • BPE optimises nothing globally. It is a greedy compression heuristic, and that is why its token boundaries are sometimes linguistically odd.
  • Byte fallback: because the base vocabulary is the 256 UTF-8 bytes, every Unicode string is encodable. There is no UNK. A single BPE token may still be an incomplete UTF-8 sequence, so decoding must buffer until a valid character forms.

Pre-tokenisation

Running BPE over raw text would let merges cross word and punctuation boundaries, producing tokens like "dog." and "dog!" that waste vocabulary. GPT-2 first splits text with a regex and only merges inside each chunk.

  • '(?:[sdmt]|ll|ve|re): English contractions as their own chunks.
  • ?\p{L}+: a run of letters with an optional leading space. The space belongs to the following word, which is why tokens look like Ġworld.
  • ?\p{N}+: a run of digits (GPT-2 allows any length; cl100k caps it at three).
  • ?[^\s\p{L}\p{N}]+: punctuation and symbols.
  • \s+(?!\S) then \s+: whitespace, leaving the last space to attach to the next word.

Implementation

Training with incremental pair updates

  • Naive training recounts all pairs after every merge: O(N) per merge, O(NV) in total.
  • We work on the unique chunks with counts (a few thousand, not the full corpus) and keep an inverted index pair → chunks containing it. A merge only touches chunks that contain the winning pair.
  • Production trainers (HF tokenizers, SentencePiece) add a priority queue with lazy deletion so that finding the maximum is O(\log P) rather than a linear scan.

What the output shows

  • The regex keeps the space with the following word (' world', ' 2024') and isolates the double space so the second space attaches to x.
  • The first merge is two spaces, because the Markdown corpus is full of indentation. The corpus decides the vocabulary; our tiny English corpus gives no merges at all for 東京 or 🙂, which stay as raw bytes.
  • b'\xc3' is half of the UTF-8 encoding of ï. A single token need not be valid UTF-8; only the concatenated sequence must be.
  • The round-trip test is the single most important tokeniser test. Byte-level BPE with no normaliser passes it by construction; keep it as a property test anyway, because a later "cleanup" step (strip, normalise, lower-case) is how it breaks.

Encoding: merge-rank application

  • For each chunk, repeatedly find the adjacent pair with the lowest rank and merge it, until no pair is in the merge table.
  • This is O(n^2) per chunk in our version. Chunks are short (a word), so it is acceptable; tiktoken uses the same algorithm in Rust with a linear scan over a small array.
  • Encoding is not "longest match from the vocabulary". Two tokenisers with the same vocabulary but different merge orders produce different IDs.
Correctness trap

Applying merges in frequency order on the new text, rather than rank order, looks plausible and gives mostly-similar output. It is wrong, and the mismatch appears only on rare strings, which is exactly where models are fragile. Always test token-for-token parity against a reference.

Byte-level BPE strengths

  • Open vocabulary: no [UNK], ever.
  • Exactly reversible when no normaliser is used.
  • Simple, fast, deterministic encoding.

Weaknesses

  • Greedy merges are corpus-frequency artefacts, not morphology.
  • Non-Latin scripts start at 2–3 bytes per character and get fewer merges.
  • Deterministic segmentation: no built-in regularisation.

WordPiece and Unigram

BPE is one of three subword families in production. WordPiece (BERT) and the Unigram language model (T5, ALBERT, XLNet, many multilingual models via SentencePiece) differ in how they choose the vocabulary and, more importantly for engineers, in how they segment at inference.

WordPiece

Training: likelihood-based merges

WordPiece merges bottom-up like BPE, but scores a candidate pair by how much it increases corpus likelihood under a unigram model rather than by raw frequency:

\text{score}(a, b) = \frac{f(ab)}{f(a)\, f(b)}
  • The score favours pairs whose parts rarely occur apart. "##ing" pairs with many stems, so its individual score is lower than a pair such as "q" "##u".
  • Word-internal pieces carry a ## prefix. A word-initial piece and a continuation piece with the same characters are different tokens.
  • Google's original training code was never released Documented (Wu et al. 2016 describe it only at a high level); the HF implementation is a reconstruction.

Encoding: greedy longest-match-first

  • WordPiece does not store merges. At inference it scans left to right, taking the longest vocabulary entry that matches, then continues with ##-prefixed pieces.
  • If any position cannot be matched, the whole word becomes [UNK]. BERT's vocabulary is character-based, not byte-based, so an unseen character (a rare emoji, say) triggers this.

Unigram Language Model

BPE and WordPiece produce one deterministic segmentation chosen by a greedy procedure. We would like (a) the most probable segmentation under an explicit model, and (b) the ability to sample alternative segmentations during training so the model becomes robust to segmentation noise.

The model

Unigram assumes each piece is drawn independently from a distribution p over a vocabulary \mathcal{V}. For a segmentation \mathbf{s} = (s_1, \dots, s_m) of text x:

P(\mathbf{s}) = \prod_{i=1}^{m} p(s_i), \qquad P(x) = \sum_{\mathbf{s} \in S(x)} P(\mathbf{s}), \qquad \mathbf{s}^{*} = \arg\max_{\mathbf{s} \in S(x)} \sum_i \log p(s_i)
  • S(x) is exponential in length, but both the sum and the max decompose over a lattice of positions, so dynamic programming solves them in O(n \cdot \ell_{\max}).
  • Viterbi computes \mathbf{s}^*. Forward–backward computes the expected count of each piece, which is the E-step of EM.

Training: EM with pruning (top-down)

  1. Start from a large seed vocabulary (all frequent substrings, or a suffix-array extraction).
  2. E-step: expected piece counts under the current p, via forward–backward.
  3. M-step: p(s) \propto \mathbb{E}[\text{count}(s)].
  4. Prune: remove the pieces whose removal least reduces likelihood (Kudo uses the top 80% by loss). Always keep single characters so everything stays segmentable.
  5. Repeat until the target size is reached.

Unlike BPE, which grows the vocabulary bottom-up, Unigram shrinks it top-down.

  • Log-likelihood rises monotonically while the vocabulary is pruned from 16 to 11 pieces: EM concentrates mass on useful pieces (hug, pug, hugs) and pruning discards the rest.
  • bunhug reuses hug but falls back to characters for bun, which was pruned. Characters are the safety net, the equivalent of BPE's byte base.
  • The toy prune (drop 25% by probability) is cruder than Kudo's loss-based criterion; it is enough to show the mechanics. Production code works in log space throughout (the lse helper) to avoid underflow.

Subword regularisation

  • At training time, sample a segmentation \mathbf{s} \sim P(\mathbf{s} \mid x)^{\alpha} instead of taking the Viterbi path (Kudo 2018). The same word appears under several tokenisations, acting as data augmentation.
  • BPE-dropout (Provilkov et al. 2020) is the BPE analogue: randomly skip merges during encoding.
  • Use it for low-resource or noisy-input models (MT, speech transcripts). LLM pretraining at scale rarely uses it; data volume already provides robustness, and deterministic tokens simplify caching.

SentencePiece

  • A library (Kudo & Richardson 2018) implementing both BPE and Unigram over raw text, with no language-specific pre-tokeniser.
  • Whitespace is a normal symbol, escaped as ▁ (U+2581). "Hello world" becomes ▁Hello ▁world, so decoding is concatenation plus replacing ▁ with a space: language-independent and lossless for whitespace.
  • Byte fallback (used by Llama 1/2, Mistral): characters not in the vocabulary are emitted as <0xE6>-style byte tokens instead of <unk>, giving an open vocabulary with a character-level base.
  • Normalisation (NFKC by default) is part of the model file, so it travels with the tokeniser. That is good for reproducibility and bad for exact round-trip.

Special Tokens, Chat Templates and Vocabulary Design

A tokeniser is not just a segmenter. It also defines control symbols that no user text can produce, and a template that maps a conversation to a token sequence. Those two artefacts are the interface between the training pipeline and every serving stack that will ever run the model.

Chat Templates as a Contract

The model was fine-tuned on conversations serialised in one exact format. At serving time, any deviation (a missing newline, a different role name, a BOS added twice) produces a distribution shift the model has never seen. Symptoms are subtle: slightly worse answers, runaway generations, or ignored system prompts.

What the output shows

  • The base SmolLM2 checkpoint ships no chat template, yet IDs 1 and 2 are already <|im_start|> and <|im_end|>: the vocabulary was designed for the instruct variant. Serving a base model with a guessed template is a common source of "the model is bad" reports.
  • The rendered prompt ends with <|im_start|>assistant\n. add_generation_prompt=True is required at inference and must be false when rendering training targets.
  • tiktoken refuses to encode a special-token string found in ordinary text unless told what to do. Encoding user text with allowed_special produces the real control token 100257, which lets a user forge a turn boundary.
Special-token injection
  • Rule: user-supplied and retrieved text must be encoded with special tokens disabled (treated as ordinary text). Only the template renderer may emit control IDs.
  • HF tokenisers parse special-token strings in text by default. Build prompts as ID lists (template IDs + encode(user_text, split_special_tokens=True)) or escape the strings before rendering.
  • Add a test: a user message containing every special-token string must not produce any special ID.

Chat template checklist

  • Version the template with the tokeniser and the weights as one artefact; hash all three.
  • Golden test: render a fixed conversation and compare IDs byte-for-byte across training code, the inference server and any client SDK.
  • Check BOS handling: template adds it, and encode must then be called with add_special_tokens=False, or BOS appears twice.
  • Configure stop tokens: EOS and the end-of-turn token.
  • Train only on assistant tokens (mask system and user tokens in the loss) unless you intend otherwise.

Vocabulary Size Trade-offs

Let V be vocabulary size and d model width.

\text{params}_{\text{emb}} = V d \;(\times 2 \text{ if untied}), \qquad \text{FLOPs}_{\text{head}} = 2 V d \text{ per token}, \qquad \text{logits memory} = B \cdot T \cdot V \cdot \text{bytes}

  • English is saturated: quadrupling V bought nothing on this sentence. The extra vocabulary pays off in code, other scripts and numerals.
  • Small models pay disproportionately: SmolLM2-135M spends 28.3M of 134.5M parameters (21%) on its 49k tied embedding (Chapter 7). A 200k vocabulary at d = 576 would be 115M parameters, most of the model.
  • Logit memory: at B = 8, T = 8192, V = 200\text{k}, fp32 logits are 52 GB. Chunked or fused cross-entropy is mandatory at large V.
  • Rare-token under-training: each token's embedding is updated only when it appears. Larger vocabularies have more tokens seen a handful of times, which become glitch tokens (Chapter 6).
  • Rule of thumb Inferred: 32k–64k for English-centric small models; 128k–256k for multilingual or code-heavy frontier models, where embedding cost is a small fraction.

Production Tokenisers

Our BPE is correct but slow and featureless. Production libraries add speed (Rust, parallelism, caching), offsets for aligning tokens back to characters, configurable normalisers and pre-tokenisers, and serialised artefacts. This chapter proves our encoder matches tiktoken token-for-token and measures what the libraries buy.

Simple Version → Production Version

Simple Version

Our ByteBPE: regex split, per-chunk merge loop in Python, bytes vocabulary.

Production Version

  • tiktoken (OpenAI): encode-only BPE in Rust with a Python wrapper; ships merge ranks for gpt2, cl100k_base, o200k_base. No training.
  • HF tokenizers: a pipeline of Normalizer → PreTokenizer → Model (BPE, WordPiece, Unigram, WordLevel) → PostProcessor (adds special tokens) → Decoder. Trains and encodes in Rust, returns offsets, serialises to one tokenizer.json.
  • SentencePiece: C++ trainer and encoder for BPE and Unigram, normaliser rules baked into a .model protobuf.

Why It Is Complicated

  • Throughput matters: tokenising a pretraining corpus of 1013 bytes at 10 MB/s per core takes ~30 core-years.
  • Offsets must survive normalisation (which changes string lengths) for NER, highlighting and citations.
  • Serialised formats must be exactly reproducible across library versions; a changed default regex is a silent model-breaking change.

Parity Test Against tiktoken

Our encoder only needs a rank table. tiktoken exposes GPT-2's (_mergeable_ranks, a private attribute), so we reuse our regex and merge loop with GPT-2's ranks and compare IDs.

Arithmetic and Digits

  • GPT-2 splits 1234567 as 123|45|67, while 80235 in a sum becomes 80|235. The same digit position lands in different tokens depending on the number, so the model cannot learn a consistent column-wise algorithm.
  • cl100k caps digit runs at three (\p{N}{1,3}) and splits left to right: 123|456|7. Consistent, but left-aligned, whereas place value is right-aligned.
  • Llama 1/2, SmolLM and DeepSeek split every digit individually; Singh & Strouse (2024) find right-to-left three-digit grouping helps arithmetic. Documented
  • Mitigation: choose the digit rule when designing the tokeniser. After training it cannot be changed without retraining the model.

Whitespace in Code

  • GPT-2 has no multi-space tokens, so an 8-space indent costs 7 tokens. cl100k added whitespace runs: the same snippet drops from 13 to 6 tokens.
  • Python code in GPT-2 costs about 2 bytes per token versus 2.85 in cl100k (Chapter 9): 40% more tokens for the same file.
  • Tabs versus spaces, trailing whitespace, and CRLF all change token counts and sometimes model behaviour. Normalise code whitespace at the edge only if you can restore it exactly.

Multilingual Token Tax

  • The same sentence costs 18 tokens in English and 100 in Hindi with GPT-2 (5.6×), and 20 with o200k (1.1×). Petrov et al. (2023) measured premiums above 10× for some languages. Documented
  • The tax compounds: higher API cost, less effective context, slower generation, and fewer training tokens per unit of meaning.

Glitch and Under-trained Tokens

  • SolidGoldMagikarp is a single GPT-2 token (43453), created because a Reddit username was frequent in the tokeniser's training data but nearly absent from the model's. Its embedding stayed near initialisation; GPT-3 behaved erratically when asked to repeat it.
  • cl100k splits it into 5 tokens, fixing that case, but every vocabulary has its own. Land & Bartolo (2024) detect them by looking for embeddings close to the mean of known-unused tokens and by output-probability probes. Documented
  • Root cause: the tokeniser corpus and the model corpus differ. Mitigation: train the tokeniser on a sample of the pretraining mix, then audit tokens with low training frequency.

Token Boundary Artefacts

  • https:// is https|://, but a prompt ending in https:/ gives https|:/. The model rarely saw :/ followed by /, so continuing the prompt is out of distribution.
  • A prompt ending in a trailing space leaves a lone ' ' token, while in training the space was attached to the next word. Completions after a trailing space are measurably worse.
  • Fix: token healing: back up the last token(s) and constrain generation to continuations whose bytes start with the removed text (as in Guidance).

Security

Tokenisation-based filter evasion
  • A Cyrillic а in pаssword is visually identical and tokenises into 4 pieces instead of 1. Keyword, embedding and classifier filters that saw password in training may not fire; the LLM behind the filter often still understands the word.
  • A zero-width space (U+200B) splits the word into pass|​|word and is invisible in most UIs. Other invisible code points: U+200C/D, U+2060, U+FEFF, and the Unicode tag block (U+E0000–E007F), which can smuggle whole hidden instructions ("ASCII smuggling").
  • NFKC fixes full-width letters but not homoglyphs or zero-width characters. Normalisation alone is not a defence.

Input hygiene for guardrails

  • Apply NFKC, then strip or flag format characters (Unicode category Cf) and tag-block characters.
  • Map confusables to a skeleton (Unicode TS #39) before keyword matching, and flag mixed-script words.
  • Run safety classifiers on the normalised text and on the raw text the model will see.
  • Log the raw code points of flagged inputs; screenshots hide the attack.
  • Counting in the wrong unit: rate limits and context budgets in characters; bills and truncation in tokens.
  • Tokeniser drift: a client estimates tokens with cl100k while the model uses o200k; budgets are off by up to 4× on non-English text.
  • Spelling and character tasks: counting letters in strawberry is hard when the model sees str|aw|berry.

Embeddings

The tokeniser emits IDs; the embedding matrix turns each ID into a vector. That matrix is the model's entire knowledge of a token before context is applied, and in most decoders the same matrix is reused to produce logits. Its geometry is measurable, and it is not the tidy isotropic space that cosine similarity quietly assumes.

From One-hot to Dense

  • A one-hot vector e_i \in \{0,1\}^V carries no similarity: every pair of tokens is orthogonal.
  • An embedding matrix E \in \mathbb{R}^{V \times d} maps e_i \mapsto E^\top e_i = E_{i,:}, a lookup. Gradients update only rows that appear in the batch.
  • word2vec (Mikolov et al. 2013) trains E so that \sigma(u_c^\top v_w) predicts context words (skip-gram with negative sampling), implicitly factorising a shifted PMI matrix (Levy & Goldberg 2014).
  • GloVe (Pennington et al. 2014) fits w_i^\top \tilde w_j + b_i + \tilde b_j \approx \log X_{ij} directly on co-occurrence counts.
  • In an LLM, embeddings are learned end to end by next-token prediction. The distributional intuition still holds: tokens used in similar contexts get similar rows.

Weight Tying

The LM head computes logits z = W h with W \in \mathbb{R}^{V \times d}. Weight tying (Press & Wolf 2017) sets W = E:

z_i = E_{i,:}^{\top} h \quad\Rightarrow\quad p(i \mid h) \propto \exp\big(\lVert E_i \rVert \lVert h \rVert \cos(E_i, h)\big)
  • Saves V d parameters. Matters for small models; negligible for 70B models, which usually untie (Llama 2/3 untie; Gemma and SmolLM2 tie).
  • Couples input and output semantics: a token's input vector is also its output prototype. Rare tokens get gradient from the softmax denominator on every step (pushed away from all hidden states), which shapes geometry.
  • The token norm \lVert E_i \rVert acts as a per-token prior in the logits.

Geometry on a Real Model

E shape: (49152, 576)  tied: True

What the output shows

  • Input and output matrices share storage: tied. The embedding is 21% of the model's parameters.
  • Neighbours are semantically sensible (' Paris' → capitals, ' Monday' → weekdays) but dominated by surface variants: ' King', 'King', ' kings'. A byte-level vocabulary stores case and leading-space variants as unrelated IDs, and the model spends capacity re-learning that they are the same word.
  • Anisotropy: two random token rows have mean cosine 0.449, not ~0. Subtracting the mean vector brings it to 0.000: a single shared direction dominates. Cosine similarity without centring mostly measures alignment with that direction.
  • Norms vary 4× (1.76 to 7.47). Under tying, norm is part of the logit, so frequent tokens tend to sit at different norms from rare ones.

Anisotropy defined

\text{aniso}(X) = \mathbb{E}_{i \neq j}\big[\cos(x_i, x_j)\big], \qquad \cos(u, v) = \frac{u^\top v}{\lVert u \rVert \lVert v \rVert}
  • Isotropic vectors give ≈0. Ethayarajh (2019) found contextual representations of GPT-2 and BERT occupy a narrow cone, with anisotropy rising in upper layers.
  • Causes include the softmax pushing rare tokens in a common direction, frequency bias, and a few outlier dimensions with very large magnitude.
  • Remedies for retrieval use: mean-centring, whitening (BERT-whitening), or contrastive fine-tuning (SimCSE, sentence-transformers), which is why you should not use raw LLM hidden states as sentence embeddings.
  • Raw cosine thresholds: a "0.8 means similar" rule tuned on one model is meaningless on another with different anisotropy.
  • Dot product versus cosine: ranking by dot product on un-normalised vectors favours high-norm (often frequent or generic) items.
  • Under-trained rows: tokens that never appeared keep near-initial embeddings clustered together; they show up as a tight cluster far from real tokens, which is also how you detect them.

Contextual Representations

A static embedding gives bank one vector whether it is a river bank or a savings bank. Every Transformer layer rewrites each position's vector using its context, so the hidden state at layer \ell is a contextual representation. This chapter measures how that happens on SmolLM2 and how to pool token vectors into one sentence vector.

From Static to Contextual

  • ELMo (Peters et al. 2018): concatenated forward and backward LSTM states, combined with learned per-layer weights. Showed that different layers carry different information.
  • BERT: bidirectional attention, so every token sees both sides. Best for encoding and classification; cannot generate left to right.
  • Decoder hidden states: causal, so position t only knows x_{\le t}. The last token is the only one that has seen the whole input, which matters for pooling.

Layer-wise Behaviour on SmolLM2

The second half of the Chapter 7 listing runs four sentences through the model and collects all 31 hidden states (embedding output plus 30 layers).

  • Anisotropy grows with depth: mean pairwise cosine between token vectors rises from 0.10 at the embedding layer to 0.71 at layer 29, matching Ethayarajh's finding. The final layer drops to 0.40 because the last norm and LM head reshape it for prediction.
  • Contextualisation: at layer 0, bank is identical in all sentences (cosine 1.000). By the middle layer, two financial uses (0.910) are closer than financial and river (0.793). By the last layer both have drifted, but the gap persists.
  • Absolute cosines stay high even for different senses: use relative comparisons, not thresholds.
Position Is Part of the Representation
  • RoPE, ALiBi and absolute embeddings (Volume 2) are not tokeniser features. They live in the model and shape every contextual vector.
  • When you pool or probe hidden states, you are measuring a mixture of content and position. For sentence embeddings, contrastive training usually learns to ignore absolute position; for LM probing, position effects are a confound to control for.

Probing

  • A probe is a small classifier (usually linear) trained on frozen hidden states to predict a property: part of speech, syntactic depth, sentiment, factual truth.
  • Typical pattern: surface and lexical features peak early, syntax in the middle, task- and prediction-specific features late. Middle layers often give the best general features.
  • Caveat: a high probe accuracy shows information is linearly decodable, not that the model uses it. Compare against control tasks (Hewitt & Liang 2019) and random-weight baselines.

Pooling Strategies for Sentence Embeddings

\text{mean}(H, m) = \frac{\sum_t m_t h_t}{\sum_t m_t}, \qquad \text{cls}(H) = h_0, \qquad \text{last}(H, m) = h_{\max\{t : m_t = 1\}}
cls          sim(q,para)=0.901  sim(q,unrelated)=0.699  gap=0.203
mean         sim(q,para)=0.634  sim(q,unrelated)=0.075  gap=0.559
max          sim(q,para)=0.833  sim(q,unrelated)=0.643  gap=0.190
mean_nomask  sim(q,para)=0.589  sim(q,unrelated)=0.219  gap=0.371
  • The model was trained with masked mean pooling, and that pooling gives the largest separation (0.559) between a paraphrase and an unrelated question.
  • CLS and max pooling rate the unrelated question at 0.70 and 0.64: high absolute similarity, weak separation. Pooling is part of the model; use the one it was trained with.
  • Forgetting the attention mask pulls padding vectors into the mean and cuts the gap from 0.559 to 0.371. This is a common silent bug in batched embedding services, and it makes results depend on batch composition.
  • For decoder-based embedders, use last-token pooling (with left padding or careful indexing) or the pooling the model card specifies; mean pooling over causal states over-weights early tokens that have seen little context.

Positional Information as Part of the Representation

  • Position is not a tokeniser concern: the tokeniser emits the same ID for the at every position. Position enters the representation inside the model.
  • Absolute learned or sinusoidal embeddings are added to token embeddings (GPT-2, BERT), so every hidden state mixes "what" and "where".
  • RoPE (Volume 2) rotates queries and keys and never touches the residual stream directly; position appears in hidden states only through attention patterns. This is one reason RoPE models extrapolate and interpolate more gracefully.
  • Implication for pooling and caching: identical text at different offsets yields different hidden states, so embedding caches must key on the exact input, not a substring.

Evaluating Tokenisers

A tokeniser is chosen once and lived with for the life of the model. The decision deserves numbers: how well it compresses each language and domain you care about, whether it is exactly reversible, how fast it is, and how unequally it charges users of different languages.

Reading the numbers

  • English is saturated at 4.39 bytes/token for every production tokeniser. Differences appear elsewhere.
  • GPT-2 charges Hindi 5.6× and Arabic 3.7× the English token count. o200k brings every language within 1.3×; Hindi goes from 100 tokens to 20. Vocabulary size was spent on non-English scripts.
  • SmolLM2 (49k, English-centric data) behaves like GPT-2 on non-Latin scripts but better on code (2.31), reflecting its training mix.
  • Our 1k-vocabulary BPE trained on 94 KB of English reaches 1.0 byte/token on Hindi, Chinese and Arabic: no merges exist for those bytes, so it is a byte-level model there. The tokeniser corpus determines who pays.
  • This is one sentence. Real evaluations use thousands of parallel sentences (FLORES-200) and report confidence intervals; single sentences can mislead by ±20%.

Evaluation Harness Design

Decision checklist

  • Compression measured on your traffic mix, not on English web text.
  • Maximum language premium you will accept (for example ≤ 2× for supported languages).
  • Digit rule and whitespace handling chosen deliberately for maths and code.
  • Round-trip = 1.0 on a fuzz set; special-token injection test passes.
  • Embedding cost V d acceptable at your model size.
  • Tokeniser corpus sampled from the pretraining mix, to avoid glitch tokens.

Volume Review

What You Learned

  • Tokenisation trades sequence length against vocabulary size; compression c divides attention FLOPs by c^2 and KV cache by c.
  • UTF-8 costs 1–4 bytes per code point; NFC is safe, NFKC is lossy; graphemes can span tokens.
  • BPE merges greedily by frequency and encodes by merge rank; GPT-2's regex keeps merges within word-like chunks with leading spaces.
  • WordPiece scores merges by likelihood gain and encodes by greedy longest match; Unigram trains top-down with EM and encodes with Viterbi.
  • Special tokens and chat templates are a contract that must be versioned and tested byte-for-byte.
  • Digit splitting, whitespace handling and tokeniser corpus choice cause arithmetic, code, fairness and glitch-token problems.
  • Homoglyphs and invisible characters evade token-level filters; normalisation alone does not stop them.
  • Embeddings are anisotropic; tying couples input and output; contextual states separate word senses by the middle layers.
  • Pooling is part of an embedding model; masked mean pooling beat CLS and max pooling on a mean-trained encoder.
  • Position encodings live in the model, not the tokeniser; Forge ships the tokeniser stack as forge.tokenizers.

Important Architecture

Failure Modes

  • Encoding merges out of rank order; parity breaks only on rare strings.
  • Normaliser or cleanup step breaking round-trip exactness.
  • Chat template mismatch between training and serving; double BOS; missing stop token.
  • Special-token strings in user text encoded as control tokens.
  • Inconsistent digit chunking harming arithmetic; missing whitespace tokens inflating code cost.
  • Glitch tokens from a tokeniser corpus that differs from the model corpus.
  • Homoglyph and zero-width evasion of filters.
  • Unmasked mean pooling; raw cosine thresholds on anisotropic spaces.

Evaluation

  • Bytes per token per language and domain; premium versus English on parallel text.
  • Round-trip exactness on fuzzed Unicode; golden-ID regression tests in CI.
  • Throughput single-threaded and batched.
  • Bits per byte, not perplexity, when comparing models with different tokenisers.
  • For embeddings: separation between related and unrelated pairs, not absolute cosine.
