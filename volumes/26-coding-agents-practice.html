The Coding-Agent Stack

A coding agent is not one product. It is a family of interaction models — chat, IDE agent, CLI agent, cloud/background agent — with different context, permissions and failure modes. Choosing poorly wastes tokens; choosing blindly ships defects.

The Engineering Problem

A team standardises on “the AI tool” after a demo. Six months later the same people use chat for architecture, an IDE agent for multi-file edits, a CLI agent for overnight refactors and a cloud bot for PR comments — with four contradictory instruction files and no shared gate. The tools are fine. The stack was never designed.

Four interaction surfaces

  • Chat (browser / app): high-level reasoning, learning, rubber-ducking, light coding without deep repo coupling. Examples: ChatGPT, Claude.ai. Documented
  • IDE agent: multi-file edits inside an editor with project rules, @-context and optional MCP. Examples: Cursor; Kiro as an agentic IDE. Documented / Inferred for Kiro details
  • CLI / terminal agent: permissioned shell and edit loops over a checkout. Example: Claude Code. Documented
  • Cloud / background agent: long-running or PR-attached agents that continue without your laptop. Cursor Cloud Agents / Bugbot-style review and peers. Documented where vendor-named; treat feature depth as moving.

Key Idea
  • Match the surface to the job. Do not use a cloud agent to learn a concept you have not run locally.
  • Match the workflow to the risk. Learning and vibe coding are allowed; shipping requires gates (Chapters 8–10).
  • When not to use an agent: irreversible production changes, unclear requirements, security-sensitive code you cannot review, or when you need to build the mental model yourself first.

Cost, Context and Control as First-Class Variables

Volume 15 showed that agency costs tokens roughly quadratically in steps when every call re-reads the transcript. Coding agents inherit the same economics: a confused Composer or Claude Code session that retries the same failing test ten times is not “persistence”; it is a budget incident with a git branch attached.

\mathbb{E}[\text{session tokens}] \approx \sum_{i=1}^{n} (c_0 + i\Delta) = n c_0 + \tfrac{n(n+1)}{2}\Delta

Here c_0 is the always-on context (rules, AGENTS.md, open files) and \Delta is the growth per tool round. Prompt caching may reduce price; it does not reduce the cognitive load of reviewing a 2 000-line diff that accrued while you were not watching.

Research Frontier
  • SWE-agent (Yang et al., 2024) argues the agent–computer interface is as important as the base model for repository tasks. That is why IDE/CLI agents with search, lint feedback and file viewers systematically beat paste-into-chat for monorepos.
  • Function-level benchmarks (HumanEval / Codex) remain useful for model comparison and nearly useless as a substitute for your CI gate.

  • Using vibe-coding habits on a ship branch.

Cost and Context Limits as Constraints

  • Seat licences are visible; token burn on Agent mode is often not. Measure both.
  • Context pollution (huge rules, generated trees, lockfiles) lowers answer quality before you hit a hard token cap.
  • Rate limits turn long autonomous loops into queue-shaped outages mid-refactor.
  • Review time is part of cost. A “free” agent diff that takes four hours to review is not free.
Implementation Notes
  • Keep a living scorecard in the repo (Volume 23 Chapter 1) with a “last verified” date per tool.
  • When a Documented cell drives a security policy, link the vendor doc URL and archive a PDF snapshot.

The Engineering Problem

Hooks and Local Fakes

Some products support hooks (pre-edit, post-command). Treat them like CI lite: useful for formatting and secret scanning reminders; dangerous if they silently mutate policy. Local fakes (Volume 15’s ScriptedModel pattern) still belong in tests — do not ask a coding agent to “pretend” a production API when you can run a deterministic fake in-process.

Trade-off
  • One shared module reduces drift. Over-sharing (forcing frontend rules into backend paths) creates noise. Use globs.
  • AGENTS.md Commands match CI exactly.
  • CLAUDE.md does not fork Commands.
  • Cursor rules are path-scoped where possible.
  • MCP servers are on the allow-list; no secret env.
  • .env is gitignored; only .env.example is committed.

Failure Modes

  • Four full copies of the style guide that drift independently.
  • MCP servers added “just for a spike” and left in the shared config.
  • Instruction files that contradict CI.

Claude (Chat, Projects, Claude Code)

Claude’s strength for many engineering teams is long-context reasoning and an explicit CLI agent (Claude Code) that asks before destructive actions. Use chat for architecture; use Claude Code when the repo and permissions matter.

The Engineering Problem

An engineer pastes half a codebase into claude.ai, gets a beautiful design, then re-types it into the IDE by hand — or worse, pastes secrets from .env “so Claude can debug”. The model was helpful. The boundary was missing.

  • Pointer pattern (default): one line “see AGENTS.md” — Chapter 3.

  • Put “never cat .env” in AGENTS.md so every tool sees it.
  • In Claude Code sessions, require the agent to paste command output for lint/tests before claiming done — same as Volume 23.
Risk
  • Projects knowledge can accumulate stale secrets and customer snippets. Periodically audit uploads.
  • Computer use and broad tool permissions are not appropriate for production credentials.

Projects and Knowledge Hygiene

Claude Projects are sticky context. That is their value and their risk. A Project that began as “architecture notes” often accretes API keys from a debugging session six weeks ago. Schedule an audit the way you schedule dependency updates.

  1. List every uploaded file and pasted snippet in the Project.
  2. Delete anything with credentials, customer identifiers or production hostnames.
  3. Replace with redacted fixtures or public sample schemas.
  4. Record the audit date in the Project description.

Artifacts versus Repository Truth

Artifacts are excellent for iterating on a self-contained draft. They are not the source of truth once code must live in git. Promote Artifact contents through Workflow C: tests, review, PR — never “download and force-push”.

Permissions
  • Prefer Claude Code’s ask-before-destructive defaults for ship work.
  • Deny network for sessions that only need local tests unless MCP is explicitly required.

Failure Modes

  • Using computer use against production admin UIs.
  • Duplicating the entire style guide into CLAUDE.md until it drifts from AGENTS.md.
  • Trusting Artifacts that never ran under CI.

Lean on Claude when

  • You need careful architecture or long-document synthesis.
  • You want an explicit permissioned CLI agent on a checkout.

Prefer another surface when

  • You need tight IDE Tab-completion UX all day (Cursor).
  • Your org’s approved path is ChatGPT Enterprise only.

Cursor

Cursor is an AI-native IDE: Tab for completion, Chat for questions, Composer/Agent for multi-file work, Rules and Memories for durable context, MCP for tools. The failure mode is infinite edit loops on an under-specified goal.

The Engineering Problem

An engineer opens Agent mode with “fix the flaky tests”. The agent touches twelve packages, renames utilities, and still fails CI. The thread is polluted. Starting over feels like defeat — so they keep prompting. Two hours later the branch is unreviewable.

Optimising @ Context

  • Prefer @file and @folder for the slice you are changing over “whole codebase”.
  • Attach the failing test output, not the entire CI log.
  • Attach AGENTS.md only when the agent is inventing commands — otherwise it should already be indexed via rules.
  • Exclude generated code, vendored trees and huge lockfiles from indexing where the product allows.

Memories and Rules Drift

Memories that say “we use poetry” while the repo uses uv will sabotage every Agent session. Audit Memories quarterly. Project Rules that always-apply should be short enough to read in one screen.

Trade-off

Kiro

If Kiro (or any agentic IDE) generates a specification artefact, a human still owns its correctness. Treat generated specs like generated code: review, then freeze acceptance tests that encode the spec before bulk implementation.

Workflow A — Learning

Learning mode uses agents to build mental models: spaced prompts, Socratic dialogue, notes and tests. Copying without running is the anti-pattern.

The Engineering Problem

Someone “learns RAG” by pasting a tutorial into chat, saving the answer, and never running a retriever. In the interview they recite vocabulary. In production they cannot debug a bad chunk. The agent accelerated illusion, not skill.

workflow=learning
items:
  1. State the concept you want to understand in one sentence
  2. Ask for a Socratic explanation, not a paste-ready solution
  3. Run a tiny experiment yourself before accepting an answer
  4. Write one note and one test that encode what you learned
  5. Mark Documented vs Inferred when quoting vendor or paper claims
hard_stops:
  - Do not merge learning-session code to main
  - Do not paste production secrets or customer code
Key Idea
  • The artefact of Workflow A is notes + a failing-then-passing test, not a PR.
  • Force the model to ask questions. If it only lectures, you are consuming, not learning.
  • Spaced repetition beats one mega-chat: revisit the same concept with a new experiment.
  1. Write one sentence: what you want to be able to explain tomorrow.
  2. Ask for a Socratic session; answer out loud or in a scratch buffer.
  3. Run a 20-line experiment (even a toy) yourself.
  4. Encode the invariant in a test under tests/ on a learning branch.
  5. File Documented vs Inferred claims in your note so marketing does not become memory.

Spaced Prompts and Mental Models

One marathon chat creates familiarity, not mastery. Prefer three short sessions across days:

  1. Day 0 — Socratic dialogue; you explain back; no code merge.
  2. Day 2 — rebuild the toy experiment from memory; ask only when stuck for five minutes.
  3. Day 5 — write a test that fails if the invariant is wrong; keep it.
Anti-pattern
  • “Explain like I’m five” forever. Eventually you must operate the real interface: pytest, git, the gate CLI.

Learning mode gains

  • Durable notes and tests.
  • Calibrated confidence.

Learning mode costs

  • Slower than vibe for demos.
  • Temptation to “just merge the learning branch”.

Anti-patterns

  • Copying solutions without running them.
  • Merging “learning” patches that rename production modules.
  • Asking for interview cheat-sheets instead of experiments.

Workflow B — Vibe Coding

Vibe coding is allowed: fast prototypes on throwaway branches with a time-box. It must stop before production. The skill is knowing when the vibe ends.

The Engineering Problem

A spike that felt magical becomes the production service because “we already have code”. There are no tests, no threat model and a hallucinated dependency. The vibe never ended; it was renamed “MVP”.

workflow=vibe
items:
  1. Create a throwaway branch with a time-box (e.g. 60–90 minutes)
  2. Write a one-line goal; refuse scope expansion mid-session
  3. Prefer disposable prototypes over production paths
  4. Capture what worked in a note; delete or quarantine the branch
  5. Stop when the timer ends — decide ship-gate or discard
hard_stops:
  - Do not open a production PR from a vibe session without Workflow C
  - Do not disable CI to keep the vibe going
  - Do not paste production secrets or customer code
Key Idea
  • Vibe coding maximises exploration rate, not merge readiness.
  • When the timer ends: discard, or promote through Workflow C (spec → tests → gates).
  • Package hallucination risk is highest here — never pip install an unfamiliar name without verification (Spracklen et al.).

Throwaway Branches as a Social Contract

Name vibe branches so humans are not confused: vibe/2026-03-29-widgets. Set a calendar or kitchen timer. When it rings, you may only: discard, note-take, or open a new ship branch that cherry-picks nothing until tests exist.

Risk
  • Vibe sessions are when people paste prod keys “to unblock”. Hard stop remains: never.
  • Slopsquatting risk peaks when the agent invents a package mid-flow and you install it to keep momentum.

Failure Modes

  • Renaming vibe/ to feature/ without Workflow C.
  • Disabling ruff “temporarily” to finish the demo.
  • No note — the only artefact is an unreviewable branch.
Trade-off
  • METR (Becker et al., 2025) found experienced developers can feel faster with AI while being slower on real tasks. Vibe sessions are especially prone to that miscalibration — use the timer, not the feeling.

Workflow C — Ship with Gates

Shipping is a pipeline: spec → tests → agent → review → static analysis → security → PR. Measure how often each gate catches defects. This extends Volume 23’s validation story into a daily coding-agent practice.

The Engineering Problem

CI is green on weak tests. A hallucinated package slipped in. Reviewers skim because the diff is “AI-generated so probably fine”. Production pages. The team blames the model. The missing object was a gate with a measured catch rate.

workflow=ship
items:
  1. Write acceptance criteria and failing tests first
  2. Bound the agent to specific files / packages
  3. Run the ship gate (lint, types, tests, security, deps)
  4. Human review: scope, security paths, hallucinated APIs
  5. Open a small PR; record gate failures caught before merge
hard_stops:
  - Do not merge without human review
  - Do not add dependencies without allow-list check
  - Do not paste production secrets or customer code

Over many PRs, track catch rate per gate as \mathrm{catch}_g = \frac{\#\{\text{PRs where } g \text{ failed before merge}\}}{\#\{\text{PRs that reached } g\}}. A gate that never fails is either perfect or unused — investigate which.

Multi-Tool Playbooks

Serious teams use more than one product. The skill is handoffs: ChatGPT plans, Cursor implements, Claude reviews — with conflict rules when tools disagree.

The Engineering Problem

Three engineers paste three incompatible designs from three tools into the same PR description. Debate becomes brand loyalty. Nobody owns the ADR. The merge is a coin flip.

Example handoff playbook (adapt; keep gates shared).
StageToolArtefact
Learn / planChatGPT or Claude chatOne-page spec + open questions (Workflow A/C)
ImplementCursor Agent or Claude CodeBounded diff + test output
ReviewOther model / Bugbot / humanChecklist findings, not vibes
MergeHuman + CIGreen gates; no tool may auto-merge
Key Idea
  • Parallel exploration is fine on throwaway branches. Serialise before merge.
  • When tools disagree: write a decision table (options × criteria), pick with evidence, record in an ADR.
  • Never “average” two incompatible patches. Choose one lineage and delete the other.

Playbook: Plan → Implement → Review

  1. Plan (ChatGPT or Claude chat): produce a one-page spec with acceptance bullets. No code.
  2. Freeze: human edits the spec; writes failing tests in the repo.
  3. Implement (Cursor Agent or Claude Code): bounds from the spec; paste gate output.
  4. Review (other model + human): second model proposes checklist findings; human verifies every claim against the diff.
  5. Merge: human only, CI green.
Brand loyalty failure
  • If the review model disagrees with the implement model, do not pick based on which vendor you like. Pick based on tests, threat model and maintainability.

Failure Modes

  • Three tools editing the same branch concurrently.
  • Review model rubber-stamping because the prompt said “be supportive”.
  • No ADR when architecture diverged.

Conflict resolution rules

  • Tests over prose: the design that passes the acceptance tests wins.
  • Security over elegance: if either tool’s patch weakens authz, reject both and redesign.
  • Smaller diff over cleverness: prefer the change a junior can maintain.
  • Documented over Inferred: when citing vendor limits, prefer Documented cells.

Team and Enterprise Practice

Individuals can improvise. Teams need shared rules repos, secrets hygiene, customer-code policies and productivity measures that are not vanity.

The Engineering Problem

Each engineer invents personal Cursor rules. Customer code ends up in consumer chat logs. Leadership asks for “AI productivity” and gets acceptance-rate screenshots. Nothing connects to escaped defects or time-to-revert.

Security callouts (non-negotiable)
  • Secrets: never paste production keys, tokens or .env contents into chat, Projects, Custom GPTs, Memories or MCP env blocks.
  • Customer code: treat proprietary customer repositories as regulated input — use approved enterprise tiers, DLP and redacted samples.
  • Production keys: rotate any key that might have entered a prompt. Assume logs are durable.

  • Tool lock-in is reduced by canonical AGENTS.md and open gates — not by banning all tools.

Quick Threat Reminders for Coding Agents

  • Review bots are untrusted advisors; they do not hold merge rights.
