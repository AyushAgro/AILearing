Data as the Primary Lever

At a fixed compute budget, the single largest controllable variable in a pretraining run is the data. Architecture changes move benchmark numbers by small amounts; data curation choices routinely move them by more. This chapter frames data work as an engineering discipline with measurable outputs, not a pre-processing chore.

The Engineering Problem

You have a fixed GPU budget that buys roughly C \approx 6ND FLOPs. Model size N and tokens D trade off, but every token you train on costs the same whether it is a well-written textbook paragraph or a cookie banner. The question is not "how much data can we get" but "which D tokens give the lowest loss on the capabilities we care about".

Why data dominates at fixed compute

  • Every token has the same price. Junk tokens do not merely fail to help; they displace useful tokens from a fixed budget.
  • Web text is mostly junk. Navigation, boilerplate, spam, machine-generated pages and duplicates make up the majority of raw crawl bytes.
  • Duplicates distort the objective. Repeated text is effectively upweighted, increases memorisation and wastes compute (Chapter 6).
  • Evidence from open pipelines. RefinedWeb, FineWeb and DCLM each reported that models trained on their curated web data matched or beat models trained on less-filtered data of the same size Documented (Penedo et al. 2023; Penedo et al. 2024; Li et al. 2024).
  • The web is finite. Estimates of the stock of high-quality public text suggest frontier runs are approaching it (Villalobos et al., approximate). Better filters and repetition policies matter more as the supply tightens.

The filtering funnel means raw crawl volume must be an order of magnitude or more above the training budget. The survival rates below are illustrative assumptions; measure your own.

Key Idea
  • Pipelines are funnels: multiplying survival rates quickly gives single-digit percentage yields.
  • A stage that removes "only" 10% more on a 30T-token crawl is a 3T-token decision. Every threshold is a budget decision.
  • Treat each stage like a query plan operator: know its selectivity, cost and error rate.

The Data Flywheel

  • Pretraining: filter and mix web-scale corpora. Feedback comes from small-scale ablation runs.
  • Post-training: instruction, preference and tool-use data. Feedback comes from evaluations and production traffic.
  • Production: user interactions, failures and ratings flow back (with consent and PII controls) into evaluation sets and fine-tuning data.
  • The flywheel only turns if every artefact is versioned and every model is traceable to exact data versions (Chapter 11).

Ablations: How Data Decisions Are Evaluated

  • Train small proxy models (hundreds of millions to a few billion parameters) on each data variant with identical token budgets.
  • Evaluate on benchmarks that give signal early in training (FineWeb and DCLM both used suites chosen for low variance at small scale) Documented.
  • Use several seeds or at least report seed variance; many filter differences are within noise at small scale.
  • Risk: rankings at small scale do not always transfer to large scale. DCLM studied this explicitly and found reasonable but imperfect transfer Documented (Li et al. 2024).

Collection

Collection decides what the model can ever know. It is also where provenance is either captured or lost for good.

The Engineering Problem

You need trillions of tokens from heterogeneous sources, each with different formats, licences and update cadences. Later stages must be able to answer "where did this token come from, when, and were we allowed to use it?" for any document, years later.

Common Crawl

  • A non-profit crawl released roughly monthly since 2008-era; each crawl covers billions of pages (approximate; varies by crawl).
  • Three formats per crawl:
    • WARC: raw HTTP request/response records including HTML. Largest; needed if you want your own extraction.
    • WAT: JSON metadata (headers, links) computed from WARC.
    • WET: plain text extracted by Common Crawl. Cheap, but the extraction keeps boilerplate and loses structure.
  • RefinedWeb and FineWeb extracted from WARC with trafilatura rather than using WET, reporting better downstream results Documented (Penedo et al. 2023, 2024). C4 used WET.
  • Files are gzip members concatenated per record, so they can be read in streaming fashion and split by byte offset; this is what makes them easy to shard across workers.

  • Why the offset matters: it lets you re-extract a single document with a new extractor without re-reading the whole crawl.

robots.txt, Terms and Opt-Out

  • robots.txt is advisory but it is the most widely recognised opt-out signal. Check it at crawl time and record the decision; the file can change later.
  • AI-specific user agents (for example crawler names used for training) let site owners block training while allowing search. Your crawler must identify itself honestly.
  • Common Crawl honours robots.txt for its own crawler, but its data predates later changes to a site's policy. Some pipelines re-apply current opt-outs at processing time Inferred.
  • Terms of service may prohibit scraping even where robots.txt allows it. Keep a domain-level policy table and join against it.
Collection is an attack surface
  • Split-view poisoning: datasets distributed as URL lists (for example image–text sets) can be poisoned by buying expired domains so the content at download time differs from curation time. Mitigate with content hashes recorded at curation (Carlini et al. 2024).
  • Front-running poisoning: if an attacker knows when a snapshot (for example of Wikipedia) is taken, a malicious edit only has to survive until the snapshot.
  • Treat any source an adversary can write to as untrusted input. Chapter 6 and Chapter 11 return to this.

Extraction and Normalisation

Extraction turns bytes into the text the tokeniser sees. Errors here are invisible to every later stage: a filter cannot remove boilerplate it cannot distinguish from content, and a tokeniser cannot recover a paragraph the extractor dropped.

The Engineering Problem

A typical HTML page is mostly navigation, scripts, ads, cookie banners and footers. The main content may be a few hundred words inside several kilobytes of markup. You need the main content, in reading order, with paragraph structure, in a single canonical Unicode form, labelled with its language.

Possible solutions

  • Tag stripping: fast, keeps all boilerplate. Does not solve main-content detection.
  • Block heuristics (text density, link density, stop-word ratio; jusText, boilerpipe, trafilatura): good default. Does not handle unusual layouts or JavaScript-rendered pages.
  • DOM / visual models: best quality on hard pages. Too expensive for billions of pages.
  • Common Crawl WET: free, but keeps menus and footers, so later filters must work harder.

How Block-Based Extraction Works

  • Parse the DOM; drop subtrees that are almost never content (script, style, nav, footer, form).
  • Split the rest into blocks at block-level tags.
  • Score each block: word count, link density (characters inside anchors ÷ block characters), stop-word density, keyword patterns ("cookie", "all rights reserved").
  • Keep blocks that look like prose. Production extractors also use context: a short block between two content blocks is probably content.
\text{link\_density}(B) = \frac{\sum_{a \in \text{anchors}(B)} |a|}{|B|}

Language Identification

  • Production pipelines use character n-gram classifiers such as fastText lid.176 (CCNet, RefinedWeb, FineWeb) or CLD3 Documented. They are fast (microseconds per document) and cover about 176 languages.
  • The threshold matters. FineWeb kept English documents with fastText score ≥ 0.65; C4 used langdetect with probability ≥ 0.99 Documented.
  • Failure modes: short texts, code-switching, closely related languages (Bosnian/Croatian/Serbian, Hindi/Urdu in Latin script), and dialects labelled as "low quality" by thresholds tuned on standard varieties.
Bias enters here
  • A strict language threshold removes dialectal English and code-switched text disproportionately. Measure retention rates per region or dialect on a labelled sample before choosing a threshold.

PDF and Document Extraction

  • PDF stores glyphs at positions, not text in reading order. Two-column layouts, footnotes, headers and tables are the main failure sources.
  • Options, in increasing cost: text-layer extraction (pdfminer, PyMuPDF), layout-aware parsing, OCR, and vision-language models trained to emit Markdown/LaTeX (Nougat-style).
  • Equations are the hardest case; for scientific text, sources with LaTeX (arXiv) beat PDF extraction.
  • Evaluate on a small hand-labelled set with edit distance against gold text, per layout type.

Heuristic Quality Filtering

Heuristic filters are cheap, interpretable rules that remove documents which are obviously not natural prose. They run before expensive stages and typically remove a large share of the extracted web.

The Engineering Problem

After extraction and language ID you still have spam, keyword-stuffed pages, product listings, tables of numbers, code fragments, auto-generated text and pages dominated by repetition. You need filters that run at hundreds of thousands of documents per core-second and that you can explain to a reviewer rule by rule.

Possible solutions

  • Hand rules (this chapter): cheap, auditable. Do not capture "is this well written".
  • Perplexity filters: capture fluency relative to a reference. Bias towards the reference domain.
  • Learned classifiers (Chapter 5): capture a target notion of quality. Need labels; less auditable.

C4 Rules

  • C4 (Raffel et al. 2020) worked at line level on WET text Documented:
    • Keep only lines ending in terminal punctuation, with at least three words.
    • Drop pages with fewer than five sentences.
    • Drop lines containing "javascript"; drop pages with "lorem ipsum", a curly brace, or a word from a bad-words list.
    • Deduplicate three-sentence spans; keep English with langdetect probability ≥ 0.99.
  • The curly-brace rule removes most code; the bad-words list was later shown to disproportionately remove text about and by minority groups (Dodge et al. 2021) Documented.

  • Each rule returns its reason, not just a boolean. Logging reasons lets you compute a removal histogram per rule, which is how you find a rule that is silently eating good data.
  • The toy C4 variant uses three sentence-lines instead of five because the fixtures are tiny.
  • Note the lorem case: Gopher passes it and C4 removes it. Rules are complementary; pipelines stack several families.
Engineering the filter stage
  • Implement as a pure function doc -> (keep, reason, features). Persist features (a few floats) rather than decisions so thresholds can change without recomputation.
  • This is predicate push-down: run the cheapest, most selective rules first.
  • Sample 100 removed and 100 kept documents per rule for human review before every threshold change.
  • Domain collateral: mean-word-length and alphabetic-ratio rules remove maths, chemistry and code. Route those domains around the web filters.
  • Language assumptions: stop-word lists and word-length ranges are English-specific. Chinese and Japanese have no spaces; Finnish has long words.
  • Poetry and lists: legitimate repetition (lyrics, liturgy, recipes) fails repetition rules.
  • Adversarial SEO spam is written to pass these rules. That is why model-based filters exist.

Model-Based Quality Filtering

Heuristics remove what is obviously not prose. Model-based filters try to select what is useful: fluent, informative, educational text. They are the largest single lever in recent open datasets, and the most opinionated.

The Engineering Problem

After heuristic filtering, most surviving pages are grammatical but uninformative: product descriptions, thin SEO articles, forum noise. You want a scalar quality score per document, cheap enough for billions of documents, that correlates with downstream benchmark gains.

Perplexity Filtering

  • Train a small language model on a reference corpus (CCNet used a 5-gram KenLM model on Wikipedia) and score each document by perplexity Documented (Wenzek et al. 2019).
  • Low perplexity means "looks like the reference". CCNet bucketed documents into head, middle and tail by perplexity percentile per language.
\text{PPL}(x) = \exp\!\Big(-\frac{1}{T}\sum_{t=1}^{T} \log p_{\text{ref}}(x_t \mid x_{t-1})\Big)
  • What it does not solve: the reference defines "quality". A Wikipedia reference penalises dialogue, fiction, informal and non-standard text; it also rewards boring, repetitive text that has low perplexity.

Classifier Filtering

  • Train a binary classifier: positives from a "high-quality" source, negatives from random web text. Score is the log-odds of the positive class.
  • GPT-3 used a classifier with WebText, books and Wikipedia as positives Documented (Brown et al. 2020).
  • DCLM trained a fastText bigram classifier with instruction-style data (OpenHermes and ELI5 answers) as positives and RefinedWeb samples as negatives, and found it beat several alternatives in their ablations Documented (Li et al. 2024).
  • With naive Bayes the score for document x with words w_1..w_T is
s(x) = \log\frac{P(+)}{P(-)} + \sum_{t=1}^{T}\log\frac{P(w_t\mid +)}{P(w_t\mid -)},\qquad P(w\mid c)=\frac{n_{c,w}+1}{n_c+|V|}

Reading the result

  • Both methods separate the easy cases. Both are fooled by the ten "junk written in good style" documents: loosening the threshold admits them and precision drops to 0.89.
  • The perplexity filter at the strictest threshold loses recall on good documents with a navigation tail appended. This is the extraction–filter interaction: poor extraction lowers perplexity-based scores of good pages.
  • Thresholds are chosen on keep rate as much as precision: the token budget sets how much you can afford to discard.

LLM-Annotated Quality Labels (the FineWeb-Edu Pattern)

  • Prompt a strong LLM to rate a sample of documents (FineWeb-Edu: roughly 450k documents, rated 0–5 for educational value by Llama-3-70B-Instruct) Documented.
  • Train a cheap regressor on embeddings of those documents to predict the rating; apply it to the whole corpus.
  • Threshold: FineWeb-Edu kept documents scoring ≥ 3, reducing FineWeb's roughly 15T tokens to roughly 1.3T tokens, with large gains on knowledge and reasoning benchmarks such as MMLU and ARC Documented (Penedo et al. 2024; figures approximate).

Threshold Selection

  • Plot keep rate against proxy-model benchmark score for several thresholds. The curve usually rises then plateaus or falls as diversity drops.
  • Aggressive filtering trades quality for repetition: a smaller pool means more epochs for the same budget. Muennighoff et al. (2023) found up to about four epochs of repetition costs little, with diminishing returns beyond Documented.
  • Prefer soft filtering (use the score to set sampling weight) over hard cut-offs when you are near the repetition limit.

Advantages

  • Captures quality notions rules cannot express.
  • fastText-class models score millions of documents per core-hour.
  • Target is explicit and changeable (edit the rubric).

Disadvantages

  • Imports the biases of the positive set or annotator LLM.
  • Narrows diversity; optimises benchmarks that resemble the positive set.
  • Hard to audit why a document was removed.
Benchmark leakage through the filter
  • If the positive set or rubric is tuned to "look like" a benchmark, the filter selects benchmark-like text. Gains may be partly contamination by style. Run Chapter 10 checks on the filtered output, not only the input.

Deduplication

The web is massively redundant: mirrors, syndicated news, templated pages, license texts and boilerplate. Deduplication is a join on similarity at trillion-token scale, and it is one of the few data interventions with consistently positive published results.

The Engineering Problem

You have billions of documents. Some are byte-identical, many are identical up to whitespace or a date, and many share long passages. You need to remove redundancy without an all-pairs comparison (\sim 10^{18} pairs for 10^9 documents).

Why deduplicate

  • Lee et al. (2022) found duplicated sequences are memorised and regurgitated far more often, and that deduplicated training reached similar or better perplexity with fewer steps Documented.
  • Duplicates silently change the mixture: a boilerplate page repeated 100k times is a 100k× upweight.
  • Duplicates between train and test inflate evaluation (Chapter 10).

MinHash: Estimating Jaccard Without Comparing Sets

Represent a document by its set of word k-shingles S. For a random hash function h, the probability that two sets share the same minimum hash equals their Jaccard similarity (Broder 1997):

J(A,B) = \frac{|A\cap B|}{|A\cup B|} = \Pr_h\big[\min_{a\in A} h(a) = \min_{b\in B} h(b)\big]

With m independent hashes the estimator and its standard error are

\hat J = \frac{1}{m}\sum_{i=1}^{m} \mathbf{1}\big[\text{sig}_i(A)=\text{sig}_i(B)\big],\qquad \operatorname{SE}(\hat J)=\sqrt{\frac{J(1-J)}{m}}
  • With m=128 and J=0.9, SE ≈ 0.027. The listing below measures 0.883 against a true 0.903.
  • Hash family: h_i(x) = (a_i x + b_i) \bmod p over a 64-bit base hash, with p = 2^{61}-1.

LSH Banding

Split each signature into b bands of r rows. Two documents become candidates if any band matches exactly. For a pair with Jaccard s:

\Pr[\text{candidate}] = 1-\big(1-s^{r}\big)^{b},\qquad s^{*} \approx \Big(\frac{1}{b}\Big)^{1/r}

  • b=8, r=16 (threshold ≈ 0.88) misses three quarters of the pairs: the S-curve is in the wrong place for a 0.5 target.
  • The single false positive is a pair with true Jaccard just below 0.5 whose estimate landed above. Verifying against exact Jaccard removes it at extra cost.
  • After candidate generation, build a graph and take connected components (union–find); keep one document per component.

Suffix-Array Substring Deduplication

  • Concatenate all tokens, build a suffix array, and find repeated spans of at least k tokens (Lee et al. used 50) by scanning adjacent suffixes for long common prefixes.
  • Removes shared boilerplate inside otherwise distinct documents, which MinHash misses.
  • Cost: memory proportional to the corpus in tokens times pointer width; built in shards and merged. RefinedWeb applied it after MinHash Documented.
  • Risk: removing spans can leave documents incoherent; drop documents with too much removed.

Scale Trade-offs

  • Map: per document, compute shingles and a signature (CPU-bound; embarrassingly parallel).
  • Shuffle: emit (band_id, band_hash) -> doc_id; group by key. This is the expensive shuffle; the number of rows is n \cdot b.
  • Reduce: emit edges for buckets with more than one document; cap bucket size to avoid quadratic blow-ups on templates.
  • Connected components: distributed union–find or iterative label propagation.
  • Global vs per-snapshot: FineWeb found deduplicating each crawl separately beat global dedup in their ablations, arguing global dedup disproportionately kept low-quality survivors Documented. This is contested and corpus-dependent.
  • Template collapse: forum threads sharing a large template exceed the threshold although content differs. Shingle only the extracted main content.
  • Giant components: transitive chains (A~B, B~C) merge unrelated documents. Cap component size or verify against the representative.
  • Keeping the wrong copy: choose the representative by quality score or earliest crawl, not arbitrarily.
  • Over-dedup of valuable repeats: licences, legal texts and famous quotations are legitimately repeated; decide whether you want the model to know them.
Dedup as a poisoning defence and target
  • Poisoning often relies on repetition to make a payload learnable. Near-dedup reduces its effect.
  • An attacker who knows your shingle size and threshold can vary text just enough to evade dedup. Do not publish exact parameters for private pipelines, and combine with substring dedup.

PII and Safety Filtering

Models memorise rare strings seen several times. Anything that reaches the training set may be extractable later, so personal data and harmful content must be controlled before training, with an audit trail that proves it was.

The Engineering Problem

Web and user data contain emails, phone numbers, card numbers, government IDs, addresses, names and credentials. You must detect them at high recall, without destroying useful text (version numbers, ISBNs, maths), and decide per document whether to redact, drop or keep.

Detection options

  • Regex: high recall for structured PII (email, IP, phone). Precision is poor on digit strings without validation.
  • Checksum validators: Luhn for payment cards, mod-97 for IBAN, national ID check digits. Dramatically improve precision.
  • NER models (spaCy, Presidio, transformer taggers): names, addresses and organisations. Slower; recall varies by language and domain.
  • Secret scanners for code: API key formats and entropy tests (as in detect-secrets-style tools).

The Luhn Checksum

Double every second digit from the right, subtract 9 from results above 9, and sum. Valid card numbers satisfy

\Big(\sum_{i} d'_i\Big) \bmod 10 = 0

A random digit string passes with probability 0.1, so Luhn removes about 90% of false card matches.

Implementation

('KEEP', 'Contact <|EMAIL|> or call <|PHONE|> for details.')
('KEEP', 'Card <|CARD|> was charged; order no 4111 1111 1111 1112.')
('KEEP', 'US office: <|PHONE|>. Server at <|IPV4|>, version 3.14.159.')
('DROP', None)
True False
  • The second sample keeps the order number: it matches the card pattern but fails Luhn.
  • The version string 3.14.159 is not tagged as an IP; the octet-bounded pattern prevents it.
  • The fourth document has more than three PII hits and is dropped entirely: dense PII signals a leak dump, not prose with incidental contact details.
  • Typed placeholders (<|EMAIL|>) preserve sentence structure; use tokens the tokeniser treats atomically, or the model learns to emit fragments of them.

Toxicity and Safety Filtering

  • Classifiers (for example trained on Jigsaw-style data) or word lists flag hateful, sexual and violent content. Dolma released its toxicity and PII taggers alongside the data Documented.
  • Aggressive toxicity filtering removes text about toxicity, which the model needs to recognise and refuse harmful requests, and disproportionately removes dialects and identity terms (Dodge et al. 2021).
  • Common approach: remove the clearly harmful tail (CSAM: always, with hash-matching; extremist propaganda), and let post-training handle behaviour for the rest.

Audit Trails

  • Log per document: detector version, hit counts by type, action taken. Never log the detected PII values themselves.
  • Keep a stratified sample of redacted outputs for periodic human review of recall.
  • Evaluate on a labelled set per locale: recall matters more than precision for PII, so report recall with confidence intervals.
Security
  • Raw stages of the pipeline hold unredacted PII. Apply the same access control as a production customer database: encryption, least privilege, retention limits.
  • Credentials in code data (AWS keys, tokens) are PII-like and actively exploited. Scan code with secret detectors and drop or redact.
  • Data extraction attacks (Carlini et al. 2021) recover verbatim training strings; memorisation is the threat model to test against.

Dataset Mixtures

A training set is not a pile of documents; it is a sampling distribution over domains. The mixture decides which capabilities get compute.

The Engineering Problem

You have many sources of very different sizes: tens of trillions of web tokens, a few hundred billion code tokens, tens of billions of books, papers and maths. Sampling in proportion to size gives the small, valuable domains almost no weight; sampling uniformly repeats them dozens of times.

Temperature-Based Domain Weights

Let n_i be the tokens available in domain i and p_i = n_i / \sum_j n_j. Temperature sampling sets

w_i = \frac{p_i^{1/T}}{\sum_j p_j^{1/T}}, \qquad \text{epochs}_i = \frac{w_i \, D}{n_i}
  • T=1: proportional. T\to\infty: uniform.
  • Used for multilingual balance (XLM-R and mT5 used \alpha = 1/T = 0.3) Documented.
  • The epochs column is the real constraint: a small domain upweighted too far is repeated past the point of useful returns.
domain   T=1     T=2     T=5     epochs@T=2
web      0.835  0.569  0.314     0.11
code     0.134  0.227  0.218     0.28
books    0.017  0.080  0.144     0.80
papers   0.010  0.062  0.130     1.04
wiki     0.003  0.036  0.104     1.80
math     0.002  0.025  0.091     2.54
{'web': 0.569, 'code': 0.226, 'books': 0.081, 'papers': 0.062, 'wiki': 0.036, 'math': 0.025}
  • At T=2 the maths domain is seen 2.5 times and wiki 1.8 times within a 1T budget; web is seen only 11%.
  • The sampler draws domain first, then a document within the domain. Seeded sampling makes the stream reproducible and resumable.

Upsampling, Epochs and Curriculum

  • Upsampling small high-quality domains is common; The Pile explicitly assigned per-component epochs (for example more than one pass over Wikipedia and books) Documented (Gao et al. 2020).
  • Repetition limits: returns diminish after a few epochs (Muennighoff et al. 2023). Beyond that, prefer more diverse data to more repetition.
  • Curriculum / annealing: many recent training reports describe raising the share of high-quality, maths and code data in the final phase while the learning rate decays Documented (for example the Llama 3 report). Ordering effects are otherwise small and hard to measure.

DoReMi-Style Mixture Optimisation

  • DoReMi (Xie et al. 2023): train a small reference model on a default mixture; then train a small proxy with Group DRO that upweights domains where the proxy's excess loss over the reference is highest; use the averaged weights for the large model Documented.
\alpha_i^{(t)} \propto \alpha_i^{(t-1)} \exp\!\big(\eta \, \max(0,\ \ell_i(\theta_{\text{proxy}}) - \ell_i(\theta_{\text{ref}}))\big)
  • Alternatives: regression-based mixing laws that fit loss as a function of mixture weights from many small runs (RegMix, data mixing laws); grid search over a few candidate mixtures at proxy scale.
  • What none of them solves: the target. Optimising average perplexity is not the same as optimising the capabilities you ship.
  • Hidden domain definitions: "web" contains code, maths and news. Domain labels from URL are noisy; weights apply to labels, not content.
  • Silent over-repetition when a source shrinks after re-filtering but weights stay fixed. Recompute epochs on every data version.
  • Non-resumable samplers: a restart that reseeds changes the data order. Store sampler state in the checkpoint.

Synthetic Data

Synthetic data (text generated by models) is now a major input to post-training and increasingly to pretraining. It is cheap and controllable. It is also a closed loop that can erode the diversity it was meant to add.

The Engineering Problem

You need more data in a narrow capability (maths reasoning, tool calls, a low-resource language) than exists naturally. A strong model can generate it, but generated data inherits the generator's errors and biases, concentrates on its most likely outputs, and may carry licence restrictions.

Diversity Control and Verification

  • Diversity: vary seeds, personas, formats and temperatures; measure with distinct n-grams, embedding coverage, and MinHash duplicate rates (reuse Chapter 6).
  • Verification: execute code, check maths answers symbolically, use a judge model with a rubric, and sample for human review.
  • Filter synthetic data with the same pipeline as real data, including decontamination: generators reproduce benchmark items they memorised.

Model Collapse

Shumailov et al. (2024) showed that models trained recursively on their own outputs progressively lose the tails of the distribution Documented. The mechanism is visible in a categorical toy model: sampling a finite set and refitting cannot recover a token that was not sampled.

  • With pure self-training, support shrinks from 1,000 to 253 tokens in ten generations and entropy falls steadily: the tail disappears first.
  • Mixing 20% fresh real data each generation stabilises support at around 540 (finite sampling still limits it), rather than falling indefinitely. Accumulating real data rather than replacing it is the published mitigation (Gerstgrasser et al. 2024) Documented.
  • The web itself is increasingly model-generated, so collapse pressure applies to crawls, not only to deliberate synthetic sets. Crawl-date provenance lets you weight older snapshots.
Licensing of generated data
  • Some model terms restrict using outputs to train competing models. Record the generator model, version, and terms in lineage for every synthetic shard.
  • Generated text can reproduce copyrighted or personal data memorised by the generator. Run PII and near-dup checks against known sources.

Contamination

A benchmark measures generalisation only if the model has not seen the test items. Web-scale corpora contain many benchmarks verbatim, and the evaluation is worthless unless you check.

The Engineering Problem

Benchmark questions are published on GitHub, copied into forums, quoted in papers and scraped into crawls. You need to find training documents that contain test items, remove them (or report them), and quantify how much contamination changes the scores.

n-gram Overlap Detection

  • Index all n-grams of every benchmark item; stream training documents and look up their n-grams.
  • GPT-3 used 13-gram overlap; later reports use 8–13 grams with various thresholds Documented.
  • Score per item: fraction of the item's n-grams found in a document.
\text{overlap}(q, d) = \frac{|G_n(q) \cap G_n(d)|}{|G_n(q)|}
forum      overlap={'q1': 1.0} contaminated=True
paraphrase overlap={} contaminated=False
clean      overlap={} contaminated=False
canary found: False
  • The forum copy is caught with full overlap. The paraphrase is not: n-gram methods miss rephrased and translated contamination.
  • For semantic contamination, add embedding similarity or an LLM judge on top candidates. Expect lower precision and review manually.
  • At scale the benchmark index is small (millions of n-grams) and fits in memory or a bloom filter broadcast to every worker. It is a broadcast hash join.

Canaries

  • BIG-bench introduced a canary GUID string to embed in benchmark files, so data pipelines can drop any document containing it and model developers can test whether a model can complete it Documented.
  • Canaries only work if (a) benchmark authors include them and (b) copies preserve them. Scrapers and reposts often do not.

Decontamination and Reporting

  • Remove contaminated documents from training (or the overlapping spans), before training. Afterwards you can only report.
  • Report per benchmark: fraction of items contaminated, and score on clean vs contaminated subsets. A large gap indicates leakage affects the number.
  • Use held-out, private or freshly written evaluation sets for decisions (Volume 10). Dynamic benchmarks with post-cutoff items limit the problem.
  • Tokenisation mismatch: n-grams on words vs tokens vs normalised text give different results. Normalise both sides identically.
  • Short items: items with fewer than n words have no n-grams. Fall back to full-string match.
  • Common phrases: boilerplate n-grams ("which of the following is") create false positives. Drop n-grams that are frequent in the training corpus.
  • Contamination via filters and synthetic data (Chapters 5 and 9): scan the final mixture, not only raw inputs.

Versioning, Lineage and Data Cards

A model is a function of its data. If you cannot name the exact bytes a model was trained on, you cannot debug it, reproduce it, delete from it, or defend it.

The Engineering Problem

The pipeline has a dozen stages, each rerun many times with changing code and thresholds. Months later someone asks which crawl snapshots, filter versions and dedup parameters produced the data behind a checkpoint, or requests deletion of one URL. The answers must be exact.

Simple Version

  • Write immutable shards. Name each shard by its content hash.
  • For each stage output, write a manifest listing shard hashes, parent manifest versions and the stage config hash.
  • The manifest's own hash is the dataset version. Training checkpoints record it.
{"dataset": "web-dedup", "version": "3ad0b44ecd242213", "parents": ["8fe198536967bbc8"], "config_sha": "ee2d5daec5bf"}
{'path': 'shard-413c3d2b37ce.jsonl', 'sha256': '413c3d2b37ce7e1d901d35d0effbb88ad821363df25899c613c1ab9fbde6be0a', 'n_docs': 3, 'bytes': 173}
{'path': 'shard-8b6cf9150c5a.jsonl', 'sha256': '8b6cf9150c5ae703971d1f5cf146e92107f2ff64f078741aa1f4406ec9f45574', 'n_docs': 2, 'bytes': 115}
tampered shards: ['shard-8b6cf9150c5a.jsonl']
  • Changing any shard, parent or config changes the version: the manifest is a Merkle-style commitment.
  • Verification catches the tampered shard. Run it before every training job reads data; it is also the defence against the split-view poisoning of Chapter 2.

Production Version

  • Storage: object store with Parquet or JSONL.zst shards; table formats (Iceberg, Delta) or tools like lakeFS/DVC for snapshots and time travel.
  • Document IDs: stable ID from (source, URL, crawl, offset) so that deletion can be joined through every stage.
  • Orchestration: stage DAG in Airflow, Dagster or similar; each task idempotent and keyed by (input version, config hash) so reruns are cache hits.
  • Processing: Spark or Ray Data for shuffles (dedup, contamination join); plain batch jobs for embarrassingly parallel map stages (extraction, filters). DataTrove (FineWeb) and the Dolma toolkit are open examples Documented.
  • Data cards: generated from manifests, not written by hand.
  • Deletion requests mutate "immutable" data: implement as a new version with a tombstone list, and track which checkpoints predate it.
  • Nondeterminism (thread scheduling in dedup, floating-point classifier scores on different hardware) breaks bit-exact reproducibility; record outputs, not just code.
  • Petabyte-scale lineage at document level is itself a large dataset; store it as a table, not as graph metadata.

Datasheets and Data Cards

  • Datasheets for Datasets (Gebru et al. 2021) poses questions on motivation, composition, collection, preprocessing, uses, distribution and maintenance Documented.
  • Minimum card content for a training mixture:
    • Sources, crawl dates, licences, and opt-out policy applied.
    • Every stage with version, config hash and removal rate.
    • Token counts per domain, mixture weights and epochs.
    • PII and toxicity policies with measured recall on labelled samples.
    • Decontamination: benchmarks checked, method, fraction removed.
    • Known biases and gaps (languages, dialects, domains removed by filters).

Ablations

Failure Modes

  • Extractor drops headings, tables or code; downstream filters cannot recover it.
  • Language and quality thresholds remove dialects and minority-group text disproportionately.
  • Heuristics remove maths and code; route specialist domains separately.
  • Quality classifiers overfit to benchmark-like style; gains partly contamination.
  • LSH parameters put the S-curve in the wrong place; recall collapses silently.
  • Transitive dedup components merge unrelated documents.
  • PII regexes without validators destroy numbers; without NER they miss names.
  • Mixture weights not recomputed after re-filtering; small domains over-repeated.
  • Synthetic data narrows distributions; model collapse.
  • Paraphrased benchmark contamination not caught by n-grams.
  • Unverified shards allow poisoning or silent corruption.

Evaluation

  • Per stage: keep rate, removal reasons histogram, and human-reviewed precision/recall on stratified samples.
  • Dedup: precision/recall against exact Jaccard on a sampled pair set; component size distribution.
  • PII: recall per type and locale with confidence intervals.
  • End to end: proxy-model ablations with fixed token budgets and several seeds.
  • Contamination: fraction of benchmark items contaminated; clean vs contaminated score gap.

Practical Project

  • Take one WARC file (about 1 GB compressed) from a recent Common Crawl snapshot.
  • Run the forge.data pipeline: extract, LID, heuristics, MinHash dedup, PII scrub, contamination check against two public benchmarks.
  • Emit manifests for every stage and a generated data card with token counts and removal rates.
  • Replace your MinHash with datasketch and confirm the candidate sets agree to within sampling error.
  • Hand-label 200 removed documents per stage and report per-stage precision.

Exercises

  1. Derive the threshold approximation s^* \approx (1/b)^{1/r} from the banding probability.
  2. Choose b, r with br \le 128 so that pairs with J=0.8 are caught with probability ≥ 0.99 and pairs with J=0.5 with probability ≤ 0.05.
  3. Add a context rule to the extractor so headings between content blocks are kept. Measure the change on 20 hand-labelled pages.
  4. Add IBAN detection with the mod-97 checksum to the PII scrubber.
  5. Extend the collapse simulator to accumulate (not replace) real data each generation and compare support curves.
  6. Replace n-gram contamination with MinHash similarity between benchmark items and documents. What does it catch that 8-grams do not?
  7. Compute epochs per domain for T \in \{1,2,3,5\} and pick the largest T with no domain above four epochs.
