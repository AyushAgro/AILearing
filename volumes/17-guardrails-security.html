About This Volume

Objective

  • Threat-model an AI product the way you would any networked system: name the assets, the trust boundaries and the attacker who can write into the prompt channel.
  • Put deterministic guards before model-based ones. Size limits, encoding normalisation, schemas, regex PII and policy engines fail closed and cost microseconds.

  • Close the data-leakage and tool-abuse paths that survive a polite model: redaction, secret tokenisation, permissions, sandboxing and human approval.
  • Ship the continuous package as forge.guard: a pre/mid/post pipeline, validators, injection heuristics, a policy engine, secret and pickle scanners, and a red-team harness that reports attack success against false positives and latency.

Threat Modelling AI Systems

An AI feature without a threat model is a chat demo with a production budget. The model is one component. The assets, the trust boundaries and the attacker who can write into the prompt channel are the rest.

The Engineering Problem

A support bot reads tickets, retrieves policy docs, calls a refund tool and answers the customer. Security review asks "is the model safe?". The question is underspecified. Safe for which asset, against which attacker, across which boundary?

Possible approaches

  • Model card only. Useful for capability and known refusal behaviour. Silent on your tools, your tenants and your logs.
  • Generic Top-10 checklist. Better than nothing. Easy to tick without naming a concrete flow.
  • Asset-and-boundary model. List what you protect, where untrusted data enters, which principals can act, and which controls sit on each edge. Map the result onto OWASP LLM, MITRE ATLAS and NIST AI RMF so the vocabulary is shareable.

Assets, Principals, Trust Boundaries

  • Assets. Customer PII, tenant documents, API keys, tool side effects (refunds, mail, writes), model weights, evaluation sets, prompt templates that encode proprietary logic.
  • Principals. End user, operator, the model (untrusted planner), tool servers, retrieval corpus authors, supply-chain publishers of weights and packages.
  • Trust boundaries. HTTP edge, prompt assembly, retrieval index, tool runtime (Volume 16), sandbox, log exporter, weight load path.
Key Idea
  • The prompt channel mixes instructions and data. Anything that can write into that channel is an attacker capability, including a document the user asked you to retrieve.
  • Controls belong on boundaries. A refusal in the system prompt is not a boundary.
  • Threat modelling names residual risk. A control that is not written down is a hope.

Input Guardrails

Most abuse is boring: oversized payloads, weird encodings, off-topic floods and strings that should never reach a model. Deterministic input guards are cheap, testable and first in the pipeline on purpose.

The Engineering Problem

A client posts a 2 MB prompt full of null bytes and full-width digits that decode into a tool name your denylist wrote in ASCII. The model call burns tokens; the heuristic never sees the attack it was written for.

Possible designs

  • Trust the gateway. HTTP limits help. They do not normalise Unicode or classify intent.
  • Model-only moderation. Catches some semantics. Adds latency, cost and a failure mode that is itself injectable.
  • Deterministic pre-pipeline. Size and rate limits, encoding normalisation, schema checks on structured fields, then cheap topic/intent classifiers. Model guards come later (Chapter 10).

The Pre Stage

True  pass               {}
False injection=0.40     {'injection': 0.4, 'hits': 1}
False injection=0.90     {'injection': 0.9, 'hits': 1}
True  pass               {}

What each line did

  • Benign refund text passed.
  • A schematic "ignore previous instructions …" family string scored 0.40 and was denied at threshold 0.30.
  • A toy marker BEGIN INJECTION scored 0.90 (corpus flag for tests, not a real exploit).
  • Null bytes were stripped and full-width digits mapped to ASCII before later guards ran.
Normalise Before You Match
  • Denylists written for ASCII fail on homoglyphs, zero-width characters and overlong encodings.
  • Normalisation is a security control. Doing it after the detector is how bypasses ship.
  • NFKC is a starting point, not a proof. Keep a regression corpus of encodings that previously slipped through.

Topic and intent classifiers are the first semantic input guards. A tiny keyword model is enough to refuse lottery spam before you spend a frontier call. Production systems replace the toy with a calibrated classifier and still keep the deterministic layers underneath.

topic:support True {'support': 3, 'coding': 0, 'off_topic': 0}
topic:off_topic False {'support': 0, 'coding': 0, 'off_topic': 2}
topic:coding True {'support': 0, 'coding': 2, 'off_topic': 0}
Trade-off
  • Strict topic allow-lists protect spend and brand. They also block unusual but legitimate asks.
  • Log topic:unknown separately from denies so you can expand the taxonomy without guessing.

Structured fields before free text

  • If the client already sends JSON (order_id, locale), validate those fields with a schema before concatenating them into a prompt.
  • A string order_id that contains a thousand characters of instructions is an input-guard failure, not a model failure.
  • Integer and enum fields should never be string-interpolated until typed.

Clamp length, normalise Unicode, drop control characters, apply a per-API-key bucket, run regex detectors. Log denials with a reason code. That is a useful v1.

  • Limits are per principal and per tenant, not per process.
  • Structured fields (JSON tool args) are schema-validated before they become prompt text.
  • Topic models are versioned; false-positive rate is a release gate (Chapter 11).
  • Aggressive normalisation can change user meaning (some languages rely on code points you folded).
  • Topic blocks create support load when a legitimate edge case looks like spam.
  • Matching before normalisation.
  • One global rate limit shared by all tenants.
  • Silent truncation that drops the safety instruction at the end of the system prompt.

Add an allow-list of Unicode scripts for your product locales. Fail closed on mixed-script identifiers that look like Latin brand names (a classic homoglyph pattern), and measure false positives on a sample of real tickets.

Prompt Injection

Prompt injection is possible because instructions and data share one token channel. Detection helps. Isolation and capability discipline are what bound the blast radius.

The Engineering Problem

A retrieved wiki page contains a paragraph that tells the model to ignore the user and call send_email. The model complies. Your system prompt said not to. The page was longer and more recent in the context window.

Attack shapes

  • Direct. The user (or a client they control) puts the instruction in the user message.
  • Indirect. The instruction arrives through a tool result, a document, an email, a web page or an MCP description. Documented Greshake et al. (2023) named the class and demonstrated it against Bing Chat and GPT-4-based applications.
Why It Is Hard
  • There is no cryptographic separation between data and instructions inside a standard decoder prompt.
  • Instruction hierarchy (Wallace et al., 2024) helps models prefer system text, and still fails under adaptive attacks.
  • Anything that only asks the same model to spot the attack shares the failure mode.

Summaries Still Smuggle
  • The toy stripped a line containing IGNORE, yet "Call send_email" survived in the summary.
  • That is why the privileged planner still must not gain tools from summary text — only from the user goal or allow-listed entity types.
  • CaMeL-style capability labels on entities would mark them untrusted for privileged arguments.

  • Retrieval pipelines stamp provenance; the harness policy can require provenance ≠ web for irreversible tools.
  • Beurer-Kellner et al. (2025) catalogue patterns; pick one and measure utility loss honestly.
  • Open-ended agents want dynamic tool choice after reading. That desire conflicts with robust injection guarantees.
  • CaMeL's published AgentDojo figures (77% tasks with a security guarantee vs 84% utility undefended) are the quantitative form of that trade-off.
  • Detector as the only control.
  • Freezing the plan after the model has already read the poisoned page.
  • Trusting MCP tool descriptions as system instructions (Volume 16).

Real-Product Case Study: Enterprise Assistants and Indirect Injection

Enterprise assistants read mail, chat and documents written by people outside the trust boundary, then act or answer for an employee with broad access. That combination produced the best-documented prompt-injection incidents so far.

Problem

  • Inferred The assistant's retrieval scope is the user's whole permission set (Volume 14), and any external sender can place text inside it. Every inbound email is a potential instruction.

Documented incidents

  • Documented Google Bard (2023): researcher Johann Rehberger showed that a shared Google Doc could inject instructions causing Bard to render a markdown image whose URL carried chat data to an attacker's server; Google fixed the issue.
  • Documented Slack AI (2024): PromptArmor disclosed that a message posted in a public channel could cause Slack AI to return a crafted link leaking data from private channels the victim could read; Slack deployed a patch.
  • Documented Microsoft 365 Copilot (2024): Rehberger reported an exploit chain combining injection, automatic tool invocation and invisible Unicode "ASCII smuggling" to hide exfiltrated data in links; Microsoft fixed it.
  • Documented EchoLeak (Aim Security, 2025; CVE-2025-32711): a single external email, with no user click needed, could lead Microsoft 365 Copilot to exfiltrate in-context data, bypassing its injection classifier and link redaction. Microsoft mitigated it server-side.

Workflow of the attacks

  • Documented In each disclosure the attacker text arrived as ordinary content and exfiltration used a URL the client rendered or the user clicked.
  • Inferred The generalisation: output rendering is an egress channel. Link and image allow-lists (Chapter 5) and a plan frozen before untrusted reads (this chapter) would have bounded each case more reliably than a detector.

Guardrails vendors document

  • Documented Microsoft documents Prompt Shields in Azure AI Content Safety, covering both user-prompt attacks and attacks embedded in documents, and published Spotlighting (Hines et al., 2024), which marks untrusted text by delimiting, datamarking or encoding.
  • Inferred Each incident was fixed by a point control (URL handling, rendering, classifier update); the root cause — one token channel — remains, which is why this chapter ranks isolation above detection.

Evaluation and cost

  • Inferred Vendors do not publish attack-success rates for these products. Buyers should run AgentDojo-style suites (Chapter 11) with their own connectors, and treat each disclosure above as a regression case.
  • Inferred The cost of isolation is utility: dual-LLM and CaMeL-style designs refuse some legitimate cross-document actions, a trade that is cheaper than a SEV1.

Implement a dual-LLM stub: a quarantined function may return only a JSON object with keys summary and entities, schema-validated, before the privileged planner runs. Show that a field named tool_call in the quarantine output is stripped.

Jailbreaking

Jailbreaks try to make a model violate its own safety policy. They are related to injection but aimed at built-in refusals rather than at your tool policy. Defences raise cost; none are absolute against an adaptive attacker with query access.

The Engineering Problem

Product policy forbids a class of advice. A user iterates on prompts until the model complies. Your input regex never matched. Logs show a long benign-looking conversation and one bad answer.

Attack families (engineering view)

  • Role-play / persona. Ask the model to act as a character that "has no rules". Defence: policy on content, not on self-description; output classifiers.
  • Many-shot. Pack the context with faux dialogues that demonstrate compliance (Documented Anil et al., 2024, Anthropic, report effectiveness growing with the number of shots in long-context models). Defence: context budgets, conversation policy, output guards.
  • Optimisation-based (GCG). Search for adversarial suffixes that maximise the likelihood of an affirmative prefix (Zou et al., 2023). Defence: perplexity filters, input classifiers, rate limits on automated clients; do not publish working suffixes in your docs.
  • PAIR and related. An attacker model iteratively refines prompts (Chao et al., 2023). Defence: treat automated multi-turn probing as abuse; throttle; escalate.
What This Book Will Not Print
  • No turnkey jailbreak strings aimed at production systems.
  • Listings use schematic corpus labels (FAMILY:roleplay, FAMILY:suffix_toy) so detectors and metrics can be tested.
  • If you need red-team depth, run a closed programme with rules of engagement (Chapter 11), not a public pastebin.
rp1  roleplay   score=0.8 block=True
ms1  many_shot  score=0.8 block=True
gcg1 gcg_like   score=0.7 block=True
ok1  benign     score=0.0 block=False

Defences and their limits

  • Alignment and refusal training. Necessary baseline (Volume 8). Adaptive attacks still land (Wei et al., 2023, Jailbroken).
  • Input and output classifiers. Llama Guard-style models (Chapter 10). Latency and false positives are first-class product costs.
  • Constitutional / policy classifiers. Separate model judges policy; attackers target the judge too.
  • System-level controls. Rate limits, anomaly detection on session shape, human review for high-risk intents — these survive when the model is fooled.

  • Monitor for PAIR-like patterns: many paraphrases of the same intent from one principal.

Output Guardrails

The model proposed an answer. Output guards decide whether the user (or a downstream tool) may see it. Schema, policy, groundedness, PII and URL/code safety are different checks with different failure modes.

The Engineering Problem

A structured endpoint asks for JSON {status, amount}. The model returns prose, or valid JSON with a negative refund, or a link to http://127.0.0.1/admin. The client crashes, the ledger mis-posts, or an SSRF-shaped fetch runs "because the model said so".

Possible designs

  • Trust the model. Fine for a demo. Not fine for a parser or a browser.
  • Retry until it looks right. Costly, and retries can amplify leakage.
  • Post pipeline with fail-closed validators. Schema first, then policy classifiers, groundedness against evidence, PII redaction, URL and code scanners.

Code in the Answer

  • If the product feeds model code to a sandbox, Volume 16's isolation table applies. An output "looks like Python" check is not a sandbox.

Policy classifiers for disallowed categories sit after schema and before user-visible send when the product forbids entire topic classes. Groundedness applies to RAG; a chit-chat surface may skip it. Make the skip an explicit policy rule, not an accident.

Parse, validate, redact PII (Chapter 6), check URLs against an allow-list, optionally score groundedness, then send. On failure, return a safe error — do not stream the bad payload first.

  • Streaming: buffer until schema-critical tokens are known, or stream with a kill switch that truncates and redacts.
  • Policy classifiers run on the full answer for categories your product forbids.
  • Groundedness gates RAG answers; abstention is a first-class outcome (preview of Volume 18).
  • Strict schemas fight natural language UX. Offer a prose mode and a machine mode with different guards.
  • Groundedness false positives punish paraphrase; tune with human labels, not vibes.
  • Validating only the happy path JSON while the model also emits a second channel (tool call, footnote URL).
  • Fetching model-supplied URLs from the server without an allow-list (SSRF).
  • Showing the raw failure to the user when the failure contains the PII you meant to block.

Extend the schema guard with a value predicate: amount must be in [0, 500]. Show that a model JSON with amount: 99999 is denied even though types match.

PII and Data Leakage

Leakage is not only "the model memorised the training set". It is also a regex you forgot on the output path, a secret in a prompt, a tenant filter in the wrong layer, and an extraction attack that treats your API as an oracle.

The Engineering Problem

Support replies include customer emails and phone numbers. Logs ship full prompts to a vendor. A curious user queries the model about "the document that begins with …" until fragments of another tenant's note appear. Separately, researchers show training-data extraction from language models (Carlini et al., 2021; Nasr et al., 2023).

Layers of leakage

  • Output PII. Detect and redact before display or egress.
  • Secret tokenisation. Never put live keys in prompts; inject at the tool boundary (Volume 16).
  • Memorisation / extraction. Training and fine-tune data can be regurgitated; treat sensitive corpora accordingly.
  • Membership inference. Attackers test whether a record was in training (Shokri et al., 2017).
  • Cross-tenant. Retrieval and cache keys must enforce tenancy in trusted code.
pii_found:email,phone,ssn,secret

  • PII redaction protects people. Secret scanners protect credentials and keys.
  • A redacted display can still leave the secret in the trace exporter. Scan both paths.
  • Tokenise secrets to opaque handles in prompts (cred:mail); resolve only inside the tool runtime after policy allow.

Tool and Agent Security

Agents fail open when tools are ambiently powerful. Permissions, confused deputies, exfiltration channels and sandbox escapes are classical problems with a model in the loop.

The Engineering Problem

The agent process holds a mail API key and a filesystem workspace. A document says to email the workspace to an external address. The model asks for send_email. The runtime obliges with the ambient key. Separately, model-written Python reads /etc/passwd because the "sandbox" was a subprocess (Volume 16).

Controls that actually move risk

  • Least-privilege tool policy. Default deny; argument predicates; plan gates (Volume 16).
  • No ambient authority. Credentials issued per allow decision, scoped, never in the prompt.
  • Egress control. Allow-listed destinations for mail, HTTP and DNS from tools.
  • Sandbox strength matched to code trust. Subprocess ≠ container ≠ microVM.
Confused Deputy
  • The deputy is your tool runtime: it holds power the user does not.
  • The confused instruction arrives via the model, which is following untrusted text.
  • Fixing the deputy means checking the user's intent and authority, not the model's confidence.

Model-Level Threats

Not every incident starts at the prompt. Training data, fine-tunes, weight files and Python dependencies are part of the trusted computing base whether you noticed or not.

The Engineering Problem

A team downloads "helpful" weights from an unofficial mirror, pickle.loads them in a notebook with cloud credentials in the environment, and fine-tunes on a scraped instruction set. Months later a trigger phrase changes behaviour, or the pickle runs a subprocess on load.

Threat families

  • Data poisoning. Web-scale and instruction-tuning poisons (Carlini et al., 2023; Wan et al., 2023).
  • Backdoors / sleeper behaviour. Triggered policies that evade average-case evals (Hubinger et al., 2024).
  • Model extraction / stealing. Distillation via queries (Tramèr et al., 2016; Carlini et al., 2024).
  • Supply chain. Weights, pickles, tokenisers, CUDA wheels, Git dependencies.

  • Model cards and SBOMs for weight releases.
  • Training-data governance: provenance, licences, PII scrubbing before fine-tune.
  • Watermarking and fingerprinting (Kirchenbauer et al., 2023) as detection aids, not silver bullets.
  • Poison rates can be tiny relative to web data and still implant behaviours.
  • Extraction vs legitimate distillation is partly a policy and metering problem.
  • Trusting a viral Hugging Face repo because the demo notebook worked.
  • Fine-tuning on unvetted "instruction" dumps.
  • Eval suites that never hit backdoor triggers.

Add a CI step that fails if any path under models/ matches pickle magic bytes, and a registry JSON that records sha256 for each allowed weight file.

Policy Enforcement

A policy that lives only in a slide deck will lose to the next feature flag. Policy-as-code, a single enforcement engine, human approval and rate/cost limits turn intent into something the runtime can deny.

The Engineering Problem

Legal says "no export of more than 100 rows without review". Engineering puts the sentence in the system prompt. A week later a new code path calls the export tool directly with 10 000 rows. The model was never asked.

Possible designs

  • Prompt policy. Cheap to write, easy to bypass, invisible to non-model paths.
  • Ad hoc if statements. Drift across services; no audit vocabulary.
  • Policy-as-code + engine. Rules as data, one decide, effects allow/ask/deny, every path mediated — including retries and batch jobs.
generate {} (<Effect.ALLOW: 'allow'>, 'chat ok')
export_data {'rows': 5} (<Effect.ALLOW: 'allow'>, 'small export')
export_data {'rows': 500} (<Effect.ASK: 'ask'>, 'large export')
admin_wipe {} (<Effect.DENY: 'deny'>, 'never')

Human approval and budgets

  • Ask pauses the session (Volume 16). Timeout denies. The model does not interpret silence.
  • Rate and cost limits are policy attributes: tokens per day, dollars per tenant, exports per hour. Exhaustion is a deny with a reason, not a crash.
  • Content policies ("no medical diagnosis") may call a classifier (Chapter 10) but the decision still returns through the engine so logs stay uniform.
Complete Mediation
  • Every privileged action calls decide — UI, API, agent tool, cron job, retry worker.
  • A "break glass" path is an explicit rule with louder audit, not a missing call.
  • Saltzer and Schroeder again: fail-safe defaults, least privilege, economy of mechanism.

Human approval is not a vague "LGTM". The gate shows the concrete diff or export preview, binds to a deadline, and writes an audit row the model cannot edit (Volume 16). Content policy denials should cite a rule id so support can explain them without reading the prompt.

Encode three rules for your product. Default deny. Wire decide in front of every tool and every export endpoint. Log the reason code.

  • Policy bundles versioned and signed; canary a new bundle on 5% of traffic.
  • Ask queues integrate with on-call; SLAs on approval latency.
  • Cost policies join the ledger from Volume 16 so a deny is consistent across chat and batch.
  • Product wants exceptions. Every exception is a rule that must be mediated and audited.
  • Multi-region and multi-tenant attributes explode the rule space; test fixtures must cover them.
  • Policy only on the agent path while the REST export is open.
  • Ask that defaults to allow on timeout.
  • Reason strings that include secrets ("denied because key sk-live-…").

Store rules as JSON in the repo. Load them into PolicyEngine at process start. Add a unit test that a PR adding admin_wipe: allow fails CI because the action is on a denylist of irreversible verbs.

Model-Based Guardrails

Classifiers and LLM judges catch semantics that regexes miss. They also add latency, cost and a new attacker surface. Use them after deterministic guards, and manage false positives like a product metric.

The Engineering Problem

A customer writes a long, polite request that is clearly out of policy. Your regexes are silent. A small safety classifier would flag it in 40 ms — or you send the full dialogue to a frontier judge at 10× the cost of the original answer.

Patterns

  • Llama Guard pattern. Documented Meta's open-weight safety model labels hazard categories (Inan et al., 2023); Google's ShieldGemma (2024) is a comparable open classifier. Input and output can both be scored.
  • LLM-as-judge guard. A general model answers "violate policy X?". Flexible, expensive, injectable.
  • Constitutional / policy classifiers. Documented Separately trained input and output classifiers aligned to a written constitution (Sharma et al., 2025, Anthropic).
  • NeMo-style rails. Documented NVIDIA's NeMo Guardrails: dialogue flows and Colang policies around the LLM (Rebedea et al., 2023).

Trade-off: Latency, Cost, False Positives
  • Every model guard adds a serial hop unless you parallelise carefully with a kill switch.
  • False positives are user-visible product failures. Track FPR by locale and topic.
  • Judges can be jailbroken. Prefer specialised classifiers for hard bans; use judges for graded review.

Operating the false-positive budget

  • Shadow-mode a new classifier: log would-block without blocking; estimate FPR.
  • Slice by language, product surface and user tier.
  • Appeal path: human can override with an audit event; overrides feed the next training set.
  • Never let the model under evaluation score its own safety as the only gate.

Real-Product Case Study: Chat Assistant Safety Layers

ChatGPT, Claude and Gemini run the largest guardrail stacks in production. Providers publish the layers in outline through system cards, papers and APIs; thresholds and wiring stay private.

Problem

  • Inferred Hundreds of millions of open-ended conversations, adaptive jailbreakers, and a false-positive budget measured in user churn.

Documented layers

  • Documented Model layer: OpenAI's GPT-4 System Card (2023) describes safety training with RLHF and rule-based reward models; OpenAI's Instruction Hierarchy paper and Model Spec describe how the model should rank conflicting instructions.
  • Documented Classifier layer: OpenAI offers a public Moderation API (a multimodal omni-moderation model since 2024). Anthropic's Constitutional Classifiers paper (Sharma et al., 2025) describes input and output classifiers, reporting a 0.38 percentage-point increase in refusals on production traffic and about 24% extra inference compute. Anthropic says it deployed such classifiers as part of ASL-3 protections for Claude Opus 4 in May 2025.
  • Documented Conversation layer: in February 2023 Microsoft capped Bing Chat at 5 turns per session and 50 per day after long sessions produced erratic replies. Earlier that month a direct prompt injection had exposed its hidden instructions and codename "Sydney". Session shape became a guardrail.
  • Documented Account layer: OpenAI and Anthropic publish periodic threat-intelligence reports on banning accounts that misuse their models.
  • Documented Google DeepMind has published its evaluation of adaptive indirect-injection attacks against Gemini and the use of adversarial training as one defence (2025 technical report).

Workflow

  • Inferred The architecture matches this chapter's reference diagram: gateway abuse controls → input classifiers → a safety-trained model → streaming output classifiers able to halt a response → account-level enforcement from offline review. Ordering, thresholds and model sizes are not published.

Evaluation

  • Documented System cards report refusal, over-refusal and jailbreak-robustness evaluations plus external red teaming; Anthropic ran a public bug bounty against its classifiers.
  • Inferred Treat these as the provider's evidence for its own layer. Your product still needs ASR and FPR on your policy (the metrics function above), because provider guards do not know your refund rules.

Cost

  • Documented The Constitutional Classifiers overhead figure above is one of the few published costs of a guard layer.
  • Inferred Streaming output classification costs extra compute on every generated token; small classifiers and early exits are what keep it affordable.

Secure the platform (practical project below): threat-model the Forge RAG agent, wire the full pipeline, run the red-team suite, and publish ASR, FPR and p95 guard latency in the PR description.

What You Learned

  • Threat models name assets, boundaries and residuals; OWASP LLM, ATLAS and NIST AI RMF share vocabulary, not designs (Chapter 1).
  • Input guards normalise and limit before semantics; matching after encoding is a bypass (Chapter 2).

  • Jailbreaks are families (role-play, many-shot, optimisation, iterative refinement) with measured defences and honest limits (Chapter 4).
  • Output guards validate schemas, groundedness, PII, URLs and code before anything acts on model text (Chapter 5).
  • Leakage spans redaction, secrets, memorisation, membership inference and tenancy — most fixes are ordinary systems controls (Chapter 6).
  • Tool security is least privilege, no ambient credentials, egress policy and real sandboxes (Chapter 7).
  • Model-level threats include poisoning, backdoors, extraction and pickle/weight supply chains (Chapter 8).
  • Policy-as-code with complete mediation, human ask and budgets enforces intent outside the prompt (Chapter 9).
  • Model-based guards follow deterministic ones; latency, cost and FPR are product metrics (Chapter 10).
  • Architecture is defence in depth plus red team metrics plus incident response (Chapter 11).

Important Architecture

How the Layers Compose

  1. Gateway authenticates and applies coarse rate limits.
  2. Pre guards normalise and score the user channel.
  3. Orchestrator builds context; retrieval is tenant-scoped.
  4. Harness mediates tools with policy, plan gate, budgets and sandbox.
  5. Mid guards inspect tool results before they re-enter the prompt.
  6. Post guards validate, redact and classify the answer.
  7. Audit and red-team metrics close the loop.
What Guardrails Are Not
  • They are not a proof of safety.
  • They are not a substitute for authentication, tenancy or payment authorisation.
  • They are not allowed to be the only place a destructive tool is checked — the harness still decides.

Failure Modes

  • Threat model equals model card; residuals unwritten.
  • Detectors before normalisation; denylists in ASCII only.
  • Prompt-only injection defence; plan frozen after untrusted reads.
  • Publishing working jailbreak payloads; safety only in the base model while tools execute.
  • Fetching model URLs; streaming unsafe bytes before validation.
  • Tenant filter in the prompt; secrets in traces.
  • Ambient tool credentials; subprocess called a sandbox.
  • pickle.load on untrusted weights; unscanned fine-tune dumps.
  • Policy on the agent path only; ask timeouts that allow.
  • Judge-only guards; FPR ignored; third-party moderation fed raw secrets.
  • No kill switch; red team that never touches tools; ASR without FPR.

Evaluation

  • Unit tests lock normalisation order, schema denies, URL denies, policy default deny, pickle findings and metric formulae.
  • The red-team harness reports attack success rate, false-positive rate and mean guard latency on every commit.
  • The open-policy attack row is the control: ASR must be > 0 when guards are removed, and 0 on defended cases you claim.
  • Scheduled adaptive tests against live models are separate from the CPU-only CI corpus.
