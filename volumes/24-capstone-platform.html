About This Volume

Platform Requirements and Architecture — Final HLD

A platform is not a bigger demo. It is a set of capabilities with named tenants, SLOs, security boundaries and a cost envelope — plus an HLD that says which Forge package owns which failure.

The Engineering Problem

Volumes 10–22 left you with excellent packages that do not yet share a request identity, a tenant quota, a single audit trail or a release gate. Product asks for "one assistant". Ops asks for one dashboard. Security asks for one threat model. Without an explicit platform boundary, every feature team reinvents auth, tracing and policy.

Capabilities and Tenants

Forge Platform 1.0 exposes four product capabilities behind one API:

  • Chat and RAG Q&A — retrieve, then answer with citations.
  • Tool-using agents — plans that call MCP tools under harness policy.
  • Batch evaluation — offline suites and shadow traffic scoring.
  • Operator surfaces — SLOs, cost ledger, approval queues, runbooks.

SLOs, Security and Cost Targets

  • Latency: chat TTFT p95 < 800 ms on the small route; agent first-tool p95 < 3 s excluding human approval wait.
  • Availability: 99.5% monthly for the gateway; model backends consume the error budget via graceful degradation, not silent 500s.
  • Quality: task-success on the private eval set must not regress more than the non-inferiority margin used by forge.serve.release.
  • Security: injection success rate on the red-team suite below the gate set in Volume 17; no cross-tenant retrieval hits in ACL tests.
  • Cost: blended $/successful-task below the monthly budget line in forge.ops cost ledger; router must prefer cheap routes when quality holds.
Key Idea
  • Requirements are numeric gates, not adjectives. "Secure and fast" is not a platform requirement; the table above is.
  • Every Forge package maps to one layer. Cross-cutting concerns (auth, trace, budget) live at the platform boundary, not inside each package.

Final HLD

Call one model with a prompt and print the answer.

Authenticate a tenant, enforce quotas, run pre-guards, route, optionally retrieve or plan tools, serve under SLOs, post-guard, emit spans and cost rows, then return a PlatformResult.

  • Failures are multi-layer: a wrong answer may be retrieval ACL, routing or the model.
  • Without a shared request ID, continuous improvement cannot attribute a fix.

Platform LLD — Contracts, Shared Libraries, Config, Data Model

The LLD turns the HLD into typed envelopes, versioned configs and tables that auditors can query. If two services disagree on a field name, the platform is lying about being integrated.

The Engineering Problem

Integration by "just import the package" fails when each package invented its own request ID, tenant ID and error shape. Platform LLD is the shared vocabulary: one envelope in, one result out, one event schema for the ledger.

Model Layer — Forge Models, Adapters, Registry, External Providers

The platform never hardcodes a provider SDK in product code. One adapter protocol fronts Forge local models, LoRA adapters and hosted APIs; the registry decides what is allowed to serve traffic.

The Engineering Problem

Product code that imports OpenAI types directly cannot swap to a self-hosted forge.serve endpoint without a rewrite. Provider lock-in shows up as a platform defect the first time a model is retired or a residency rule appears.

Adapter Protocol

provider=scripted  model=small-local  text=[scripted:small-local] What is the refund policy?

Registry and Adapters

  • forge.serve.registry stores immutable artefacts with weight digests and eval-gate metadata (Volume 12).
  • Fine-tuned LoRA adapters register as artefacts that require a base model ID; the serving layer loads multi-LoRA when memory policy allows (S-LoRA pattern).
  • External providers (hosted APIs) register as artefacts with endpoint, region and residency tags — the router filters on those tags before price.
Risk
  • An unregistered model string in a prompt override is a supply-chain hole. The gateway resolves model only through the registry allow-list for that tenant.

Inference and Serving Layer

The platform treats forge.serve as the model plane: OpenAI-compatible HTTP, continuous batching, health probes and release controls. Autoscaling and quantised variants are capacity decisions above that contract.

The Engineering Problem

Agents and RAG both need completions. If each path embeds its own HTTP client with different timeouts and retry policies, you get retry storms and incomparable latency SLOs. One serving boundary with one resilient client is non-negotiable.

Engine, Batching and Quantisation

  • Engine: local development runs forge.serve with a small open-weight model; production swaps the engine for vLLM/SGLang while keeping the same HTTP contract (Volume 12).
  • Batching: continuous batching and backpressure live inside the server — the platform must not invent a second queue in the gateway for token generation.
  • Quantised variants: register FP16 and INT4 artefacts separately; the router may prefer INT4 when the eval gate says quality is within margin.

Knowledge Layer — Hybrid RAG, ACLs, Freshness

forge.rag already retrieves. The platform adds tenant ACLs, freshness windows and a single citation contract so answers remain attributable and cross-tenant leakage fails closed.

The Engineering Problem

A shared vector index without ACL filters is a data breach waiting for a curious prompt. A fresh-looking answer from a six-month-old chunk is a product bug. Knowledge without policy is not a platform layer.

Ingestion and Hybrid Retrieval

  • Ingestion pipeline: parse → chunk → embed → lexical post → optional graph edges (Volume 14 patterns).
  • Hybrid retrieval: dense + BM25 (or equivalent) fused with RRF; the platform does not invent a third ranking algorithm in the gateway.
  • Graph edges help multi-hop "who owns X" questions; they still pass ACL checks per node.

ACLs and Freshness

hits_raw=20  after_acl=4  after_freshness=3  citations=['policy-42', 'faq-9', 'runbook-3']
Risk
  • Filtering after the model has seen text is too late. ACL runs before packing context. Mid-stage forge.guard still scans retrieved text for injection.

Failure Modes

  • Embedding version drift: query embedder ≠ index embedder.
  • ACL encoded only in metadata the retriever ignores.
  • Freshness disabled "temporarily" in prod and never re-enabled.
  • Citations that point to docs the user cannot open (UI ACL ≠ retrieve ACL).

Agent Layer — Harness, Tools, MCP, Approvals

forge.agents decides what to try; forge.harness decides what is allowed to take effect. The platform wires both behind mode agent, with MCP tool servers and human approval queues.

The Engineering Problem

An agent loop without a harness is a confused deputy with network access. Tools that skip approval for "speed" recreate the incidents Volume 16 was written to prevent.

Harness Lifecycle

Reuse forge.harness.lifecycle phases: CREATED → RUNNING → AWAITING_APPROVAL → … → COMPLETED|FAILED|CANCELLED. Illegal transitions are programming errors, not model creativity.

Tools, MCP and Approvals

  • Tool registry validates JSON Schema before any call (Volume 15 / 16).
  • MCP client/server from forge.harness connect external tools without baking vendor SDKs into the agent loop.
  • Approval gate: high-impact tools (send_email, transfer_funds, delete_*) transition the session to AWAITING_APPROVAL.
status=awaiting_approval  tool=send_email  phase=awaiting_approval
Key Idea
  • Platform mode agent is a product surface. The enforcement point remains the harness. Guardrails score text; they do not grant filesystem writes.

Control Layer — Guardrails, Policy, Router, Budgets

Control is the spine between the gateway and every workload: forge.guard for text policy, a deterministic policy engine for tools and data, forge.router for model choice, and budgets that stop runaway spend.

The Engineering Problem

Scattering checks across RAG, agents and chat guarantees inconsistent refusals and unauditable allows. One control plane runs before routing and after generation; mid guards sit on tool and retrieval text.

Guardrails and Policy

  • Pre: size, encoding, rate, topic, injection heuristics (forge.guard).
  • Mid: tool output and retrieved chunks re-scanned before the next model call.
  • Post: schema, groundedness, PII redaction, URL allow-lists.
  • Policy engine: allow / ask / deny with fail-closed defaults matching Volume 17.

Router and Budgets

forge.router selects on the quality–cost–latency frontier. The platform passes tenant class, modality, remaining budget and SLO burn as features — not only the raw prompt length.

status=ok  route=small-local  cost_usd=0.0021  guard=pass

Central control

  • One audit trail for refusals and routes.
  • Budgets apply to RAG and agents alike.
  • Router features stay consistent across modes.

Central control costs

  • Control latency adds to TTFT; keep deterministic guards first.
  • Misconfigured fail-open becomes a platform-wide incident.
  • Policy duplication with harness must be reconciled, not double-denied silently.
Trade-off
  • Model-based guards are slow and stochastic. Size and schema checks stay deterministic and fail closed; classifiers are advisory unless calibrated on your red-team suite.

Evaluation Layer — Offline, CI, Online, Feedback

forge.eval is how the platform knows a change is an improvement. Offline suites gate merges; CI gates block promotion; online experiments and feedback close the loop Chapter 11 will run.

The Engineering Problem

A platform without evaluation is a deployment script. Prompt edits, router weight changes and index rebuilds all claim to help; only paired measurements on frozen suites and online slices can tell.

Online Experiments and Feedback

  • Shadow: new router or prompt scores offline labels on live traffic copies without affecting users (forge.serve.release pattern).
  • Sticky canary: small tenant cohort on the candidate; auto-rollback on task-success or TTFT guardrail breach.
  • Feedback: thumbs, corrections and escalation tickets join request_id and feed the failure taxonomy in Chapter 11.
Implementation Notes
  • Reuse Volume 10 sample-size arithmetic before declaring a canary "winning".
  • Online judges are noisy; keep a private human-labelled slice as the court of appeal.

Operations Layer — OTel, SLOs, Cost Ledger, Runbooks

forge.ops makes the platform operable: every request emits spans and cost rows; SLOs burn visibly; runbooks name the first five minutes of an incident without reading the codebase.

The Engineering Problem

A beautiful architecture that cannot answer "which tenant burned the budget?" or "did TTFT regress after the canary?" is incomplete. Operations is part of the product surface for Platform 1.0, not an afterthought dashboard.

OpenTelemetry Instrumentation

  • One trace_id per request_id; child spans for guard, route, retrieve, model, tool and post-guard.
  • Attributes: tenant.id, route.model, rag.hit_count, agent.phase, guard.decision, cost.usd.
  • Export to the local Compose stack (collector → Tempo/Jaeger + Prometheus) from Volume 22.

Incident Runbooks

  1. Confirm burn alert on the small-route TTFT panel; note deploy SHA and canary %.
  2. Check forge.serve queue depth and KV utilisation; scale if saturated.
  3. If a canary is live, trigger automated rollback via forge.serve.release.
  4. If not a release, shed partner traffic and force router to INT4 / small-only.
  5. Capture trace samples for five slow requests; file a failure-class ticket (Ch. 11).
  1. Page security; freeze index deploys.
  2. Reproduce with ACL suite rag_grounded using the suspect tenant scopes.
  3. If confirmed, disable hybrid retrieve for that index; serve cached refusals.
  4. Audit retrieval_hits for foreign doc_id values; rotate keys if needed.
  5. Post-incident: add a regression case before re-enable.
Key Idea
  • Runbooks are executable checklists tied to SLOs and packages. "Look at logs" is not a step; naming the panel and the rollback command is.

Deployment — Compose, GPU VM, Kubernetes

Platform 1.0 ships three deployment shapes: laptop Compose for developers, a single GPU VM for a sober pilot, and documented Kubernetes for multi-replica production. Cloud apply requires explicit authorisation.

The Engineering Problem

"It works on my notebook" is not a release. Without a Compose path, new contributors cannot run integration tests. Without a VM path, you never learn GPU reality. Without K8s docs, the first outage becomes an architecture debate under page lights.

Local Docker Compose

Single GPU VM

  • Provision a VM with one NVIDIA GPU; install drivers and the NVIDIA Container Toolkit.
  • Run forge.serve (or vLLM) with GPU reservation; gateway and ops on CPU.
  • Pin model weights on a persistent volume; never bake secrets into the image.
  • Document the monthly cost crossover using forge.serve.costing before claiming self-hosting wins.
Trade-off
  • A single VM has no replica failover. Use it for pilots and load characterisation, not as the unspoken production plan.

Continuous Improvement Loop — Failure Class → Fix → Re-eval → Release

Production feedback is worthless unless you classify the failure, change the right layer, re-evaluate and release under the same gates. This chapter is the operating rhythm of Platform 1.0.

The Engineering Problem

Teams fine-tune when the bug was an ACL miss, or rewrite prompts when the router sent every request to the expensive model. Mis-attributed fixes create Sculley-style debt: glue that appears to work until the next release.

Targeted Fixes

  1. Data: add or repair corpus docs; fix chunking; bump embedding version.
  2. Retrieval: hybrid weights, freshness, graph edges, ACL metadata.
  3. Prompts / context: delimiters, citation instructions (Volume 13).
  4. Routing: update capability profiles, cascade thresholds, budgets.
  5. Fine-tuning: only when classification says model capability — and after an eval set exists for the slice.

Re-evaluation and Release

ticket=retrieval  suites=green  shadow=ok  canary=ok  promote=sha_a1b2  cost_delta=$-0.004/req
Engineering Rule
  • No promote without a green suite that covers the failure class. A hotfix that bypasses forge.eval gates is how silent regressions ship.

Worked example

  • Symptom: partner tenant sees outdated pricing in citations.
  • Class: retrieval / freshness (not "the model is dumb").
  • Fix: lower max_age_hours for price docs; re-ingest week’s PDF.
  • Re-eval: rag_grounded + new golden case price_week_fresh.
  • Release: shadow → 5% canary → promote; cost unchanged; TTFT flat.

Platform Review — Design, Threat, Cost, Reliability and What Next

Before calling Platform 1.0 done, review the design against the requirements, walk the threat model, check the cost envelope and reliability story, then name what you deliberately did not build.

End-to-End Design Review

  • Does every HLD box map to a package owner and a CI suite?
  • Is the request envelope the only cross-service contract?
  • Can you replay a request from ledger + session events without guessing?
  • Are fail-closed defaults documented for guard, ACL and harness?

Reliability Review

  • Degradation ladder: refuse new agent sessions → force small route → shed partners → read-only RAG → maintenance.
  • Breakers and shedding tested in integration (inject serve failures).
  • Approvals do not count against TTFT SLOs; separate "time to human" metric.

What Platform 1.0 includes

  • One gateway, one envelope, eight Forge packages wired.
  • Eval gates and an improvement loop with release packets.
  • Compose + documented GPU VM / K8s.

What we defer

  • Multi-region active-active and formal DR drills.
  • Learned routers in production (keep rule/capability first).
  • Full multi-agent swarms; single harnessed agent is enough.
  • Customer-facing billing UI (ledger exists; invoices do not).

What to Build Next

  1. Expand private eval slices per tenant class.
  2. Automate weekly cost and SLO review packets.
  3. Add more MCP tools only after approval metrics stay healthy.
  4. Graduate documented K8s to a real cluster when traffic and on-call exist.
  5. Feed paper-card lessons (debt, test score, SE for ML) into the roadmap below.
Research Frontier
  • Operationalising ML interview studies (Shankar et al., 2022) still read like a checklist for AI platforms: ownership, monitoring and continual validation beat one-shot model launches.

Red-Team and Security Checklist

  • Direct injection phrases in chat mode → refuse (pre-guard).
  • Indirect injection inside a retrieved chunk → mid-guard blocks pack or strips.
  • Tool call send_email without approval → session AWAITING_APPROVAL, no side effect.

  • Secret-looking strings in output → post redaction or refuse.

Simple Versus Production

One Python process, scripted adapter, in-memory ACL list, print statements for cost.

Compose or K8s, real forge.serve, Postgres ledger, OTel export, CI gates on every promote, runbooks on call.

  • Production fails on joins: traces without cost, cost without tenant, eval without SHA.
  • Scripted tests catch contract breaks; only live serve catches GPU and queue dynamics.

Release Packet Template

Key Idea
  • If you cannot fill the release packet, you are not ready to promote — regardless of how good the demo looked.

Tenancy and Multi-Index Patterns

  • Shared index + ACL metadata: one corpus, scopes on each chunk; cheapest ops, highest risk if filters fail — hence mandatory ACL tests.
  • Index per tenant: stronger isolation, higher cost; router and gateway must resolve index from tenant, not from prompt text.
  • Partner overlays: partner docs in a separate index mounted read-only; never merge embeddings across residency zones.

Budget Arithmetic

Let B be the per-request budget in dollars, c_r the router's expected model cost, c_t tool costs so far, and c_g a guardrail overhead allocation. Admit a next model call only if

c_r + c_t + c_g \le B

Agents charge c_t after each tool; RAG charges retrieval as near-zero but still attributes embedding query cost in the ledger for honesty.

Trade-off
  • Budgets that ignore tool side effects (emails sent, tickets filed) under-account risk. Price irreversible tools in approval friction, not only dollars.

Important Architecture

Failure Modes

  • Package-local request IDs that cannot join cost, traces and eval.
  • Provider SDKs imported in product handlers — registry bypass.
  • ACL applied after the model saw foreign chunks.
  • Agent tools that skip harness "just for the demo".
  • Fail-open guards under latency pressure.
  • Router ignored when "the large model is smarter".
  • Canary without non-inferiority rollback.
  • GPU VM treated as multi-AZ production.
  • Fine-tuning used to paper over retrieval or policy bugs.
  • Hotfixes that skip forge.eval gates.
  • Cost ledger rows without tenant or route labels.
  • Runbooks that say "check logs" without a panel or command.

Evaluation

  • CI: rag_grounded, agent_tools, guard_redteam green.
  • Promote: router_frontier and non-inferiority on task success.
  • Pre-release: slo_synthetic TTFT/TPOT under scripted load.
  • Security: zero cross-tenant hits in ACL tests; red-team success below gate.
  • Ops: monthly cost by tenant; SLO burn alerts wired to runbooks.
  • Process: at least one Chapter 11 cycle from ticket to measured promote.

Practical Project

Ship the integrated platform and prove it with gates, not slides.

  1. Stand up Compose: gateway, forge.serve (or scripted), Postgres, OTel, Prometheus, Grafana.
  2. Implement envelope, control handle(), RAG ACL path, harnessed agent path.
  3. Pass integration tests: ACL, injection refusal, CI gates.
  4. Define SLOs and two runbooks; inject a serve failure and show breaker + shed.
  5. Optional: one GPU VM pilot with costing crossover documented.
  6. Run one improvement cycle from a seeded failure ticket to a release packet.
  7. Write a one-page Platform 1.0 review: threat, cost, reliability, deferred list.

RESEARCH PAPER Hidden Technical Debt in Machine Learning Systems Sculley et al., 2015 · NeurIPS
Problem
ML systems accumulate maintenance costs that traditional software accounting misses: glue, entanglement, hidden feedback loops.
Previous limitation
Debt discussions focused on code quality inside a single model training codebase.
Approach
Catalogue debt forms: entanglement, correction cascades, undeclared consumers, data dependencies, configuration debt.
Contribution
A vocabulary for why "just ship the model" creates long-lived platform liability.
Practical impact
Platform boundaries, contracts and ownership in Chapters 1–2; classification before fine-tuning in Chapter 11.
Limitations
Pre-LLM serving and agent tool risk; the debt shapes still apply, the examples need updating.
RESEARCH PAPER The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction Breck et al., 2017
Problem
Teams lacked a shared bar for whether an ML system was production-ready.
Previous limitation
Ad hoc checklists; model accuracy treated as the only gate.
Approach
A scored rubric across data, model, infrastructure and monitoring tests.
Contribution
Makes readiness measurable; encourages tests beyond loss curves.
Practical impact
Chapter 8 suites and Chapter 10 integration markers are the platform's ML Test Score analogue.
Limitations
Rubric predates LLM-specific risks (injection, tool abuse); extend categories, do not discard the idea.
RESEARCH PAPER Software Engineering for Machine Learning: A Case Study Amershi et al., 2019 · ICSE-SEIP
Problem
How do real organisations engineer ML products — where do SE practices help or break?
Previous limitation
Advice was often lab-centric or purely algorithmic.
Approach
Case study of Microsoft teams building ML systems; synthesise process lessons.
Contribution
Evidence that data availability, feedback loops and cross-team coordination dominate.
Practical impact
Ownership of layers in the HLD; improvement loop as a process, not a notebook (Chapters 11–12).
Limitations
One corporate context; still the right questions for Forge Platform 1.0 reviews.
RESEARCH PAPER Challenges in Deploying Machine Learning: A Survey of Case Studies Paleyes, Urma and Lawrence, 2022 · ACM Computing Surveys
Problem
Deployment and productionisation failures are under-taught relative to model training.
Previous limitation
Scattered war stories without a structured survey across industries.
Approach
Survey case studies; taxonomise challenges from data to monitoring to organisation.
Contribution
A map of where ML projects die after the notebook: serving, drift, ownership, cost.

Honest Compose / VM / K8s chapter; deferred multi-region; reliability ladder (Chapters 10, 12).
Limitations
Survey breadth over depth; pair with your own incident history.
