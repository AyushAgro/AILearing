Workflows versus Agents

An agent is a loop in which a model chooses the next action. That single design choice trades predictability for flexibility. This chapter makes the trade explicit, puts numbers on it, and gives a decision procedure that defaults to the cheaper option.

The Engineering Problem

A team wants to "add an agent" to customer support. Some tickets are routine (where is my order?), some need investigation across three systems, and a few need a refund. The team must decide who owns control flow: code written in advance, or a model deciding at run time. The wrong choice either caps what the system can do or makes it slow, expensive and hard to test.

Definitions used in this volume

  • Workflow: code fixes the sequence of model calls and tool calls. Branches exist, but they are enumerated in advance.
  • Agent: a model chooses the next action from a set of tools, observes the result, and repeats until it decides to stop or a budget stops it.
  • Agentic system: any mix of the two. Most production systems are workflows with one or two bounded agentic steps.
  • Documented This follows Anthropic's public post Building effective agents (December 2024), which also catalogues the common workflow patterns: prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser.

The Cost of Agency

Agency has three costs that engineers routinely underestimate: token cost grows faster than linearly with steps, per-step errors compound, and variance in latency and cost becomes a tail problem. The simulation below compares a fixed three-step workflow with an agent that uses the same per-step accuracy but decides its own number of steps. It deliberately assumes the task is one the workflow can solve; the point is what agency costs when it is not needed.

What the numbers say

  • Cost per success is 3.5× higher for the agent (17,471 versus 4,923 tokens) even though its mean number of calls is only 1.5× higher. Each call re-reads the growing transcript, so total tokens grow roughly quadratically in steps.
  • The p95 is the real budget. Agent p95 tokens are 8.8× the workflow's; capacity planning and rate limits must be set on the tail, not the mean.
  • Errors compound. With independent per-step accuracy p, a trajectory of n steps succeeds with probability p^n. At 97% per step, 20 steps succeed about half the time.
  • The independence assumption is optimistic in one direction (real agents can recover from errors) and pessimistic in another (errors correlate: a wrong early belief poisons later steps). Measure it on your own trajectories (Chapter 12).
P(\text{success}) \approx \prod_{i=1}^{n} p_i \;=\; p^n, \qquad \mathbb{E}[\text{tokens}] \approx \sum_{i=1}^{n} \bigl(c_0 + i\,\Delta\bigr) = n c_0 + \tfrac{n(n+1)}{2}\Delta

Here c_0 is the initial context and \Delta is the tokens appended per step. Prompt caching (Volume 11) reduces the price of the re-read prefix but not the latency of long contexts or the quality loss that comes with them.

Key Idea
  • Default to the workflow. Promote a single step to an agent only when its steps are genuinely unknowable in advance and you have a success signal to test it with.
  • Agency is paid for in tokens (quadratic in steps), tail latency, compounding error and a larger safety surface.
  • The most useful production shape is "workflow outside, bounded agent inside": code owns entry, exit, budgets and side effects; the model owns a bounded search.
Common Mistakes

The Minimal Agent Loop

Every agent, whatever the framework, reduces to one loop: ask the model for an action, execute it, append the observation, repeat until a stop condition fires. This chapter builds that loop properly (about 100 lines) with a parser, a step budget, loop detection and tests, then runs it against a real small model to see what breaks.

The Engineering Problem

The five-line run_agent from Volume 1 trusts everything: it assumes the model emits a well-formed action, that the tool exists, that the tool does not raise, and that the model will stop. Each of those assumptions fails in production daily. The loop must turn every failure into either an observation the model can act on or a clean, labelled termination.

Design Decisions

  • Action format: one JSON object per turn, either {"tool": name, "args": {...}} or {"final": answer}. Hosted APIs return tool calls as structured fields (Volume 13); a text protocol lets us test with any model and makes parsing failures visible.
  • Tool errors are observations, not exceptions. The model often recovers if it is told what went wrong.
  • Three stop conditions: the model says it is done; the same action repeats more than max_repeats times; the step budget runs out. Parse errors get their own budget.
  • Everything returns a labelled status (final, budget, loop, parse_errors) so evaluation can count failure types (Chapter 12).
  • The model is a Protocol with one method, so a fake and a real model are interchangeable.
Implementation Notes
  • parse_action takes the outermost {…}, so "I will look it up. {…}" still parses. That tolerance is deliberate; strictness belongs in constrained decoding (Volume 13), not in the loop.
  • Repeat detection hashes the canonical JSON of the action. It catches the commonest pathological loop (calling the same tool with the same arguments after an unhelpful observation) at zero cost.
  • The loop is stateless between runs; all state lives in messages. Chapter 4 makes that state explicit and persistent.

A Real Model in the Loop

Fakes test the loop; they say nothing about whether a model can drive it. The only model cached offline on this machine is HuggingFaceTB/SmolLM2-135M, a 135M-parameter base model with no instruction or tool-use tuning. We give it one few-shot example and plug it into the unchanged loop.

What went wrong, honestly

  • The first action is perfect: the few-shot format is easy to copy. A base model is a pattern completer, and the pattern was one step deep.
  • After the observation it does not produce {"final": …}. It continues the document, inventing a new "Goal: Where is order 1?" and then acting on its own invented goal. It has no notion of whose turn it is.
  • The loop did its job: it labelled the failure (budget), fed back parse errors, and stopped after four steps. The loop cannot make a weak policy good; it can only make failure bounded and visible.
  • Instruction-tuned models with native tool-calling (Volume 8 post-training, Volume 13 APIs) are what make this loop useful. Research on this started with Toolformer (Schick et al., 2023), which taught a model to insert API calls into its own text through self-supervision.
Do Not Over-Read Demos
  • One run of a real model is an anecdote. Chapter 12 turns this into a measurement: success rate, failure-status distribution and variance over repeated runs.
  • Greedy decoding hides variance; production sampling (temperature above zero, or provider-side non-determinism) exposes it.

Add a fourth stop condition: stop with status no_progress if three consecutive observations are errors. Write the test first. Then decide whether "three errors" should reset after a success, and justify the choice with a trajectory where each policy is wrong.

Tool Design

The model never sees your code. It sees a name, a description, a schema and whatever text comes back. Tool design is interface design for a reader that is fast, literal and occasionally careless. This chapter builds a registry that generates schemas from type hints, validates every call, writes errors for the model, and makes side effects idempotent.

The Engineering Problem

In Chapter 2 the model called get_order("42x") and received KeyError: '42x'. Multiply that by fifty tools: hand-written JSON schemas drift from the functions they describe, invalid arguments reach production systems, error messages are stack traces, and a retry after a timeout refunds a customer twice.

Possible solutions, and what each does not solve

  • Hand-written schemas: precise, but drift from the code and are never tested.
  • Constrained decoding (Volume 13): guarantees the JSON shape, but not that order_id exists or that pence were not confused with pounds.
  • Trust the model and catch exceptions: turns every bad call into a real call against a real system first.
  • Registry + validation + model-facing errors + idempotency keys: what we build. It still cannot stop a valid but wrong call; that needs permissions and approvals (Chapter 10, Volume 16).

Error Messages Written for Models

  • Say whether anything happened. "ERROR (not executed)" versus "ERROR while executing" matters: the first is safe to retry, the second may have partially committed.
  • Name the argument, the offending value and the expected type. The model fixes '45.99' is not of type 'integer' in one step; it rarely fixes ValidationError.
  • Offer the nearest valid option ("Did you mean 'search_orders'?"). Our prefix match is crude; edit distance or embedding similarity is better.
  • Re-state the contract (the expected properties) on failure, because it may have fallen out of an over-long context.
  • Never leak secrets or internal stack traces into observations. They end up in logs, traces and, possibly, the user's screen.

Idempotency

Agents retry: the model repeats a call after an ambiguous observation, the loop retries after a timeout, and a resumed run re-executes the step it crashed in (Chapter 4). Every side-effecting tool therefore needs an idempotency key. The registry derives one from the call's canonical JSON when the caller supplies none, which deduplicates exact repeats. That default is wrong for legitimately repeated actions (two identical £5 refunds), so production callers pass an explicit key such as run_id:step.

Validation Is Not Authorisation
  • A schema-valid refund_order("A-1001", 4599, …) may still be a refund the user is not entitled to, or one injected by text in a retrieved document.
  • Authorisation must check the principal (the end user), not the agent, and happen in the tool runtime, outside the model's control. Volume 16 builds the permission layer; Volume 17 covers prompt injection.

The Agent-Computer Interface

Documented SWE-agent (Yang et al., 2024) coined the term agent-computer interface (ACI): the commands and feedback formats an agent uses to operate a computer. Its central finding is that interface design, not only model choice, drives agent performance: a file viewer that shows a window of lines with line numbers, a search that returns a bounded list, and an editor that runs a linter and rejects syntactically broken edits outperformed giving the model a raw shell.

ACI principles

  • Bounded output with an explicit count ("5000 matching lines") so the model knows what it is not seeing.
  • Next-action hints in the output ("call view_log(…, offset=2)"), which turn pagination into a copyable action.
  • Stable addresses (line numbers, IDs) so later actions can refer to earlier observations precisely.
  • Guarded mutations: validate edits before applying them and report exactly what changed.
  • Empty results say so ("0 matches for 'ERRROR'"); silence is misread as success.
  • Schema drift: the function changes, the hand-written schema does not. Generate schemas from code and test them.
  • Overlapping tools: get_user, lookup_customer and find_account split selection probability three ways.
  • Unbounded outputs push the goal and earlier evidence out of the context.
  • Ambiguous errors cause blind retries and repeat loops.
  • Non-idempotent side effects execute twice on retry or resume.

Real-Product Case Study: Coding Agents

Coding agents — SWE-agent, Claude Code, OpenAI's Codex — are the most widely used agents in production, and the clearest evidence that tool design matters as much as the model.

Problem

  • Documented SWE-bench (Jimenez et al., 2023) frames the task: given a real GitHub issue and repository (2,294 tasks from 12 Python projects), produce a patch that makes the project's hidden tests pass.

Workflow and tools

  • Documented SWE-agent gives the model a windowed file viewer, bounded search and a lint-checked editor, and reports that this ACI beats a raw shell with the same model (Yang et al., 2024).
  • Documented Claude Code's documentation describes a terminal agent with tools to read, search and edit files and run shell commands; project instructions loaded from CLAUDE.md files; hooks; subagents; and MCP servers for extra tools.
  • Documented OpenAI's Codex launch (May 2025) describes a cloud agent that runs each task in its own sandboxed container preloaded with the repository, reads AGENTS.md for project conventions, and returns terminal logs and test output as evidence; the separate Codex CLI is open source.
  • Inferred All three are the Chapter 2 loop with ACI-shaped tools, context compaction for long sessions and a test-run step as the external verifier. Their internal prompts and ranking of which files to read are not published in full.

Guardrails

  • Documented Claude Code documents a permission system that is read-only by default and asks before file edits and commands unless the user adds allow rules or selects a more permissive mode.
  • Documented Codex documents that network access is disabled during task execution by default, confining the agent to the repository and pre-installed dependencies.
  • Inferred The two illustrate the two ends of Chapter 10's approval spectrum: a local agent with per-action human approval, and a remote agent with a sandbox and review of the final diff.

Evaluation

  • Documented Model vendors report SWE-bench Verified scores in launch posts and system cards; SWE-agent's paper reports its own SWE-bench results.
  • Inferred Benchmarks cover Python bug fixes with tests. Teams should add private tasks from their own repositories, scored by tests and by review of the diff, because public scores do not transfer to a monorepo in another language.

  • Documented Claude Code's documentation includes cost tracking and guidance on reducing token usage (for example compacting context).
  • Inferred Cost is dominated by re-reading context each step; prompt caching of the stable prefix and bounded tool output (the view_log lesson above) are the main levers.

State and Control Flow

The Chapter 2 loop keeps its state in local variables. That is fine until the process dies, a human must approve a step tomorrow, or you need to know why a run stopped. This chapter makes the state explicit (a small state machine), checkpoints it after every transition, and resumes after a crash, including the awkward window between a side effect and its checkpoint.

The Engineering Problem

An agent runs a twelve-step task that takes eight minutes. At step nine the worker is redeployed. Restarting from scratch repeats eight model calls and, worse, repeats side effects: the email is sent twice. The team needs resumable runs with at-most-once side effects and an audit trail of every transition.

An Explicit State Machine

  • Phases are data, so a checkpoint records where the run is, not just what it has seen.
  • DECIDE and ACT are separate transitions. The pending action is persisted before execution, so a crash in ACT is detectable on resume.
  • Transition table: the TRANSITIONS map makes illegal moves fail loudly; it is also the diagram, in code.
  • Termination is explicit: DONE with an answer, or FAILED with a reason. There is no "loop fell off the end".
Implementation Notes
  • Atomic write: write to a temporary file and os.replace it. A crash mid-write leaves the old checkpoint intact rather than a truncated JSON file. (For durability across power loss, also fsync the file and its directory.)
  • Deterministic idempotency key: run_id:step is stable across a resume, so the tool runtime can recognise a replayed call.
  • What is not checkpointed: the model object and tool registry. Resumption rebuilds them from configuration; the checkpoint holds only data.
  • Include a schema version in real checkpoints. A deploy that renames a field otherwise strands every in-flight run.

Crash and Resume

crashed: process killed; checkpoint phase=decide step=3 messages=7 emails_sent=1
resumed: phase=done step=4 answer='Reported: London 14C, Paris 17C'
emails sent: ['ops@example.com']
checkpoint bytes: 828

The resumed run consumed one model call, not four, and sent one email. That is the easy case: the crash happened in DECIDE, after the previous ACT had been checkpointed.

The Side-Effect Window

The hard case is a crash after a tool commits its side effect but before the checkpoint records it. On resume the state still says ACT with the action pending, so the tool runs again. No ordering of "execute" and "save" removes this window; only the tool side can close it, by recognising the replayed idempotency key. That requires the idempotency store to survive the crash.

durable idempotency store   : resumed from phase=done, emails sent=1
Exactly Once Is a Contract, Not a Feature
  • A checkpointed agent gives at-least-once execution of tool calls. Exactly-once effects need the effect's owner (payment provider, email service, your database) to deduplicate on a key you pass.
  • Where the downstream system has no idempotency support, wrap it: record the key and the outcome in the same transaction as the effect, or put an outbox table in front of it.
  • Chapter 10 generalises the checkpoint into an event log with replay, the model used by durable execution engines.

Memory for Agents

An agent's context window is its only working memory, and every step makes it longer. Memory engineering decides what stays verbatim, what is compressed, what is written down on purpose, and what is retrieved from earlier runs. This chapter builds all four and shows exactly what each loses.

The Engineering Problem

A research agent reads 30 pages of supplier quotes. By page 20 the transcript is 3,000 tokens of mostly filler, the cheapest quote from page 0 is buried, and cost per step keeps rising (Chapter 1). Next week, a similar task starts from zero and repeats last week's mistakes.

Generative Agents (Park et al., 2023) combined a memory stream of observations with retrieval scored by recency, importance and relevance, plus periodic reflection that writes higher-level summaries back into memory. Voyager (Wang et al., 2023) stored successful behaviours as a skill library of executable code, retrieved for new tasks: procedural memory rather than text. Both are variants of the same idea: write selectively, retrieve by relevance.

What the run shows

  • Budgeting works on cost: the prompt stays at about 380 tokens instead of 4,230 and does not grow with steps.
  • Summarisation is lossy in a specific direction. Our summariser keeps the tail, so only 7 of 28 folded pages survive, and page 0, which holds the answer, is gone. A real LLM summariser loses information less predictably, which is worse: you cannot reason about what it dropped.
  • The scratchpad saved the task. The fact that matters was written deliberately and is rendered in every prompt, independent of compaction. Give the agent a note tool and prompt it to record decisions and key facts.
  • Lexical retrieval ties. Both refund episodes score 0.68; the failure lesson (the one that matters for a gift-card refund) is not ranked above the generic one. Embedding retrieval (Volume 14) plus metadata filters (outcome, tool set) and a re-ranker fix most of this.

Design Choices

  • When to compact: on a token threshold (as here), on phase boundaries (after each subtask), or both. Compacting on boundaries produces better summaries because the unit is semantically complete.
  • What to keep verbatim: the goal, the latest observations, any unresolved error, and every identifier the agent may need to cite. Summaries are where IDs silently mutate.
  • What to write to episodic memory: task, action sequence, outcome, cost and a one-line lesson. Store failures; they are the most useful retrievals.
  • Retrieval as a hint, not an instruction. Retrieved lessons are untrusted text from the past: they can be stale (the API changed) or wrong (the lesson generaliser was wrong).
Memory Is a Persistence Channel for Attacks
  • If an injected instruction in a web page ends up in a stored lesson or summary, it is replayed into every future run that retrieves it. Treat memory writes like database writes from untrusted input: provenance, review for high-impact memories, and expiry.
  • Episodic stores often contain user data. Apply the same retention and deletion policy as your other user data stores.
  • Summary drift: repeated summarisation of summaries loses or distorts early facts.

Planning

Planning means deciding more than one step before acting. It buys fewer model calls, a reviewable artefact and a chance to reject bad plans before anything runs. It costs adaptability. This chapter implements plans as data, validates them against the tool registry, and compares plan-then-execute with ReAct interleaving.

The Engineering Problem

A ReAct agent pays one model call per step, and its intent is only visible one step at a time, so nobody can review or approve the whole course of action in advance. A plan-then-execute agent makes one planning call and then runs tools without further model calls, but it cannot react when step 1 returns something unexpected. Neither is universally better.

  • A plan is a list of steps, each with an id, a tool, args and dependencies.
  • Arguments may reference earlier outputs with $s1 or $s1.field. References create implicit dependency edges.
  • Validation is static and runs before any tool: unknown tools, schema errors, dangling references, cycles and oversize plans. It uses the same registry and schemas as Chapter 3.

Reflection and Replanning

"Ask the model to check its work" is the most popular agent pattern and the most misunderstood. Retrying helps when something outside the model tells it whether and how it failed. Without that signal, self-critique mostly spends tokens. This chapter builds a verifier-driven loop and then measures five retry strategies on the same simulated tasks.

The Engineering Problem

An agent's first attempt at a coding task passes about half the time. The team adds a "reflect and revise" step. Success does not move, cost triples, and some previously correct answers are now wrong. The question is not whether reflection works, but which reflection, with which signal.

Kinds of reflection, by where the signal comes from

  • External verifier with feedback: unit tests, a compiler, a schema validator, a database constraint, a checker model trained for the task. The signal is reliable and says what failed.
  • External verifier, pass/fail only: enables best-of-n or resampling; the model gets no hint.
  • Self-critique: the same model judges its own output. The signal is only as good as the model's ability to recognise its own errors, which is weakest exactly where it failed.
  • Reflexion (Shinn et al., 2023) stores verbal reflections on failed trials in memory and conditions the next trial on them. Its strongest results (for example on HumanEval coding) used an external signal: executed tests or environment reward.
attempt 1: passed=False  feedback: median([4, 1, 3, 2]) returned 3, expected 2.5
attempt 2: passed=False  feedback: median([]) raised IndexError: list index out of range
attempt 3: passed=True  feedback: all 3 tests pass

The scripted coder is an idealisation: it always fixes the named bug. Its purpose is to show the shape of useful feedback (the input, the actual and the expected value) rather than to claim that real models always use it well.

When Reflection Helps, and When It Does Not

To compare strategies fairly we simulate 20,000 tasks with a latent difficulty d \sim U(0,1); a first attempt succeeds with probability 1-d. Every strategy gets up to three attempts. The assumptions for each strategy are stated in the code; change them and rerun.

single                    success=0.502  model calls/task=1.00
verifier+feedback         success=0.852  model calls/task=1.76
verifier+resample         success=0.753  model calls/task=1.82
self-critique             success=0.501  model calls/task=3.26
self-critique, no signal  success=0.471  model calls/task=3.25

Reading the result

  • A verifier is the active ingredient. Resampling with only a pass/fail verifier lifts success from 0.50 to 0.75; adding informative feedback lifts it to 0.85 at fewer calls, because correct answers stop early.
  • Self-critique with a weak judge is a wash (0.501) at 3.3× the calls. The judge flags correct answers almost as often as wrong ones, and a blind revision is slightly worse than the original (d + 0.05), so it breaks as many answers as it fixes.
  • With no signal it is harmful (0.471): revisions are made at random, and the revision is worse than the first draft on average.
  • This matches published findings that LLMs struggle to self-correct reasoning without external feedback (Huang et al., 2024, Large Language Models Cannot Self-Correct Reasoning Yet), while execution feedback reliably helps coding agents.
P(\text{solve within } k) = 1 - (1-p_1)\prod_{j=2}^{k}\bigl(1 - q_j\bigr)

With a perfect verifier, q_j is the probability that attempt j fixes a known failure. Without one, you must also subtract the probability that a revision breaks an answer that was already correct, which the formula above ignores.

Failure Recovery and Replanning

  • Classify the failure first: a transient tool error needs a retry with back-off, not a new plan; a validation error needs a corrected call; a wrong plan needs replanning; an impossible goal needs escalation.
  • Replan with evidence: pass the failed plan, the failing step and its error (Chapter 6) to the planner, and forbid repeating the identical plan.
  • Cap everything: attempts per step, replans per run, and total cost. A reflection loop without a cap is an unbounded bill.
  • Keep the best candidate, not the last. With a graded verifier (tests passed out of total), return the best-scoring attempt if the budget runs out.
When Not to Reflect
  • No verifier and no ground truth: spend the budget on a better first attempt (context, retrieval, a stronger model) instead.
  • The verifier is the same model with a different prompt: measure its accuracy as a classifier on your data before trusting it (Volume 10, LLM-as-judge calibration).
  • Tasks where revisions have side effects (sent messages, executed trades): reflect before acting, never after.

Code as Action

A JSON tool call does one thing. A snippet of code can loop, filter, branch and compose many tools in one action. Code-as-action agents trade the safety of a narrow interface for expressiveness, which makes the execution environment the security boundary. This chapter builds a restricted executor, shows what it does and does not contain, and previews the sandboxing of Volume 16.

The Engineering Problem

"Total value of all shipped orders among 40" takes 40 JSON tool calls plus arithmetic the model may get wrong. With code, it is one action. But the code is written by a model that may be wrong, confused or steered by injected text, and it now runs on your machine.

CodeAct (Wang et al., 2024) proposed executable Python as a unified action space and reported higher success rates and fewer interaction turns than JSON or text actions across many LLMs, because code gives control flow, variables and library access for free. Code interpreters in hosted assistants and most coding agents take the same approach.

A Restricted Executor

ok=True stdout='20 3000' in 0.03s
error surfaces as observation: KeyError: 'B-1'
infinite loop: ok=False returncode=-24 after 2.0s (SIGXCPU=24 from RLIMIT_CPU)
sleeping (no CPU used): ok=False TimeoutExpired after 3.0s
can read your home directory: True
can open sockets: socket created

Two limits, two failure shapes

  • CPU limit (RLIMIT_CPU) kills a busy loop with SIGXCPU after 2 CPU-seconds; the parent sees return code −24.
  • Wall-clock timeout catches code that blocks without using CPU (sleep, network waits, deadlocks). You need both.
  • -I (isolated mode) ignores PYTHON* environment variables and the user site directory; the stripped env hides API keys in the parent's environment from the child. Both are hygiene, not isolation.
This Is Not a Sandbox
  • The child runs as your user: it read the home directory listing and could read SSH keys, cloud credentials and browser profiles.
  • It created a socket: nothing stops it exfiltrating what it reads.
  • A temporary working directory changes the default path, not what is reachable. RLIMIT_AS is not enforced on macOS, so memory is not bounded here either.
  • Real containment needs OS-level isolation: a separate user and filesystem namespace, no network or an egress allowlist, seccomp or a microVM (gVisor, Firecracker), plus resource quotas. Volume 16 builds this. Never run model-written code with only the executor above on a machine that holds anything you care about.

A CodeAct Agent

The agent loop does not change. Code execution is simply one tool whose argument is a program, and whose observation is stdout or the last line of the traceback.

obs: ERROR: KeyError: 'totl'
obs: A-40 {'total': 290, 'status': 'open'}
obs: (final)
final A-40 is the largest order (290).

Code actions

  • Loops, filters and composition in one step; far fewer model calls for data-heavy tasks.
  • Arithmetic is done by the interpreter, not the model.
  • Tracebacks are precise, familiar feedback for code-trained models.
  • Tools are ordinary functions; no schema ceremony.

Costs

  • The sandbox becomes the security boundary and must be real.
  • Per-call permission checks are harder: one action may touch many tools.
  • Actions are harder to audit, approve or replay than a JSON call.
  • State inside the interpreter (variables) must be persisted if the run is to be resumable.
  • Escape from a pseudo-sandbox: in-process exec with a restricted globals dictionary is trivially escaped through object introspection.
  • Output flooding: a print in a loop fills the context; truncate and say so.
  • Hidden side effects: code calls a mutating tool inside a loop, bypassing approval gates designed for single calls.
  • Non-determinism: code that reads the clock or the network cannot be replayed (Chapter 10).

Make the interpreter stateful across steps (a persistent child process that executes successive snippets in one namespace) while keeping the timeout. How do you checkpoint that state for resumption? Compare pickling the namespace with replaying all previous snippets.

Multi-Agent Systems

Splitting work across specialised agents looks like organisation design. It can isolate context, parallelise independent subtasks and force disagreement before a decision. It also multiplies failure modes: handoff loss, shared-state races, collusion and cost that grows with every extra model call. This chapter builds three patterns, then a minimal MCP over stdio, and names the failures that research keeps rediscovering.

The Engineering Problem

A support ticket needs an order lookup, a policy check and a carefully worded answer. One agent with three tools works until the context fills with irrelevant tool output and the model starts mixing policy text into refund amounts. The team proposes "a lookup agent, a policy agent and a writer". Before adding processes and message buses, they need to know which topology solves the context problem and which only adds coordination debt.

When multiple agents earn their keep

  • Context isolation: a worker sees only the subgoal and the tools it needs; the orchestrator never dumps a full tool trace into every specialist's prompt.
  • Parallel independent work: retrieval, code search and web checks that do not depend on each other.
  • Forced disagreement: debate or red-team/blue-team setups where a single chain-of-thought would confirm its own bias (Du et al., 2023).
  • Organisational boundaries: different permission sets, tenants or data planes that must not share a tool namespace.

When they do not

  • The task is a fixed pipeline of known steps: use a workflow (Chapter 1), not a committee.
  • Workers need the same tools and the same context; you have renamed one agent three times.
  • You cannot state the handoff contract (inputs, outputs, failure signal) in a schema.

Orchestrator–Worker

The orchestrator decomposes the goal into named subtasks, dispatches each to a registered worker, and synthesises the results. Workers are ordinary callables here; in production each may be its own model loop with a narrow tool set. The important contract is the WorkerResult: success flag, output string and a cost counter the orchestrator can budget against.

status=ok
  lookup: ok=True tokens=120 -> {"status": "shipped", "carrier": "DHL", "total": 89}
  policy: ok=True tokens=80 -> Refunds within 30 days if unopened.
answer: Order data={"status": "shipped", "carrier": "DHL", "total": 89}; policy=Refunds within 30 days if unopened.
Keep Synthesis Boring
  • The synthesise step above concatenates structured worker outputs. Resist giving it tools. Once the synthesizer can call refund, you have recreated a single powerful agent with a confusing name.

A pipeline is a workflow wearing agent clothing: stage order is fixed, each stage transforms text, and failure stops the chain. Prefer it when the steps are known. Shared State and Agent-to-Agent Protocols

Workers that mutate the same store without a single writer produce the classic bugs: double refunds, lost updates, "I thought you locked the ticket". Prefer one mutable store owned by the orchestrator, with workers returning proposed writes. For process boundaries, speak a protocol rather than sharing a Python dict.

Documented The Model Context Protocol (MCP), introduced by Anthropic in November 2024 as an open specification, is a JSON-RPC 2.0 protocol for listing and calling tools (and exposing resources and prompts) across a process boundary, over stdio or HTTP transports. Documented Google's Agent2Agent (A2A) protocol, announced in April 2025, targets the complementary agent-to-agent hop: agents advertise capabilities and exchange tasks rather than raw tool calls. The implementation below is a teaching subset: tools/list and tools/call only. It is enough to see the trust boundary.

MCP Is a Trust Boundary, Not a Sandbox
  • A tool server runs with its credentials. Connecting an agent to an untrusted MCP server is equivalent to handing it those credentials. Pin server identity, allowlist tools, and treat every tool result as untrusted text (prompt injection).
  • stdio MCP inherits the parent's environment unless you scrub it. Same lesson as Chapter 8's subprocess executor.
  • Agent-to-agent messages that carry "system" instructions from another agent are also untrusted input. Authenticate who may send them; never let peer text raise privileges.

Multi-agent

  • Isolates context and permissions per worker.
  • Parallelises independent subtasks.
  • Debate can surface disagreements a singleton hides.
  • MCP (or any RPC) makes tool hosting a deployable unit.

Costs

  • Handoffs drop constraints; partial results look like success.
  • Token cost and latency grow with every extra call.
  • Shared mutable state needs a single writer or transactions.
  • Failure attribution across agents is harder to debug.
  • Specification under-specification (Cemri et al., 2025): workers invent goals the orchestrator never stated.
  • Inter-agent misalignment: a writer "helpfully" softens a policy worker's refusal.
  • Verification gaps: no one checks the synthesised answer against worker evidence.
  • Conversation junk: agents congratulate each other while the ticket stays open.
  • Shared-state races: two workers refund the same order.
  • Protocol confusion: treating MCP tool descriptions as trusted system policy.

Long-Running Agents and Human Approval

An agent that runs for seconds can live in one process. An agent that waits on a human, a batch job or an overnight crawl cannot. You need an append-only record of what happened, the ability to resume without redoing side effects, and an approval gate that cannot be talked out of existence by fluent model text. This chapter builds those three pieces.

The Engineering Problem

A research agent plans twelve steps, finishes three, then the deploy kills the pod. Restarting from scratch re-runs web fetches, double-posts a draft, and loses the human's "approved outline" click. Separately, the same agent can call refund because the model wrote a confident JSON tool call and nothing asked a person. Durability and approval are the same engineering problem: decisions must be recorded outside the model's context window.

Requirements

  • Durable execution: progress survives process death; side effects are at-least-once with idempotency (Chapter 3) or exactly-once via a ledger.
  • Resumability: rebuild conversational state by replaying an event log, then continue; do not pickle live Python objects as the source of truth.
  • Human-in-the-loop: risky actions block until an explicit allow / deny / escalate is recorded.
  • Escalation: the run pauses with a pending action; a human or another system finishes it; the agent does not invent consent.

Event-Log Durable Runner

Chapter 4's JSON checkpointer stores a snapshot. Snapshots are fine until you need an audit trail or must distinguish "model decided" from "tool ran". An append-only event log records every transition. Replay rebuilds messages; the runner refuses to start a twin final answer if one already exists.

Approval, Denial and Escalation

The gate's decide callback is where a UI, a ticket queue or a policy engine plugs in. In tests it is a function returning allow, deny or escalate. The model never sees a shortcut: denial arrives as an observation error; escalation ends the run with a pending action for a human.

Approval Bypass Patterns
  • Model-as-approver: never ask the same agent "should I be allowed to refund?" and treat a yes as consent. Approval must come from outside the loop (UI, separate service, signed policy).
  • Tool renaming: if the gate matches on name strings, an agent that invents refund_v2 skips the list. Gate on capability tags registered with the tool registry, not free-text names.
  • CodeAct escape (Chapter 8): code that calls refund inside a loop bypasses per-call gates unless the interpreter's tool bridge enforces the same gate.
  • Replay of act without idempotency: resuming must not re-execute side effects that already have an observe. Pair the log with idempotency keys from Chapter 3.
  • Default-allow on timeout: if the human does not respond, deny or escalate; never auto-allow after N minutes for irreversible actions.

Simple version. JSONL event log on disk, in-process approval callback, idempotent tools, resume by replay.

Production version. A workflow engine or queue with exactly-once side-effect ledgers, signed approval records, SLAs on escalation, dead-letter queues, and retention policies that keep the audit log longer than the chat UI.

Why it is complicated. At-least-once delivery plus non-idempotent tools creates duplicates; exactly-once requires a ledger. Humans are slow and inconsistent; policies must encode amounts, roles and time bounds. Partial failures (act succeeded, observe never written) need reconciliation jobs.

  • Snapshot-only checkpoints with no event history when auditors ask "who approved this?"
  • Re-executing act events on resume because observe was not written.
  • Storing approval as a boolean in the prompt instead of a signed log record.
  • Escalation that leaves the pending action executable by the next model turn without a human.

Use a framework when

  • Several engineers share one graph and need a common vocabulary.
  • You want battle-tested checkpoint adapters and streaming.
  • The graph is large enough that hand-rolled routing becomes noisy.
  • You already own tests, schemas and an evaluation harness.

Skip it when

  • The loop fits in ~100 lines and changes weekly.
  • You need an audit log or approval model the framework fights.
  • Debugging requires reading framework internals more than your code.
  • Dependency and version churn cost more than the boilerplate saved.
Framework Lock-In Is Soft Until It Is Not
  • Keep the model adapter, tool registry and event log behind your own interfaces (forge.agents). Swap the graph engine later if needed. Do not put business rules only in framework-specific node configs with no tests.
  • Starting from a framework tutorial before a tested loop exists.
  • Putting approval inside a prompt node labelled "human".
  • No offline ScriptedModel tests because "the graph is the test".
  • Version pinning to latest; graph semantics move between minors.

Evaluating Agents

A single demo trajectory is an anecdote. Agents fail by being flaky, by reaching the right end state through an unsafe path, and by calling the right tool with the wrong arguments. This chapter builds forge.agents.evalh: outcome checks, trajectory invariants, tool-call scoring, cost/steps, and pass^k — the reliability metric Volume 10 introduced for tool agents.

The Engineering Problem

Two agent prompts both "solve" 40 support tickets on a single run. Prompt A is quietly wrong on a fixed 20% of ticket types but almost always right on the rest. Prompt B is slightly worse on average but randomly fails the same ticket on retry. Leadership ships B because pass@1 looks higher. Customers see inconsistent refunds. The missing metric was reliability across repeated trials, plus process checks that catch unsafe successes.

What to measure

  • Task success (outcome): final state matches the goal (DB rows, files, ticket fields).
  • Trajectory quality: required tools in order; forbidden tools absent; step budget held.
  • Tool-call accuracy: name match and argument match after canonicalisation.
  • Cost and steps: tokens and model calls per task and per success.
  • Reliability (pass^k): probability that all of k i.i.d. trials succeed.
\widehat{\text{pass}^k} = \mathbb{E}_{\text{tasks}}\left[\frac{\binom{c}{k}}{\binom{n}{k}}\right]

With n trials and c successes on a task, this is the unbiased estimator used by τ-bench (Yao et al., 2024). It is the opposite of pass@k: pass@k asks whether any try worked; pass^k asks whether every try worked.

Harness and pass^k

The harness runs each task for n independent trials (fresh sampling), scores every trial, and aggregates mean success, steps, tokens and pass^k. Kapoor et al. (2024) argue that agent claims without cost and reliability controls do not matter for deployment; the report below makes those controls unavoidable.

agent A: success=0.728 steps=1.73 tokens=518 pass^1=0.728 pass^2=0.671 pass^4=0.631 pass^8=0.575
agent B: success=0.847 steps=1.85 tokens=554 pass^1=0.847 pass^2=0.721 pass^4=0.534 pass^8=0.350

Reading the result

  • Agent B wins pass^1 (0.847 vs 0.728) and would win a single-run leaderboard.
  • At pass^8, B collapses to 0.350 while A holds 0.575: A is reliable on the tasks it can do.
  • Report cost beside reliability: tokens per trial here track steps; in production track tokens per successful task.

Task length as an axis. Kwa et al. (2025) measure agents by the time horizon of tasks they can finish: tasks are calibrated by how long skilled humans take, and a model's 50% time horizon is the human task length at which it succeeds half the time. Success falls steeply as tasks get longer, and the horizon of frontier agents grew roughly exponentially over 2019–2025. For your own evaluation this means two things: stratify golden tasks by length (steps or human minutes), and never extrapolate reliability measured on short tasks to long-running ones.

Release Gate for Agents
  • Outcome success on a stratified golden set, with slice floors.
  • Trajectory invariants: zero tolerance for forbidden tools on high-risk slices.
  • pass^k at the k that matches user retry behaviour (often 2–8).
  • Budget ceilings: p95 steps and tokens per success.
  • Paired comparison against the previous prompt/graph (Volume 10).
  • Scoring only the final answer; unsafe trajectories pass.
  • Exact string match on tool JSON without canonicalising types and enums.
  • Single-trial evaluation reported as reliability.
  • Optimising public agent leaderboards instead of a private, never-published set.
  • Ignoring cost: a 2-point success gain at 10× tokens is usually a product loss.

Review and Next Steps

What You Learned

  • An agent is a loop in which a model chooses the next action; agency has quadratic token cost, compounding error and heavy-tailed latency (Chapter 1).
  • The minimal loop (goal → model → action → tool → observation) is ordinary control flow and must be tested with scripted models before a real model ever drives it (Chapter 2).
  • Tools are an agent–computer interface: schemas, validation, idempotency and error messages written for models matter as much as the functions themselves (Chapter 3).
  • Explicit state machines, budgets and checkpoints make stop conditions and resume behaviour visible (Chapter 4).
  • Memory splits into scratchpad, episodic log and summarised history; each has a different failure mode under context pressure (Chapter 5).
  • Planning ranges from plan-then-execute to ReAct; plans need validation and caps on replanning (Chapter 6).
  • Reflection helps when an external verifier supplies signal; undirected self-critique often wastes tokens (Chapter 7).
  • Code as action (CodeAct) compresses tool use but moves the security boundary to the executor (Chapter 8).
  • Multi-agent topologies (orchestrator–worker, pipeline, debate) and MCP-style protocols buy isolation at the cost of handoff and shared-state failures (Chapter 9).
  • Long-running agents need append-only event logs, resume-by-replay, and approval gates that cannot be bypassed by model text (Chapter 10).
  • Frameworks like LangGraph map onto the same machine; own the loop before adopting the dependency (Chapter 11).
  • Agent evaluation needs outcomes, trajectory invariants, tool-call accuracy, cost/steps and pass^k — not a single demo (Chapter 12).

Important Architecture

Failure Modes

  • Building an agent where a workflow would do.
  • Untested loops driven only by live model demos.
  • Tools without schemas, idempotency or model-readable errors.
  • Implicit state; no budgets; no resume story.
  • Reflection without an external verifier.
  • Pseudo-sandboxes for CodeAct; MCP servers treated as trusted.
  • Multi-agent handoffs without contracts; shared-state races.
  • Approval in the prompt; default-allow on timeout; replay that doubles side effects.
  • Framework-first design with no owned interfaces.
  • Outcome-only eval; single-trial "reliability"; ignoring cost.

Evaluation

  • Agents are evaluated on outcomes and trajectories together (Chapter 12): task success against a verifiable end state, tool-call accuracy (name and arguments), steps and cost per successful task, and the rate of unsafe or unapproved actions.
  • Report reliability with pass^k over repeated trials, not a single run. An agent with 70% pass@1 and 30% pass^8 is not ready for unattended use; set the release gate on pass^k at the k your users will actually experience.
  • Keep deterministic tests for the loop itself with ScriptedModel: termination, step limits, malformed tool calls, tool errors, resume after crash and approval denial. These run in CI at Tier L and must never depend on a live model.
  • Evaluate the environment as carefully as the agent: seed tasks with known solutions, check the grader against human judgement on a sample, and watch for agents exploiting grader shortcuts.
  • Track long-horizon behaviour separately. Success typically falls as task length grows (Kwa et al. 2025), so stratify results by the number of steps or the human time the task would take, and only claim capability for the lengths you tested.
