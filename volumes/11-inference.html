Anatomy of Autoregressive Inference

A transformer generates one token at a time. That simple fact splits inference into two regimes with opposite bottlenecks: a parallel prefill over the prompt, then a serial decode that is almost always starved of memory bandwidth. Every optimisation in this volume targets one of those regimes — or the hand-off between them.

The Engineering Problem

A product quotes “2,400 tokens per second on an H100”. Interactive users still complain that the first token takes a second, and agents complain that long answers crawl. Throughput and latency are not the same axis. You need a vocabulary for prefill versus decode, compute-bound versus memory-bound, and the three numbers SLOs actually use: TTFT, TPOT and goodput.

Possible solutions and what each misses

  • Bigger GPU: raises peak FLOPs and HBM; does not fix a decode-bound workload if batch size is 1.
  • Shorter prompts: cuts TTFT; does nothing for TPOT once the KV is warm.
  • Batch more sequences: raises tokens/s; worsens TPOT for every sequence in the batch.
  • Engine work (this volume): KV paging, continuous batching, quantisation, speculation — each moves a different term in the cost equation.

Prefill versus Decode

  • Prefill has high arithmetic intensity: each weight byte participates in S MACs. On modern GPUs it is often compute-bound for long prompts.
  • Decode has low intensity: each weight byte is used once per step. Latency is set by how fast you can stream weights and KV from HBM, not by peak TFLOPs.
  • MQA/GQA (Volume 7) shrink the KV read; they do not shrink the weight read unless you also quantise or sparsify weights.
I_{\text{decode}} \approx \frac{2N}{2N + 2 L n_{\text{kv}} d_{\text{h}} t / B} \quad\text{(FLOPs per byte; } N \text{ params, batch } B\text{)}
Key Idea
  • At batch 1, decode sits far below the roofline knee: more FLOPs help little; bandwidth, quantisation and larger batches help a lot.
  • Prefill and decode want different hardware schedules. Disaggregated serving (Chapter 9) makes that literal.

A First Cost Model

Pope et al. (2022) organise inference cost by phase. A practical engineer’s version:

C_{\text{request}} \approx C_{\text{prefill}}(S) + (n_{\text{out}}-1)\, C_{\text{decode}}(S + n_{\text{out}}/2)
  • C_{\text{prefill}} grows roughly linearly in prompt length on a compute-bound GPU, with a quadratic term if attention is not Flash-style IO-aware.
  • C_{\text{decode}} grows with KV length (bytes moved) and is nearly flat in FLOPs.
  • Batching multiplies useful decode tokens per weight load; it does not multiply “user TPOT” favourably.

The KV Cache

Without a cache, every decode step recomputes keys and values for the entire prefix — quadratic work for a linear stream of tokens. The KV cache stores those tensors once and turns decode into an incremental update. It is also the main consumer of GPU memory per concurrent sequence, so its size sets how many users you can serve at once.

The Engineering Problem

A naive generator runs full self-attention over [1..t] at step t. Prefill already paid for those keys and values. Recomputing them wastes FLOPs and, worse, re-reads activations. You need a correct cache layout, a memory formula you can size GPUs with, and a measured speed-up on a toy model.

What the cache stores

  • Per layer, per sequence: keys and values for every past position, shape roughly (n_{\text{kv\_heads}}, t, d_{\text{head}}) each.
  • Not queries (recomputed), not the residual stream (recomputed), not attention weights (never materialised in FlashAttention).
  • With GQA/MQA, n_{\text{kv}} is smaller than query heads — the cache shrinks linearly.
M_{\text{KV}} = 2 \cdot L \cdot n_{\text{kv}} \cdot d_{\text{h}} \cdot t \cdot b \cdot B_{\text{seq}}

where b is bytes per element (2 for FP16), B_{\text{seq}} concurrent sequences, and the factor 2 is K and V.

Key Idea
  • Weight memory is fixed per replica; KV memory grows with concurrency × context. Past a few dozen long chats, KV — not weights — decides whether the next request fits.
T=256 D=64: naive 412.3 ms, cached 18.7 ms, speedup 22.0x, max|diff| at end checked OK

Implementation Notes
  • Pre-allocate (max_batch, max_seq, ...) and write into a slot, or use paged blocks (Chapter 3). Concatenate-every-step copies like the toy above do not belong in production.
  • RoPE: either cache rotated K, or cache unrotated K and apply rotation at read — engines differ; be consistent between prefill and decode.

Trade-offs

  • Larger cache dtype (FP16 vs FP8/INT8 KV): quality vs concurrency.
  • GQA: smaller KV, slight quality trade on some tasks.
  • Longer max context: reserves memory even if most chats are short — unless you page.

Failure Modes

  • Reserving B \times T_{\max} contiguous KV and running out of HBM at low real utilisation.
  • Mismatched RoPE between cached K and new queries → garbage at long context.
  • Forgetting that beam search / speculation multiplies KV by the number of active candidates.
Pitfall
  • Measuring “KV cache speed-up” only at short T. The asymptotic gap versus naive recompute grows with context; at T=32 both look fine.

Memory Management for KV

Contiguous per-sequence KV reservations fragment HBM and force you to size every request for the worst-case length. PagedAttention borrows the OS virtual-memory idea: fixed-size KV blocks, a block table per sequence, and allocation on demand. Prefix caching then reuses blocks across requests that share a prompt stem.

The Engineering Problem

With continuous batching, sequences arrive and finish at different lengths. Pre-reserving T_{\max} tokens per slot wastes most of the cache. Bumping T_{\max} for one long RAG request starves everyone else. You need non-contiguous physical storage with a logical view attention can still index.

Possible solutions

  • Contiguous slots: simple kernels; catastrophic internal fragmentation.
  • PagedAttention (Kwon et al., 2023): block tables; near-zero internal waste.
  • Prefix / radix caching (SGLang, Zheng et al., 2023): share blocks for common system prompts and multi-turn stems.
  • KV quantisation and eviction (H2O, StreamingLLM, …): fit longer contexts by compressing or dropping tokens.

Fragmentation

Key Idea
  • Attention reads logical positions 0..t-1; the kernel translates through the block table. Fragmentation becomes a free-list problem, not a layout problem.

Prefix Caching and Radix Trees

  • Many requests share a long system prompt or RAG template. Hashing token prefixes to retained blocks avoids recomputing and rewriting that KV.
  • A radix tree (SGLang) indexes shared prefixes efficiently under multi-turn and branching conversations.
  • Cache policy matters: LRU on blocks, reference counts when several sequences share a block, and eviction that never drops a live sequence’s private suffix.
prompt=[1, 2, 3, 4, 5, 9, 9]  prefix_hit=5/7
prompt=[1, 2, 9]  prefix_hit=2/3
prompt=[9, 9, 9]  prefix_hit=0/3

KV Quantisation and Eviction

  • KV INT8/FP8: store K/V in low precision; dequantise in the attention kernel. Often <1% quality loss with careful scales.
  • Eviction / streaming: drop or sink-attend old tokens (H2O, StreamingLLM) when context exceeds budget — not lossless.
  • Combine with paging: compressed blocks still need a free list and a policy.

Trade-offs

  • Smaller blocks → less internal waste, more table indirection and kernel complexity.
  • Aggressive prefix sharing → huge TTFT wins on chat templates; risk of stale shared state if mutable system prompts are mis-keyed.

Failure Modes

  • Pool exhaustion under bursty long contexts; need preemption or admission control.
  • Prefix cache key collisions when ignoring LoRA id, draft model, or sampling-affecting template tokens.
  • Evicting blocks that are still referenced by a beam or speculative branch.
Implementation Notes
  • Block size 16–256 tokens is common; tune to kernel tile sizes and average leftover partial blocks.
  • Production kernels gather K/V through the block table inside the attention kernel — they do not concatenate into a dense tensor every step as the toy gather does.
  • Admission control: reject or queue when free cannot cover the prompt’s blocks plus a decode reserve.

Batching

A GPU at batch size 1 wastes most of its decode bandwidth on under-shared weight loads. Batching raises utilisation — but static batches wait for the slowest sequence, and naive dynamic batches still stall on long prefills. Continuous (iteration-level) batching and chunked prefill are how modern engines keep the device busy without destroying latency SLOs.

The Engineering Problem

Ten chat users arrive with different prompt lengths and will generate different numbers of tokens. If you wait to form a batch of 10 and run until every sequence finishes, short replies pay for long ones. If you run them one at a time, tokens/s collapse. You need a scheduler that adds and removes sequences between decode steps.

Batching modes

  • Static: fix the batch; pad to max length; release when all done. Simple, poor tail latency.
  • Dynamic request-level: form a batch, run to completion or timeout, then form the next. Better, still couples lifetimes.
  • Continuous / iteration-level (Orca, Yu et al., 2022): every decode iteration, the batch membership can change. Finished sequences free KV; new ones enter after prefill.
  • Chunked prefill (Sarathi-Serve): split long prefills into chunks interleaved with decode so interactive TPOT does not stall behind a 32k RAG prompt.
FCFS short-first makespan=14  avg_latency=8.5  max_latency=14
FCFS long-first  makespan=14  avg_latency=11.2  max_latency=14
Pitfall
  • Unlimited prefill admission destroys TPOT for everyone already decoding. Cap prefill tokens per step (chunked prefill) and keep a decode reservation.
prefill_budget=2048  steps_to_finish_prefill_approx=2
prefill_budget= 512  steps_to_finish_prefill_approx=8
prefill_budget= 128  steps_to_finish_prefill_approx=32

Scheduler fairness

  • FCFS: simple; long jobs block the head of the queue.
  • Deficit / token fair-share: track tokens served per tenant; prefer under-served tenants when admitting.
  • Priority classes: interactive vs batch pools, or separate GPU pools (Volume 12).

Failure Modes

  • Head-of-line blocking from a multi-million-token prefill without chunking.
  • Starving batch tenants when interactive always wins admission.
  • Counting batch size in sequences rather than tokens — one 32k prefill is not “batch 1” in cost.

budget=1024 steps_to_drain_prefill=3  last_step={'decode': 32, 'prefill': 920}
Implementation Notes
  • Real engines track tokens and KV blocks as separate resources; a sequence may be runnable for decode but blocked on memory.
  • Preemption: pause a low-priority prefill mid-chunk to reclaim blocks for an interactive decode — only safe with paging.

Quantisation Fundamentals

Quantisation maps high-precision tensors to fewer bits so weights (and sometimes activations or KV) move less data through memory. The engineering core is not the bit width alone — it is how you choose scales, where you share them, and how you calibrate them so accuracy loss stays acceptable.

The Engineering Problem

A 70B FP16 model needs ~140 GiB just for weights. Decode is memory-bound, so halving bytes nearly doubles tokens/s if kernels keep pace. Blindly casting to INT8 destroys quality on some layers. You need the standard affine maps, granularity choices and a calibration loop.

x_q = \operatorname{clamp}\!\left(\operatorname{round}\frac{x}{s} + z,\, q_{\min},\, q_{\max}\right), \quad \hat{x} = s\,(x_q - z)
  • Symmetric: z = 0, scale from max abs.
  • Asymmetric: non-zero zero-point fits skewed distributions (common for activations).
  • Per-tensor: one scale for the whole matrix — cheap, often too coarse.
  • Per-channel / per-token: scale along the dimension with largest dynamic-range variation.
  • Group-wise: e.g. groups of 128 weights — the INT4 sweet spot for GPTQ/AWQ-style methods.
Key Idea
  • Error is roughly proportional to scale. Outliers force a huge scale and drown the rest of the tensor in quantisation noise — hence SmoothQuant, GPTQ Hessian weighting and AWQ’s salient-channel protection.
sym per-tensor       MSE=0.048211
sym per-channel(0)   MSE=0.000312
activations asym MSE=0.000041  sym MSE=0.000118

Calibration

  • Max / percentile: collect activation ranges on a calibration set; percentile clips rare spikes.
  • MSE / entropy minimisation: search scales to minimise reconstruction or KL to FP16 softmaxes.
  • Always hold out a task metric (perplexity, MMLU slice, your golden set) — MSE alone lies.

Weight Quantisation Methods

Production stacks almost always ship weight-only or W8A8 quantisation rather than pure FP16. This chapter builds miniature versions of the ideas behind LLM.int8(), SmoothQuant, GPTQ and AWQ, then sketches FP8 and how to evaluate quality after compression.

The Engineering Problem

You must fit a model on one GPU (or reduce HBM traffic for decode) without a week of QAT. Post-training methods differ in what they protect: outlier features (LLM.int8), activation smoothing (SmoothQuant), second-order weight error (GPTQ), or salient channels under activation magnitude (AWQ).

Mini LLM.int8() and SmoothQuant

  • Dettmers et al., 2022: keep outlier activation features in FP16; matrix-multiply the rest in INT8.
  • Xiao et al., 2022: migrate difficulty from activations to weights via a diagonal smooth factor X \operatorname{diag}(s)^{-1}, \operatorname{diag}(s) W, then quantise both more evenly.
rel err vanilla W8A8=0.1823
rel err SmoothQuant =0.0411

Mini GPTQ and AWQ

  • GPTQ (Frantar et al., 2022): quantise weights column-by-column (or block), compensating remaining weights with a Hessian-aware update from calibration activations.
  • AWQ (Lin et al., 2023): find ~1% salient channels by activation magnitude; protect them with higher effective precision via per-channel scaling, then round the rest.
rel err RTN  =0.0942
rel err GPTQ~=0.0618
RTN rel=0.1120  AWQ-like rel=0.0487

FP8 Overview

  • Hardware-native on Hopper/Blackwell tensor cores; E4M3 for weights/activations often, E5M2 for gradients in training.
  • Needs per-tensor or per-block scaling (often dynamic); friendlier than INT8 when outliers are moderate.
  • Still validate task metrics — FP8 is not “free accuracy”.

Quality Evaluation

  • Perplexity on a held-out corpus as a cheap smoke test.
  • Capability suites and your golden tasks (tool calls, RAG faithfulness).
  • Compare matched decode settings; quantisation can interact with temperature and long-context.
Implementation Notes
  • Weight-only W4A16 is usually enough for decode speedups when activations stay FP16 — INT4 GEMM is optional if you dequantise to FP16 before matmul.
  • Pack INT4 values (two weights per byte) in the Forge module; the toys above keep floats for clarity.

Failure Modes

  • Quantising embeddings or LM head with the same recipe as MLP layers.
  • Shipping AWQ/GPTQ without checking long-context or code benchmarks.
  • Mixing scales from one checkpoint with weights from another.

Speculative Decoding

Decode is serial and memory-bound. Speculative decoding uses a cheap draft model (or heads) to propose several tokens, then verifies them in one parallel forward of the target model. With the right acceptance rule, the output distribution matches the target exactly — you buy latency, not a different model.

The Engineering Problem

TPOT is limited by one full-model step per token. A 7B draft might run several times in the time a 70B target runs once. If many draft tokens are accepted, wall-clock tokens/s rises. If acceptance is low, you paid extra work for nothing. The acceptance sampler must not bias the distribution.

Family of methods

  • Draft–verify (Leviathan et al., 2022; Chen et al., 2023): separate small draft LM.
  • Medusa (Cai et al., 2024): extra heads on the target predict future tokens.
  • EAGLE (Li et al., 2024): draft from feature-level autoregression over hidden states.
  • N-gram / prompt lookup: draft from prompt copies or a datastore — zero train cost, variable acceptance.

Exact Acceptance Sampling

Given draft tokens \tilde{x}_{1:k} from q and target probabilities p at each position (one parallel target forward with KV), accept token i with probability \min\!\left(1,\, p(x_i\mid x_{<i}) / q(x_i\mid x_{<i})\right). On rejection, sample from the adjusted residual distribution. Guarantees x \sim p.

Key Idea
  • Expected accepted length grows when q \approx p. A poorly matched draft can be slower than vanilla decode.
target p  [0.05 0.1  0.15 0.3  0.4 ]

Trade-offs

  • Medusa/EAGLE avoid a second model in memory but need training.
  • Lossless verification keeps quality; lossy “always take draft” does not.
  • Speculation multiplies KV for draft branches unless carefully shared.

Failure Modes

  • Draft much stronger or weaker than target → low acceptance, net slowdown.
  • Implementing acceptance without residual resampling → biased outputs.
  • Measuring speedup only on easy repetitive text where n-gram drafts shine.
Implementation Notes
  • Share the target KV between verification positions; only draft KV (or Medusa tree) is extra.
  • Tree attention (Medusa) verifies multiple candidate branches in one target forward.
  • Keep sampling RNG identical between baseline and speculative paths when A/B testing quality.

Attention Kernels and GPU Optimisation

Standard attention materialises an S \times S score matrix and streams it through HBM — often slower than the FLOPs suggest. FlashAttention tiles the computation, fuses softmax with the value multiply, and keeps tiles in SRAM. Online softmax makes that fusion numerically safe.

The Engineering Problem

A 4k-context decode still reads a long KV; a 32k prefill wants an S^2 attention matrix that does not fit in cache. You need tiling, a numerically stable online softmax, and a sense of how torch.compile and Triton fit into the stack — without requiring a GPU to learn the algorithm.

Online Softmax

m_i = \max(m_{i-1},\, \ell_i),\quad \alpha = e^{m_{i-1}-m_i},\quad \ell_i^{\text{new}} = \alpha \ell_{i-1} + e^{x_i - m_i}

Running max and normaliser let you merge tiles without revisiting earlier scores.

max|flash - naive| = 2.22e-15
Implementation Notes
  • Production FlashAttention-2/3 improves work partitioning and warp scheduling; the maths is the same online softmax + tiling.
  • Fused kernels also merge bias, dropout and residual paths — fewer HBM round-trips.
  • torch.compile can fuse pointwise chains; for attention, prefer a known FlashAttention backend.
  • Triton: write tiled GEMM/attention in a Python DSL that compiles to GPU kernels — Tier G exercise.
compile match max|diff|=0.00e+00
note: use CUDA + inductor backend for real fusion wins

Failure Modes

  • Reimplementing attention in PyTorch ops for production decode — leaves performance on the table.
  • Ignoring numerical differences between FlashAttention variants when debugging “nondeterminism”.
  • Expecting torch.compile to rewrite a custom paged-attention kernel automatically.

Fused Kernels and Graphs

  • Fusion: combine RMSNorm + QKV projection, or bias+activation+residual, to cut launches and HBM round-trips.
  • CUDA Graphs: capture a decode step’s launch sequence when shapes are static (fixed batch of pages); replay with tiny CPU overhead.
  • torch.compile: good for pointwise and GEMM chains; pair with SDPA/FlashAttention backends rather than rewriting attention in Python.
  • Triton: author tiled kernels with explicit block sizes; ideal for custom fused ops once you know the algorithm from the NumPy reference.

Distributed Inference

One GPU eventually runs out of HBM or decode bandwidth. Tensor parallel shards weights inside a layer; disaggregated serving splits prefill and decode across pools; MoE adds expert parallel so only routed experts run. Each preserves correctness while changing the latency/throughput frontier.

The Engineering Problem

A 70B FP16 model barely fits on one 80 GB GPU after KV; a 405B model does not. Interactive traffic wants low TTFT and low TPOT simultaneously — but prefill loves FLOPs and decode loves bandwidth. One homogeneous replica pool forces a compromise.

CPU and Edge Inference

Not every deployment has an H100. Laptops, phones and CPU-only servers run quantised models through llama.cpp/GGUF, ONNX Runtime and Apple MLX. The art is knowing when CPU is the right cost and latency trade — and when it is false economy.

The Engineering Problem

A team wants offline document Q&A on employee laptops, or a 3B model beside a backend with no GPU quota. Cloud GPU serving would work but blows the budget at their QPS. You need a map of CPU/edge stacks and decision rules.

Key Idea
  • CPU often wins on privacy / offline / idle-included hardware you already own, not on raw $/MTok against a busy managed GPU at scale.
  • Aggressive GGUF quant (Q4_K_M) is the usual enabler; validate quality like Chapter 6.

When CPU / edge is right

  • Air-gapped or on-device constraints; data cannot leave the machine.
  • Burst-sparse interactive use on hardware already purchased (dev laptops, kiosks).
  • Small models (<8B) with Q4–Q5 quants and modest context.
  • Prefill-light, short-output tools where 20–60 tok/s is acceptable.

When it is wrong

  • High QPS chat with SLO TPOT < 30 ms.
  • Long-context RAG prefills — CPU prefill scales poorly.
  • Large MoE without specialised kernels.

Benchmarking Inference

Optimisations without a methodology produce dashboards that cannot decide a ship call. Inference benchmarks must fix the workload, separate prefill from decode, report percentiles, and prefer goodput under SLOs — and finally convert that into cost per million tokens.

The Engineering Problem

Vendor A claims 3× tokens/s; vendor B claims 2× lower TTFT. Workloads differ (ShareGPT vs long RAG), batching policies differ, and one run includes warm-up while the other does not. You need a repeatable harness that answers: “At our SLO, how many successful tokens/s and at what $?”

Key Idea
  • Goodput = throughput of requests that meet all latency SLOs. Tokens/s that miss p95 TTFT are not capacity.
Engine A
n=500  TTFT p50/p95=244/712 ms
TPOT p50/p95=28.1/34.5 ms
throughput=1000 tok/s  goodput=722 tok/s  in_SLO=72.2%  $/MTok=0.050
Engine B
n=500  TTFT p50/p95=279/345 ms
TPOT p50/p95=35.0/39.9 ms
throughput=1000 tok/s  goodput=948 tok/s  in_SLO=94.8%  $/MTok=0.050
  • Same raw throughput and $/MTok on all tokens; B wins on goodput under the SLO — the number that should drive engine choice.

Methodology checklist

  • Fix prompt/output length distributions (or replay production traces).
  • Separate warm-up from measured window; pin model, engine version, sampling.
  • Open-loop load generation for capacity; closed-loop for UX at fixed concurrency.
  • Report TTFT and TPOT percentiles, not only means; include failure/timeouts.
  • Sweep concurrency; plot goodput vs load until SLO collapse.
  • Convert to $/MTok at the concurrency you will actually run (with headroom).
Pitfall
  • Benchmarking only greedy decode on short prompts — hides prefill and sampling costs you will see in production.

Failure Modes

  • Comparing engines at different maximum batch sizes without stating the TPOT trade.
  • Omitting prefix-cache hit rate when the production workload is multi-turn.
  • Cost models that assume 100% GPU utilisation 24×7.

  • Log prefix-cache hit rate, batch size, and KV utilisation beside latency — otherwise you cannot explain a regression.
  • Pin seeds and disable non-deterministic kernels when comparing quality across engines.

Extend the harness to charge separately for input and output tokens (as APIs do). Re-rank engines A and B when input tokens are 10× output tokens (RAG) versus 1× (chat).

Volume Review

What You Learned

  • Autoregressive inference splits into compute-heavy prefill and memory-bound decode; TTFT, TPOT, throughput and goodput measure different things.
  • The KV cache makes decode incremental; its memory grows with concurrency × context and often exceeds weight memory.
  • PagedAttention removes contiguous-reservation fragmentation; prefix/radix caches reuse shared stems; KV quant and eviction extend context at a quality cost.
  • Continuous (iteration-level) batching and chunked prefill keep GPUs utilised without letting long prefills destroy interactive TPOT; fairness needs an explicit policy.
  • Quantisation is affine maps plus scale granularity and calibration; outliers dominate error.
  • LLM.int8, SmoothQuant, GPTQ and AWQ attack outliers differently; FP8 is hardware-native on recent GPUs; evaluate with task metrics, not MSE alone.
  • Speculative decoding with exact acceptance sampling preserves the target distribution; speedup needs a matched draft (Medusa, EAGLE, n-gram).
  • FlashAttention tiles attention with online softmax to cut HBM traffic; fused kernels, torch.compile and Triton are the practical tooling layer.
  • Distributed serving uses TP to fit models, disaggregated prefill/decode to split bottlenecks, and expert parallel for MoE.
  • CPU/edge stacks (llama.cpp/GGUF, ONNX, MLX) win for privacy, offline and owned hardware — not automatically for $/MTok at scale.
  • Benchmark with fixed workloads, percentiles and SLO-constrained goodput; convert to cost per million tokens at real utilisation.

What You Built

  • Roofline classifiers for prefill vs decode; naive vs KV-cached attention generators with timed speed-ups.
  • PagedKV with block tables, plus a radix-style prefix cache.
  • A continuous-batching scheduler sketch and chunked-prefill token budgets.
  • Symmetric/asymmetric and per-channel quantisers; mini SmoothQuant, GPTQ-style compensation and AWQ-like salient scaling.
  • Exact speculative acceptance sampling with an empirical distribution check; n-gram prompt drafting.
  • A NumPy FlashAttention reference matching naive attention; a torch.compile smoke test.
  • TP matmul identities, a tiny MoE router, CPU vs API cost break-evens, and a goodput benchmark harness.

Failure Modes

  • Decode-bound chat sized from peak TFLOPs.
  • Contiguous KV reservations that look fine at mean length and OOM at p99.
  • Unlimited prefill admission starving decode TPOT.
  • Per-tensor INT8 on outlier-heavy activations.
  • Speculative decoding without residual resampling (biased text).
  • TP degree so high that collectives dominate TPOT.
  • CPU deployments sold on GPU-class latency promises.
  • Throughput leaderboards without SLO-constrained goodput.

Evaluation

  • Every optimisation is a change to the model's output distribution or to its latency distribution, so gate it on both. Run the Volume 10 quality suite (golden set, task success, judge win-rate against the unoptimised baseline) before and after, and report the paired difference with a bootstrap interval, not a single score.
  • Exactness checks come first: the KV-cached generator must match naive greedy decoding token for token; paged KV must match contiguous KV; speculative decoding must match the target model's sampling distribution (test with a chi-squared check over many seeds, Chapter 7).
  • Lossy optimisations (INT8, INT4, FP8, KV quantisation, eviction) need a non-inferiority margin agreed in advance: for example perplexity within 1% and task success no more than 1 point below FP16, measured on long-context and code slices as well as the average, because quantisation damage concentrates in the tails.
  • Performance is evaluated as goodput under SLO at a stated workload mix (Chapter 11): TTFT and TPOT percentiles, requests per second meeting both, and $/MTok at that load. Always publish the workload, hardware, engine version and batch policy with the number.
  • Keep a regression benchmark in CI at Tier L (tiny model, fixed prompts, fixed seed) that fails when tokens/s drops or output tokens change unexpectedly; run the Tier G benchmark on every engine or kernel upgrade.

Iteration-level scheduling: enter/leave the batch between decode steps.
