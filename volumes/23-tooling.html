A Framework for Evaluating Tools

Every quarter a new framework claims to replace your stack. The engineering problem is not finding tools; it is deciding which ones you are willing to own for years, which ones you rent, and which ones you ignore.

The Engineering Problem

A team adopts a popular agent framework because the demo graph is elegant. Six months later the product needs streaming, human approval, multi-tenant budgets and a non-Python worker. The framework's abstractions fight every requirement. Migration cost exceeds the original build. The demo was never an evaluation.

What a tool evaluation must answer

  • Job to be done: which concrete failure or bottleneck does this tool remove?
  • Boundary: what does it own, and what must you still build around it?
  • Exit cost: how hard is it to leave if the project dies, prices rise or requirements change?
  • Operational fit: does it match your languages, clouds, compliance and on-call skills?
  • Evidence: can you measure the claim on your workload in a week, not a slide deck?
Key Idea
  • Tools are contracts: APIs, data formats, operational burden and switching cost.
  • Prefer tools that speak open interfaces (OpenAI-compatible HTTP, OpenTelemetry, MCP, ONNX, standard registries) over tools that invent a private dialect for everything.
  • A short spike with a written scorecard beats a long architecture debate.

Buy, Build, Integrate

Prefer buy / adopt when

  • The hard problem is commodity (serving engines, object storage, vector indexes).
  • An open interface lets you swap the implementation later.
  • Your differentiation is the product, eval set and data — not the framework.

Prefer build / thin wrap when

  • The tool's control flow fights your reliability or security model.
  • Lock-in would put a core control plane behind a vendor API.
  • You need a pedagogical or test double (Forge packages in earlier volumes).
Trade-off
  • "Not invented here" and "framework of the month" are symmetric failure modes. The scorecard is the antidote to both.

Spike Protocol

  1. Write the success metric and the workload (requests, tokens, documents, failure injection).
  2. Time-box to a few days. One engineer owns the spike; another reviews the scorecard.
  3. Exercise the failure path: kill the process, revoke a credential, overflow the context, inject a poisoned tool result.
  4. Estimate exit cost: what artefacts and skills become useless if you leave?
  5. Decide: adopt, adopt behind a thin interface, or reject. Write the decision down.
Implementation Notes
  • Put the scorecard in the RFC or ADR, not in a private chat.
  • Pin versions in the spike the way you will in production.
  • If the vendor will not run against your eval harness, treat marketing numbers as untrusted.

Total Cost of Ownership

Licence price is the visible line item. Ownership cost includes people, incident load, migration options and the opportunity cost of a worse interface.

Open Interfaces Worth Preferring

  • OpenAI-compatible HTTP for chat and embeddings clients (Volumes 1 and 12).
  • OpenTelemetry GenAI conventions for spans and usage metrics.
  • MCP for reusable tool servers across agents and IDEs.
  • OCI images + content digests for deployable artefacts.
  • Standard model cards / registry metadata rather than proprietary-only lineage.
Research Frontier
  • Tool ecosystems consolidate and fragment in waves. Optimise for replaceability of the control plane you own (policy, eval, data), not for predicting next year's winning brand.

Pick one tool your team adopted in the last year. Fill the scorecard honestly in thirty minutes. Would you adopt it again? What interface would have lowered exit cost?

Failure Modes

  • Choosing by GitHub stars or conference keynote.
  • Evaluating only the happy path.
  • Adopting three overlapping tools "for flexibility" and owning none well.
  • Skipping licence review until legal blocks the launch.
  • Optimising for demo latency and discovering multi-tenant fairness later.
  • No revisit date: a rejected tool never gets reconsidered when the landscape moves.

Model Development Tools

Training and adapting models still rests on a small set of libraries. PyTorch and Hugging Face dominate most LLM engineering. JAX and Lightning matter when you need their specific strengths. The goal is to know what each owns so you do not rebuild them.

The Engineering Problem

A team starts from research notebooks with ad hoc training loops, unversioned checkpoints and a different CUDA stack per laptop. Reproducing a run takes a week. Shipping a fine-tune takes a month. The model is not the bottleneck; the lack of a shared development toolkit is.

Core model-development tools and what they own.
ToolPrimary jobYou still ownTypical use in this book
PyTorchTensors, autograd, nn modules, CUDA/Metal backends, torch.compileData pipelines, distributed recipes, servingDefault research and production training stack
Hugging Face TransformersModel definitions, tokenisers, generate, Hub checkpointsTraining orchestration quality, eval, licence complianceLoad open-weight LLMs; fine-tune with Trainer / TRL
Hugging Face Datasets / Accelerate / PEFT / TRLData loading, multi-GPU launch, LoRA, RLHF/DPO loopsYour data contracts and eval gatesAdaptation without rewriting distributed code
JAXFunctional transforms (jit, grad, pmap/pjit), XLAEcosystem familiarity; debugging habits differ from PyTorchLarge-scale research stacks (e.g. MaxText-style)
PyTorch Lightning / FabricTraining loop boilerplate, hooks, multi-device strategiesNot a substitute for understanding the loopTeams that want structure without a full custom trainer

PyTorch in Practice

  • Eager by default: easy debug; compile or export when the kernel graph is stable.
  • Device placement: be explicit about CPU vs CUDA vs MPS; silent copies destroy throughput.
  • AMP and dtype: BF16/FP16 training needs loss scaling awareness; inference often uses FP8/INT8 via separate stacks (Volume 11).
  • Distributed: FSDP/HSDP for large models; know what is sharded versus replicated.
Key Idea
  • PyTorch is the substrate (Paszke et al., 2019: eager, define-by-run execution was the design choice that won research and then production). Hugging Face is the model zoo and adaptation toolkit on top of it for most LLM teams (Wolf et al., 2020).
  • If you cannot load a checkpoint, run a forward pass and compute your eval metric outside the framework's Trainer, you do not control the model.

Hugging Face Ecosystem

Risk
  • Hub models can include custom code. Prefer trust_remote_code=False unless you have audited the repository.
  • Model licences are not all Apache-2.0. Commercial use and redistribution constraints belong in the registry (Chapter 3).

JAX Overview

  • Strengths: pure functions, XLA compilation, strong multi-host scaling stories in research labs.
  • Costs: smaller industry hiring pool; debugging compiled traces; ecosystem packages differ from PyTorch's.
  • Rule: adopt JAX when your org already runs it at scale, or when a specific codebase you must use is JAX-native. Do not switch mid-product for fashion.

Implementation Notes
  • If you maintain both, isolate packages and CI images. Mixed CUDA stacks on one laptop are a time sink.
  • Prefer one substrate per product service unless there is a written reason.

Lightning

Lightning (and Fabric) structures the training loop: hooks for train/val steps, checkpointing and strategy selection. It helps teams standardise. It does not remove the need to understand gradient accumulation, checkpoint formats or eval. Prefer Fabric when you want less magic than full Lightning modules.

Lightning helps when

  • Many engineers share training jobs and need a common skeleton.
  • You want multi-GPU strategies without rewriting boilerplate each time.

Lightning hurts when

  • The abstraction hides a bug you cannot see in the loop.
  • Your job is a thin HF Trainer / TRL script and Lightning adds a second paradigm.
Practical Default
  • Default stack for this book's audience: PyTorch + Transformers + PEFT/TRL + Accelerate.
  • Keep a one-file "load, generate, score" script that does not depend on your Trainer. Use it as a smoke test after every upgrade.

Adaptation Tooling: PEFT and TRL

Full fine-tunes are rare for product teams. LoRA/QLoRA via PEFT and supervised / preference loops via TRL cover most adaptation work. The engineering risks are data quality, eval leakage and checkpoint hygiene — not whether you can call get_peft_model.

Adaptation path versus when to use it.
PathWhenCost / risk

Environment and Reproducibility

  • Lock CUDA, drivers, PyTorch and Transformers together in an image digest.
  • Record seeds, dataloader order flags and eval decoding parameters.
  • Prefer content-addressed checkpoints over "final.pt" on a shared drive.
  • Separate training code from scoring code so metric changes are reviewable.
Trade-off
  • Hugging Face Trainer speeds experiments and can hide batching or padding bugs. Keep a non-Trainer smoke path.

Break your smoke script on purpose (wrong revision, missing pad token). Confirm it fails loudly. Then add the same check to CI for model upgrades.

Experiment Tracking and Registries

If you cannot answer which checkpoint, which data digest and which hyperparameters produced a metric, you do not have ML ops — you have folklore. Trackers and registries turn folklore into artefacts.

The Engineering Problem

Two fine-tunes both claim "better than baseline". One used a different eval split. The other silently changed the system prompt in the scoring script. Leadership asks which model to ship. Nobody can reconstruct either run from logs alone.

MLflow versus Weights & Biases — roles, not a beauty contest.
ConcernMLflowWeights & Biases
Core modelOpen-source platform; self-host friendlySaaS-first; strong UI and collaboration
TrackingExperiments, params, metrics, artefactsRuns, metrics, media, reports
Model registryFirst-class stages (Staging/Production)Artefact/model registry patterns; often paired with other stores
LineageRun → model version linksRun graphs, tables, sweeps
Lock-in riskLower if you own the store; UI is secondaryHigher if all history lives only in their cloud
Best fitTeams that want OSS + registry in one placeTeams that want fast iteration UX and hosted convenience
Key Idea
  • Log enough to reproduce: code SHA, data digest, config, seed, metric definitions, model binary digest.
  • The registry is the release surface. Tracking is the laboratory notebook. Do not conflate them.

What to Log Every Run

  • Identity: run id, git commit, container digest, hardware.
  • Data: dataset name, version or content hash, train/eval split ids.
  • Config: hyperparameters, prompt templates, decoding params if they affect scores.
  • Metrics: primary online/offline metrics with confidence intervals when possible.
  • Artefacts: checkpoints, tokenizer, eval predictions sample, confusion cases.

Registry Discipline

  1. Immutable versions: never overwrite "Production"; promote a new version.
  2. Required metadata: eval report link, data licence, model licence, known failure modes.
  3. Stage transitions gated by CI: offline eval + smoke serve + canary (Volume 12).
  4. Rollback means pointing traffic at a previous digest, not rebuilding from memory.
Trade-off
  • Heavy logging costs storage and can leak prompts or PII into the tracker. Redact; sample; set retention.

Failure Modes

  • Metrics without metric definitions (different tokenisers, different judges).
  • Registry that stores names but not digests.
  • W&B-only history with no export plan for audits.
  • "Latest" tags used in production instead of immutable versions.

Model Cards and Release Notes

A registry entry without a model card is a binary with a nickname. Cards need not be long; they must be honest.

  • Intended use and explicitly out-of-scope uses.
  • Training data summary (sources, licences, known gaps).
  • Eval results with dataset ids and decoding settings.
  • Known failure modes (languages, domains, safety).
  • Compute and carbon notes when your org tracks them.
Practical Default
  • Self-host MLflow if compliance demands data residency and you want registry+tracking together.
  • Use W&B when collaboration UX pays for itself — and schedule exports.
  • Either way: promotion to Production is a CI job, not a UI click without evidence.

Take one historical "best model" story in your team. Reconstruct the data digest and git SHA. If you cannot, that is the backlog item — before the next fine-tune.

Serving Tools

Volume 12 built serving as a systems problem. This chapter is the product map: which engines to try for which workload, and how they relate. Prefer OpenAI-compatible HTTP as the client contract so engines stay swappable.

The Engineering Problem

You have an open-weight model and a latency SLO. One engineer installs a desktop runner. Another deploys a research server. A third wraps Transformers in FastAPI. All three "work" in a demo and disagree on throughput by 10× under load. You need a serving tool chosen for traffic shape, not familiarity.

Serving engines — comparison for engineering choice (details evolve; re-benchmark).
EngineStrengthWeaknessDefault when
vLLMPagedAttention, continuous batching, broad model/hardware coverage, OpenAI serverFast-moving flags; tune per versionSelf-hosted open-weight LLMs at scale
SGLangRadixAttention prefix cache; strong structured / agentic multi-call programmesSmaller ecosystem than vLLMShared-prefix and tool-heavy workloads
TGI (Text Generation Inference)HF-native serving path; production-orientedLess universal than vLLM in many benchmarks todayHF-centric stacks that already standardise on TGI
OllamaLocal DX: pull model, run API, great for laptops and demosNot the multi-tenant GPU scheduler for large fleetsDev machines, edge prototypes, small teams

Key Idea
  • Engines package Volume 11 ideas (paging, batching, kernels). You still own API, auth, probes, rollout and cost.
  • Benchmark goodput and $/MTok on your prompt length mix. Public leaderboard numbers are starting points.

Selection Heuristic

  1. Need laptop/CPU first? Start with Ollama or llama.cpp; measure quality under your quantisation.
  2. Need multi-tenant GPU throughput? Bake off vLLM vs SGLang (and TGI if HF-standardised) on your traces.
  3. Need many model types in one platform? Triton as the outer server; LLM backend still chosen explicitly.
  4. Always keep a thin client interface so changing engines is a config change plus a canary.
Implementation Notes
  • Pin engine versions in images. Serving regressions often arrive as "helpfully" changed defaults.
  • Expose /health and metrics your autoscaler understands (queue depth, KV utilisation).
  • Prefix caching changes economics for RAG and agents; include shared-prefix tests in the bake-off.
Trade-off
  • Ollama for production GPU fleets is a category error. vLLM for every laptop prototype is also a category error. Match the tool to the environment.

Engine Bake-Off Protocol

  1. Capture a replay set: prompt length histogram, system prompt sharing, tool-call traces.
  2. Fix model weights and quantisation; pin engine versions in images.
  3. Measure TTFT, TPOT, goodput, error rate and $/MTok at the SLO concurrency.
  4. Include a prefix-heavy mix if you serve RAG or agents.
  5. Chaos: kill a replica mid-stream; verify client retries and idempotency keys.

RAG and Data Tools

Retrieval quality is mostly data engineering. Tools help you load, chunk, embed, index and refresh corpora. They do not invent a good chunking policy or a trustworthy corpus (Volume 14).

The Engineering Problem

A product wires a vector database to a chat UI in an afternoon. Citations look great on the launch corpus. Three months later documents are stale, chunk boundaries split tables, and nobody can rebuild the index from source. The vector DB was never the hard part.

RAG / data tooling layers.
LayerExamplesJobCommon failure
Connectors / loadersUnstructured, custom ETL, crawl pipelinesIngest from Drive, HTML, PDFs, ticketsSilent parse loss; no checksums
Chunking / parsingCustom splitters; docling-style parsers; LlamaIndex node parsersStructure-aware segmentsNaive fixed windows across tables/code
EmbeddingsHF models, vendor APIs, multimodal encodersVectors for similarityModel swap without reindexing
Vector / hybrid storespgvector, OpenSearch, Pinecone, Weaviate, Qdrant, ChromaANN + filters + hybrid BM25No metadata filters; no hybrid
Orchestration libsLangChain/LlamaIndex retrievers; custom graphsGlue retrieval to promptsBusiness logic trapped in framework glue
Eval for RAGRagas-style metrics; custom labelled setsFaithfulness, context precisionOnly vibe-checking answers
Key Idea
  • Own the document identity, version and chunk ids. Treat the index as a build artefact.
  • Prefer Postgres+pgvector or OpenSearch when you already operate them and need joins/filters; use specialised vector DBs when ANN scale or features justify another system.

Build Versus Framework

Thin custom pipeline

  • Clear data contracts and tests.
  • Easy to swap embedder and store.
  • Matches Volume 14 teaching architecture.

Heavy framework glue

  • Fast first demo.
  • Harder to see retrieval failures.
  • Upgrades reshape abstractions under you.
Practical Default
  • Start with a store you can query with SQL or familiar search APIs.
  • Version the embedding model id into the index name.
  • Keep a golden question set in CI; fail index deploys on retrieval regressions.

Failure Modes

  • Re-embedding into the same collection with a new model and mixed vector spaces.
  • No delete/tombstone story when source documents are removed (privacy incident waiting).
  • Chunking code that only exists inside a notebook.

Agent and Orchestration Tools

Agent frameworks accelerate expressing control flow. They are not harnesses (Volume 16). MCP standardises tool servers. Lock-in appears when your product logic is unreadable outside the framework's graph dialect.

The Engineering Problem

A prototype in LangGraph ships to production. Permissions live in node functions. Budgets are "max steps" in a config file. Traces are framework-specific. A security review asks for complete mediation of tool calls. The answer is a rewrite — because the framework was treated as the security boundary.

Agent / orchestration surfaces.
Tool / protocolWhat it gives youWhat it does not give you
LangGraphStateful graphs, checkpoints, durable execution patternsA default-deny security policy; org-wide budgets; sandboxing
LangChain / LlamaIndex agentsBatteries-included tools and retrieversStable long-term abstractions (expect churn)
MCP (Model Context Protocol)JSON-RPC tool/resource protocol; reusable serversTrust: servers and results are still untrusted data (Volume 16)
Custom loop + harnessFull control; testability; clear policy pointMore code to write up front
Workflow engines (Temporal et al.)Durable business workflows around model callsLLM-specific decoding / tool semantics
Key Idea
  • Use a framework to express the graph. Enforce effects in a harness: policy, budget, approval, sandbox, trace.
  • MCP is a transport and schema boundary. It is not an allow-list.

Lock-in Patterns

  • Graph lock-in: business rules only exist as framework nodes with proprietary state serializers.
  • Vendor lock-in: traces, evals and prompts only readable in one SaaS.
  • Protocol lock-in (benign): speaking MCP or OpenAI tools is usually good — many clients can call them.
  • Model lock-in: prompts and tools tuned to one provider's quirks without an adapter layer.
Trade-off
  • Avoiding all frameworks can waste time. Accepting all framework opinions can waste the company. Put product logic and policy in modules you can unit test without starting the graph runtime.
Risk
  • MCP server descriptions and results can inject instructions. Policy must run on the next tool call regardless of what the server said.
  • Framework "memory" stores that write unbounded user data into prompts need retention and access control.
Practical Default
  • Prototype graphs quickly; extract pure functions early; put the harness interface under test with a scripted model.
  • Prefer MCP for reusable tool servers when multiple agents/products need the same integrations.

MCP in the Tooling Landscape

  • Servers expose tools/resources over JSON-RPC — filesystem, browser, SaaS, internal APIs.
  • Clients (IDE agents, Claude Code, custom harnesses) discover and call those tools.
  • Benefit: write an integration once; reuse across coding agents and product agents.
  • Non-benefit: protocol compliance ≠ safety. Volume 16's policy still decides allow/ask/deny.
Lock-in severity for agent stacks.

OpenAI tool JSON schemasLowMany runtimes speak them

Trade-off
  • Durable graph execution (checkpoints, resume) is valuable and can couple you to a serializer. Budget an export/migration test yearly.

List every tool your agent can call. Mark which are mediated by a harness policy versus only by a prompt. Anything unmarked is a finding.

Evaluation and Observability Tools

Volume 10 treated evaluation as engineering. Volume 16 treated traces as evidence. This chapter names the tool categories that implement those disciplines in day-to-day work.

The Engineering Problem

Production quality drops after a prompt change. Logs show the final answer but not the retrieved chunks, tool calls or token costs. Offline eval was a spreadsheet last updated before launch. Nobody can tell whether the regression is retrieval, routing or the model.

Eval and observability tool categories.
CategoryExamplesUse for
Offline eval harnessesCustom pytest; Inspect; LightEval; promptfooCI gates on golden sets
LLM-as-judge platformsIn-house judges; vendor eval productsRubric scoring with known bias limits
Tracing UIsLangSmith, Arize Phoenix, Helicone, BraintrustDebugging spans, datasets from prod
OpenTelemetry GenAIOTel collectors + your APMVendor-neutral spans and metrics

Key Idea
  • Own the eval set and metric definitions even if a SaaS runs the UI.
  • Prefer exporting OpenTelemetry-compatible spans so traces outlive any one vendor.

What a Good Trace Contains

  • Request id, user/tenant id (careful with PII), model id and version.
  • Token usage and estimated cost.
  • Retrieval: query, hit ids, scores — not necessarily full document text in hot storage.
  • Tool calls: names, args (redacted), latency, policy decision.
  • Final output hash or stored output under retention policy.
Risk
  • Full prompt logging recreates a second copy of customer secrets. Default to redaction and sampling.

SaaS tracing

  • Fast setup, good UX for prompt iteration.
  • Dataset curation from production traces.

Self-hosted OTel

  • Data stays in your boundary.
  • You integrate with existing SRE tooling.
  • More assembly required.
Practical Default
  • CI: deterministic offline suite on every prompt/model change.
  • Staging: trace-rich runs with synthetic tenants.
  • Prod: sampled traces + metrics; promote hard failures to pages.

Offline Versus Online

Eval modes and the tools that support them.

Trade-off
  • LLM-as-judge is cheap and biased. Calibrate against human labels on a slice; never let an unbounded judge be the only gate for safety-critical claims.

Failure Modes

  • Traces without policy decisions — you see the tool call, not why it was allowed.
  • Eval suites that share prompts with training or few-shot pools (contamination).
  • Dashboards nobody owns; alerts that always page false.

Deployment Tools

Models and agents still ship as artefacts into environments with rollouts, flags and CI. The AI-specific pieces (GPU images, long cold starts, token cost) plug into ordinary deployment engineering.

The Engineering Problem

Weights sit on a developer's disk. The API is started by hand on a GPU box. There is no image digest, no canary, no feature flag to disable a new tool. When the model misbehaves on Friday night, rollback means SSH and prayer.

Implementation Notes
  • Record model_digest, image_digest and config_hash on every response or trace.
  • Canary on both SRE signals (5xx, p95) and product signals (judge score, tool error rate).

Kill Switches and Flags

  • model_id: pin or shift traffic between registry versions.
  • prompt_rev: roll back a prompt without redeploying weights.
  • tools_enabled: disable a dangerous tool class during an incident.
  • agent_max_steps: tighten budgets when a cost incident hits.
  • rag_index_pointer: flip to the previous index digest.
Risk
  • Flags that change behaviour must themselves be audited. A wide-open tools_enabled=* in prod is an incident preset.

Failure Modes

  • "Snowflake" GPU boxes with hand-installed drivers.
  • Canaries that only watch HTTP 500s while quality collapses.
  • No link from deployed digest back to registry model card.

AI Coding Tools

Coding agents change how software is written. They do not change what "done" means: correct, reviewed, tested, licensed and operable. Treat Claude Code, Cursor, Copilot and peers as powerful but fallible collaborators.

The Engineering Problem

An engineer accepts a 400-line agent diff that "looks right". CI is green on weak tests. A dependency does not exist on PyPI. A licence-incompatible snippet was pasted from training-like memorisation. Production pages at 2 a.m. The agent was helpful. The process was absent.

What the evidence says

  • Code models solve many self-contained problems from a docstring; Codex (Chen et al., 2021) introduced HumanEval and the unbiased pass@k estimator used in Volume 10. Function-level benchmarks say little about repository work.
  • On real repositories, agents are limited as much by their interface as by the model. SWE-agent (Yang et al., 2024) showed that a purpose-built agent–computer interface (file viewer, search, lint-on-edit) raised SWE-bench resolution substantially over a raw shell.
  • Security: in a user study, participants with an AI assistant wrote less secure code and were more confident that it was secure (Perry et al., 2023). Review must not relax because the author was a model.
  • Productivity is task-dependent. In a randomised trial with experienced open-source developers working in their own mature repositories, allowing AI tools made them about 19% slower, although they believed they had been faster (Becker et al., 2025, METR). Measure on your own work; do not import headline speedups.

Where Each Tool Fits

  • Copilot-style completion: accelerate typing within a file you still steer turn by turn.
  • IDE agents (Cursor): multi-file features, refactors, navigating large codebases with rules and MCP.
  • CLI agents (Claude Code): longer autonomous loops, scriptable sessions, permissioned shell/edit operations.
  • PR bots: review assistance and suggested patches — never auto-merge without gates.

Benefits when used well

  • Faster boilerplate, tests, migrations and exploration.
  • Better onboarding when docs and rules are solid.
  • More time for design and evaluation work.

Costs when used poorly

  • Confident wrong code; hallucinated APIs and packages.
  • Homogenised mediocre design; skipped understanding.
  • Secret leakage into prompts; licence risk; weak review culture.
Risk
  • Do not paste production secrets into chat. Use secret scanners and exclude .env from indexed context.
  • Enterprise policies may restrict which repos and models are allowed — treat policy as a hard constraint.
Trade-off
  • METR and related studies suggest that on some experienced-developer tasks, AI tools can slow people down even when they feel faster. Calibrate with measurement, not vibes (paper cards).

Repository Context and Agent Instructions

Agents read what you leave for them. AGENTS.md, CLAUDE.md, Cursor rules and similar files are part of the product surface for AI-assisted development. Write them like runbooks, not like marketing.

The Engineering Problem

An agent invents a second HTTP client, a new logging format and a folder that violates your package layout. Reviewers blame the model. The repository never stated the conventions. Humans onboarded by oral tradition; the agent only has files.

Key Idea
  • Put durable instructions in version control next to the code.
  • Prefer short, testable rules over essays. Link to deeper docs.
  • One source of truth per concern; avoid contradictory AGENTS.md and CLAUDE.md clones that drift.

Context Budgets and Noise

  • Huge instruction files compete with code in the context window. Keep the always-on file short.
  • Use path-scoped rules (e.g. frontend vs backend) so agents do not load irrelevant constraints.
  • Generated code, vendor trees and lockfile blobs usually should be ignored by indexing.
  • Refresh instructions when CI commands change — stale commands cause hallucinated workflows.
Implementation Notes
  • If both AGENTS.md and CLAUDE.md exist, make one canonical and have the other point to it, or generate one from the other in CI.
  • Cursor project rules and Claude Code instructions should not contradict Makefile / justfile / package scripts.
Trade-off
  • Over-prescriptive rules make agents brittle. Under-prescriptive rules make them creative in the wrong places. Prefer rules you would enforce on a human junior hire.

Failure Modes

  • Contradictory instructions across README, AGENTS.md and chat memory.
  • Instructions that say "always" for something CI does not check.
  • Dumping the entire style guide into the hot context path.

AI-Assisted Engineering Workflows

The highest leverage use of coding agents is not "write my whole feature". It is structured loops: tests first, bisecting failures, review checklists and small PRs. SWE-bench and similar benchmarks reward repository-shaped problem solving — so should your workflow.

The Engineering Problem

An engineer prompts "implement the billing webhook" and receives a sprawling patch. Review takes longer than writing would have. Bugs hide in error paths nobody specified. The team concludes "AI doesn't work" when the workflow was unspecified.

Key Idea
  • Specify the contract before the implementation: types, tests, API shapes, acceptance checks.
  • Keep agent sessions task-scoped. Reset when the thread is confused.
  • Human owns design and merge decisions; agent owns draft labour under gates.

TDD with an Agent

  1. Write or sketch failing tests that define behaviour (you or agent under your review).
  2. Run tests; confirm they fail for the right reason.
  3. Ask the agent to make tests pass — without changing the tests unless you approve.
  4. Refactor with tests green; ask for edge cases next.
  5. Run the full gate (Chapter 12) before opening the PR.

Debugging Workflow

  • Paste the minimal failing reproduction, not the whole log firehose.
  • Ask for hypotheses ranked by likelihood; demand a single next experiment.
  • Prefer the agent to add a failing test that captures the bug before the fix.
  • When the agent spins, stop: re-state invariants, or debug yourself for ten minutes.

Review Workflow

Practical Default
  • One PR = one intent. If the agent did three things, split the commits or discard and retry.
  • Use agents to draft review comments on others' PRs, then verify every claim against the diff.
  • For refactors: require characterisation tests first.
Research Frontier
  • SWE-bench measures agents on real GitHub issues. Scores rise quickly; contamination and harness quality matter. Use it to choose tools, not to skip your own eval.
  • Productivity studies disagree by task and population (Peng/Ziegler vs METR). Instrument your team.

Failure Modes

  • Endless chat refinement instead of running the code.
  • Accepting refactors mixed into feature PRs.
  • No human review because "CI passed".

Prompt Patterns That Work in Repos

  • Contract first: "Here is the failing test output. Do not change the test. Make it pass."
  • File boundaries: "Only modify src/forge/serve/router.py and its tests."
  • Done definition: "Done means ruff, mypy and pytest green; paste the commands' output."
  • No drive-by: "Do not rename symbols or reformat unrelated files."
  • Ask before deps: "If you need a dependency, stop and propose it; do not edit lockfiles yet."

Code Review with Agents

  1. Human opens the PR and skims scope before asking an agent to review.
  2. Agent lists risks by severity with file:line references.
  3. Human verifies each claim; discards hallucinated "bugs".
  4. Security-sensitive files (auth, crypto, payments) get mandatory human deep-read regardless.
Risk
  • Agent review can rubber-stamp insecure patterns it also generates. Pearce et al. is the warning label: tools are not a secure SDLC by themselves.

Reproduce a SWE-bench-style loop on one open issue in your repo: failing test, patch, gate. Time yourself with and without an agent on two similar issues.

Validating Generated Code

Generated code fails in characteristic ways: inventing packages, ignoring types, skipping tests, introducing insecure defaults and mishandling licences. Build an automatic gate that catches these before review burns out.

The Engineering Problem

An agent adds import safe_requests_helper and a plausible PyPI name in requirements.txt. The name is unoccupied — or worse, later occupied by an attacker (slopsquatting). Install fails in CI today; supply-chain compromise tomorrow. Without a validation gate, review is the only thin line.

Key Idea
  • Never install a dependency the agent invented without verifying it exists and is the intended project.
  • Static gates (ruff, mypy, bandit, licence) are cheap. Use them always. Tests are necessary but not sufficient.

Hallucinated Packages

  • Check every new dependency against the official index and your allow-list / private mirror.
  • Prefer adding packages humans already use in the org; be suspicious of brand-new names in agent diffs.
  • Pin versions; avoid floating latest on security-sensitive libraries.
  • Monitor for typosquatting and slopsquatting on names agents commonly invent.
Risk
  • Spracklen et al. document widespread package hallucinations in LLM code suggestions. Treat new dependency lines as high severity in review.

Failure Modes

  • Skipping mypy because the agent "fixed" types with Any.
  • Using || true forever on audit steps.
  • Reviewers approving because the summary sounds authoritative.

What You Learned

  • Tools are evaluated like any other dependency: problem solved, mechanism, abstraction cost, when not to use them, lock-in and total cost of ownership, decided by a time-boxed spike on your own workload.
  • PyTorch plus Hugging Face is the default model-development stack; trackers and registries are separate concerns joined by run IDs and artefact digests.
  • Serving engines, RAG tooling, agent frameworks, eval platforms and deployment tools each abstract a specific layer of Volumes 11–22; knowing that layer is what lets you debug under the tool.
  • Agent frameworks provide control flow, not security; permissions, budgets and sandboxes stay in the harness (Volume 16).
  • AI coding tools range from completion to chat to autonomous agents; their output quality depends on repository context and explicit instructions as much as on the model.
  • Evidence on AI-assisted development is mixed: large gains on some tasks, slowdowns on others, and a measurable security risk. Verification gates, not trust, make it safe.
